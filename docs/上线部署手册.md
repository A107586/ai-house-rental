# 上线部署手册

把本项目放到公网上需要做的全部事情。分两部分：

- **第一至二节是「能不能上」**——合规与定位，技术上再完美也绕不过去；
- **第三节起是「怎么上」**——一步一步的操作，配置文件都在 `deploy/` 下。

> 全程只需要一条命令做自检：
> `python scripts/preflight_prod.py --env-file /etc/rental/rental.env`
> 它不过，就别发。

---

## 一、先承认三件事

这三条不是免责声明，是**会决定页面上该写什么字**的事实。

### 1.1 钱是假的

支付走的是**自建的模拟网关**（`server/app/gateway.py`），没有接任何真实
支付渠道。下单、回调、对账、退款的链路都是真的，**只有钱不是**。

所以：

- **绝不能让真实用户以为自己在付钱。** 缴费页、账单页、押金退款处
  必须有明确标注，例如「本系统为教学演示，支付为模拟流程，不涉及真实资金」。
- 别接真实收款码、别放收款二维码，别在任何地方留可转账的信息。

同一条边界还包括佣金结算（J-06）与押金退款：状态机做全，钱线下结。

### 1.2 合同没有法律效力

系统里的「租赁合同」是数据结构，不是合同。没有电子签名、没有实名核验的
可信第三方、没有存证。**页面必须写明它不构成任何法律意义上的合同**，
否则一旦有人当真，问题就不在技术层面了。

### 1.3 收真实个人信息要承担真实责任

系统会收集**姓名、手机号、身份证号**（身份证只存哈希与掩码，
手机号与姓名对外脱敏——这些是做了的）。但「做了脱敏」和
「可以收集」是两件事：一旦面向真实用户开放，《个人信息保护法》
对告知同意、最小必要、存储期限、泄露报告的要求就都适用了。

**给课程演示站的建议，按推荐程度排：**

| 方案 | 做法 | 代价 |
|---|---|---|
| **A（推荐）** | 只放演示数据，注册开放但**关闭实名与身份证录入**，首页显著位置标注「教学演示，请勿填写真实信息」 | 实名相关功能只能用种子数据演示 |
| B | 整站加一道访问口令（nginx `auth_basic`），只发给评审与老师 | 不是真正意义上的「上线」 |
| C | 面向真实用户开放并收集实名信息 | 需要隐私政策、用户协议、备案主体承担责任——**课程项目不建议** |

> 采用 A 时，把实名入口在前端隐藏、后端仍保留校验即可，
> 不必删代码——答辩时还要讲这部分设计。

### 1.4 域名与备案（服务器在中国大陆时）

用大陆服务器 + 域名对外提供服务，**必须先完成 ICP 备案**，
否则 80/443 会被拦。备案主体是个人或单位，审批周期通常按周计。

绕不开备案的两个常见选择：

- 用境外或港澳节点（访问速度差一些，且仍受各自法规约束）；
- 只用 IP + 非标准端口做内部演示（严格说不算公开服务，也容易被误判）。

**这一步要最先启动**，它的周期比其他所有步骤加起来都长。

## 二、上线形态

```
             用户浏览器
                 │  HTTPS(443)
                 ▼
        ┌──────────────────┐
        │  nginx           │  TLS 收口 / 静态文件 / 限流
        └───┬─────────┬────┘
   /api/    │         │   /agent/
            ▼         ▼
  ┌──────────────┐  ┌──────────────┐
  │ 业务后端      │  │ 智能体服务    │
  │ 127.0.0.1:8080│◄─┤127.0.0.1:8000│   ← 智能体通过 HTTP 找后端取数
  │ uvicorn ×4   │  │ uvicorn ×2   │
  └──────┬───────┘  └──────┬───────┘
         │                 │
         ▼                 ▼
      MySQL 8          大模型 API（可缺席）
```

**两个应用都只监听 127.0.0.1。** 这不是洁癖：

- 业务后端一旦能被直接访问，`X-Forwarded-For` 就成了谁都能写的东西，
  限流与操作日志里的 IP 会全部失真；
- 智能体服务**自己没有登录态**（鉴权全在业务后端，它只转发用户令牌），
  把 8000 暴露出去，等于把一个按次计费的接口摆在公网上。

以 Ubuntu 22.04、2 核 4G 为例（这套东西跑得动，但别指望扛并发）。

```bash
sudo apt update
sudo apt install -y python3.11 python3.11-venv python3-pip \
                    mysql-server nginx certbot python3-certbot-nginx git
curl -fsSL https://deb.nodesource.com/setup_20.x | sudo -E bash -
sudo apt install -y nodejs

# 专用账号，不要用 root 跑服务
sudo useradd -r -m -d /srv/rental -s /usr/sbin/nologin rental
sudo install -d -o rental -g rental /var/log/rental
```

拉代码并装依赖：

```bash
sudo -u rental git clone https://github.com/A107586/ai-house-rental.git /srv/rental
```

## 四、数据库

```sql
CREATE DATABASE rental DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE USER 'rental'@'127.0.0.1' IDENTIFIED BY '换成强口令';
GRANT SELECT, INSERT, UPDATE, DELETE ON rental.* TO 'rental'@'127.0.0.1';
FLUSH PRIVILEGES;
```

> 应用账号**不给 DDL 权限**（没有 CREATE / DROP / ALTER）。
> 建表用管理员账号执行一次建库脚本即可；应用运行期不需要改结构。

建表：

```bash
mysql -u root -p rental < "docs/评审/第6小组_基于AI智能体的房屋租赁系统_建库脚本_MySQL.sql"
```

这份脚本由 `scripts/gen_db_sql.py` 从模型生成，**执行前先确认它是最新的**：

```bash
python scripts/gen_db_sql.py --check
```

### 要不要灌演示数据

`server/seed.py` 会造一批房源、合同、账单与一个 `admin / admin123` 账号。

- **演示站**：灌。但**装完立刻改管理员口令**——`admin123` 写在 README 里。
- **真开放给用户**：不灌，手工建一个管理员账号。

`preflight_prod.py` 会去库里试 `admin123`，还没改就不让发。

## 五、配置

```bash
sudo install -d -m 750 /etc/rental
sudo cp deploy/rental.env.example /etc/rental/rental.env
sudo chmod 640 /etc/rental/rental.env
sudo chown root:rental /etc/rental/rental.env
sudo nano /etc/rental/rental.env
```

**必改的五项**（不改则服务拒绝启动）：

| 变量 | 为什么必须改 |
|---|---|
| `APP_ENV=production` | 不设则整套启动自检不执行，配置错了也照样起得来 |
| `AUTH_SECRET` | 默认值在公开仓库里，**拿到它可以自己签一个管理员令牌** |
| `PAYMENT_SIGN_SECRET` | 支付回调无登录态、只认签名，**拿到它可以把任意账单改成已付** |
| `DATABASE_URL` | 不设会落到 SQLite，库级写锁，多 worker 互相抢 |
| `CORS_ORIGINS` | 不设会停在 localhost，前端一个接口都调不通 |
| `TRUSTED_PROXY_HOPS` | 决定限流与操作日志怎么取客户端 IP，见下一节 |

两个密钥各生成一个，**不要用同一个值**：

```bash
python -c "import secrets;print(secrets.token_urlsafe(48))"
```

### 关于 `TRUSTED_PROXY_HOPS`

这一项对应一个实测出来的洞：限流按 IP 计数，而 IP 原先取
`X-Forwarded-For` 的**第一段**——那一段是请求方自己填的。

```
同一个伪造 IP 连打 10 次: [401×8, 429, 429]   ← 限住了
换成 8.8.8.8: 401                              ← 又放行了
```

现在默认不信任转发头；设为 `1` 时从**右边**数第一段，
而右边那段由 nginx 追加，客户端够不着。所以
`TRUSTED_PROXY_HOPS=1` 必须与 nginx 的
`proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;` **成对出现**。

## 六、构建与启动

```bash
# 前端（构建产物由 nginx 直接发）
cd /srv/rental/web
sudo -u rental npm ci
sudo -u rental npm run build

# 两个服务
sudo cp deploy/rental-api.service deploy/rental-agent.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now rental-api rental-agent
sudo systemctl status rental-api rental-agent

# nginx —— **顺序不能反**，见下面的说明
sudo tee /etc/nginx/sites-available/rental >/dev/null <<'CONF'
server {
    listen 80;
    server_name rent.example.com;
    root /srv/rental/web/dist;
    location /.well-known/acme-challenge/ { allow all; }
    location / { try_files $uri $uri/ /index.html; }
}
CONF
sudo ln -s /etc/nginx/sites-available/rental /etc/nginx/sites-enabled/
sudo nginx -t && sudo systemctl reload nginx

# 先签证书（这一步要求域名已解析到本机，且 80 端口通）
sudo certbot certonly --webroot -w /srv/rental/web/dist -d rent.example.com

# 证书到位之后，再换成正式配置
sudo cp deploy/nginx-rental.conf /etc/nginx/sites-available/rental
sudo sed -i 's/rent.example.com/你的域名/g' /etc/nginx/sites-available/rental
sudo nginx -t && sudo systemctl reload nginx
```

> **顺序为什么不能反：** `deploy/nginx-rental.conf` 里写着
> `ssl_certificate /etc/letsencrypt/live/...`，而那个文件在签证书之前
> 根本不存在——直接套用会让 `nginx -t` 失败，nginx 起不来，
> 接着 certbot 也没法通过 80 端口完成验证，卡成一个环。
> 所以先用一段只有 80 的临时配置把域名验证做完，再换正式配置。
>
> 证书续期由 certbot 自带的定时任务处理，`sudo certbot renew --dry-run`
> 可以验一次。

防火墙只开 80/443：

```bash
sudo ufw allow 80,443/tcp
sudo ufw enable
sudo ss -ltnp | grep -E '8000|8080'   # 应当只看到 127.0.0.1
```

> 前端的智能体地址不用手工配：构建产物在 https 页面下会**自动走同源
> `/agent`**（由 nginx 转发）。这是刻意的——原先写死
> `http://主机名:8000`，放到 https 站点上会被浏览器按混合内容拦掉，
> 而界面上只表现为「智能体没反应」。需要覆盖时用 `VITE_AGENT_BASE`。

## 七、发布前预演与发布后冒烟

### 发布前

```bash
python scripts/preflight_prod.py --env-file /etc/rental/rental.env
```

它查九件事：五项必改配置、数据库连不连得上、管理员口令是不是还叫
`admin123`、前端构建产物在不在、建库脚本与模型是否一致。

### 发布后（逐条手点，别跳）

| # | 检查 | 通过标准 |
|---|---|---|
| 1 | `curl -s https://域名/health` | `status: ok`，且**没有** `auth_secret_is_default: true` |
| 2 | `curl -s https://域名/agent/health` | `status: ok`，`word_level: true` |
| 3 | 首页 | 房源列表出得来，图片显示正常 |
| 4 | 注册 → 登录 → 收藏 | 三步都成功 |
| 5 | 浏览器控制台 | 没有 Mixed Content、没有 CORS 报错 |
| 6 | 智能体问一句「押金怎么退」 | 有回答且带引用 |
| 7 | 故意连错 9 次密码 | 第 9 次返回 429；**换个 VPN/热点再试**，计数不该重置 |
| 8 | 管理后台 → 操作日志 | 记录里的 IP 是你的真实出口 IP，不是 `127.0.0.1` |
| 9 | `sudo systemctl restart rental-agent` 后刷新首页 | 智能体状态变「未连接」，但**找房、登录、账单照常可用** |

> 第 7、8 条是这次修的那个洞的验收；第 9 条是需求 N-07 的验收
> （智能体挂了不能拖垮交易链）。

## 八、上线之后要盯的

### 8.1 备份

数据库与上传目录都要备，**两者缺一不可**：只备库，图片全丢；
只备图片，业务数据全丢。

```bash
# /etc/cron.daily/rental-backup
mysqldump --single-transaction --default-character-set=utf8mb4 \
  -u backup -p'口令' rental | gzip > /var/backups/rental-$(date +%F).sql.gz
tar czf /var/backups/rental-static-$(date +%F).tar.gz /srv/rental/server/static
find /var/backups -name 'rental-*' -mtime +14 -delete
```

**备份要试着恢复一次**，没恢复过的备份不算备份。

### 8.2 日志

两个服务都写在 `/var/log/rental/` 下，用 logrotate 切：

```
/var/log/rental/*.log {
    daily
    rotate 14
    compress
    missingok
    copytruncate
}
```

慢请求日志（超过 `SLOW_REQUEST_MS`）会打在里面，是性能问题的第一手线索。

### 8.3 花钱的那条线

大模型按次计费。公网上任何人都能触发 `/agent/*`，所以：

- nginx 已对 `/agent/` 单独限流（每 IP 1r/s，突发 5）；
- 智能体自身有单次与单轮预算、连续失败 2 次熔断 60 秒；
- **上游账户务必设消费上限**——这是最后一道闸，前两道都是自家代码；
- 真出事时的止血开关：把 `FUSION_ENABLED` 改成 `false` 再重启智能体，
  整站退回纯规则模式，功能仍在。

### 8.4 监控

最省事的做法：每分钟 curl 一次两个 `/health`，连续三次失败就告警。
`/health` 里的 `houses` 数量顺带能发现「库连上了但数据没了」。

## 九、已知的不足（上线后仍存在）

诚实列出来，因为它们会影响上线之后的判断。

| # | 不足 | 现在怎么办 | 要根治需要 |
|---|---|---|---|
| 1 | 应用内限流是**进程内计数**，4 个 worker 等于阈值放大 4 倍 | nginx 层再限一道（已配） | 换 Redis 计数 |
| 2 | 上传文件存在**本地磁盘** | 单机部署没问题 | 多机要换对象存储 |
| 3 | 没有验证码 | 靠限流把撞库成本抬起来 | 接入验证码服务 |
| 4 | 找回密码**没有邮件/短信通道** | 重置码由管理员在后台发 | 接短信服务商（需实名与资质） |
| 5 | 向量检索通道**从未在真实嵌入服务上验证过** | 留空即可，纯词法检索功能完整 | 找一台能跑嵌入模型的机器验证 |
| 6 | 服务端的**日期相关测试没有自动扫描** | 人工留意 | 把「现在」收口到一处，见 `scripts/run_at_dates.py` 的说明 |
| 7 | 没有灰度与回滚脚本 | 回滚 = `git checkout 上一版` + 重启 | 双目录部署 + 软链切换 |

## 十、回滚

出问题时最快的一条路：

```bash
cd /srv/rental
sudo -u rental git log --oneline -5          # 找到上一个好版本
sudo -u rental git checkout <那个提交>
sudo -u rental .venv/bin/pip install -r server/requirements.txt
cd web && sudo -u rental npm run build
sudo systemctl restart rental-api rental-agent
```

**数据库不要跟着回滚。** 本项目的表结构变更一直是「只加不改」
（加表、加列），旧代码跑新库是安全的；反过来把库回退，
新写进去的数据会丢。
