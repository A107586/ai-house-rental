# 中介（经纪人）功能设计方案

> 编号 **J-01 ～ J-09**
> 起草：2026-09-04
> 硬约束：**9/24 数据库评审前定表** · **10/16 代码封版**

---

## 0. 先说立场

**《贝壳对比改进报告》第 5 节明确写过「不建议做经纪人体系」**，理由是
「我们是房东直租模型，没有经纪人这一层」。现在要做，那份判断需要一个交代。

那句话没错，错在它只否掉了**贝壳那一版**的经纪人。贝壳的经纪人体系里
真正撑起来的是 ACN 跨机构协同、门店组织、虚拟号呼叫中心——这三样我们
确实一样都够不着。但把它们拿掉之后，剩下的内核是成立的：

> **房东不想自己带看。**

这是租赁市场里真实存在、且我们系统当前**完全没有出口**的一个需求。
现在房东必须自己处理每一条预约、自己去开门、自己回每一句咨询。
一个在外地工作的房东，或者手上有五套房的房东，这套系统对他是不可用的。

所以这份方案做的是**「委托 - 带看 - 成交 - 分佣」这条服务链**，
不是「经纪机构组织架构」。判断一个功能点该不该进来，只问一句：
**它是否服务于「房东把带看这件事托付出去」**。不是的一律不做（见第 10 节）。

最后一条要单独说：**贝壳自己就在用 AI 把用户的自然语言诉求整理成摘要
交给经纪人。** 而我们已经有 `/agent/parse`（K-06）在做前半段——
把一句话翻译成结构化条件。把它接到中介手上是顺水推舟，不是新造轮子。

## 2. 中介在我们的模型里凭什么存在

先划清楚它**不是**什么：

- **不是二房东**：房源产权与合同甲方永远是房东，中介不持有房源；
- **不是必经环节**：房东可以继续自管，直租模式一点不变；
- **不是新的房源来源**：中介**不能凭空发房源**。房源必须由房东先发布，
  再委托出去——否则「这套房到底是谁的」在数据上就没有源头了。

它是什么：**房东可以就某一套房，把「带看 + 咨询答复」委托给一个中介，
成交后按约定比例付佣金。**

一句话概括数据上的变化：

```
现在：房源 ──归属──> 房东 ──同时也是──> 带看人、答复人、签约甲方

之后：房源 ──归属──> 房东 ────────────> 签约甲方（不变）
             └──委托──> 中介 ──────────> 带看人、答复人（可选，且可撤销）
```

## 3. 角色与权限 —— 这是最难的一块

**建表是简单的，难的是权限。** 现有代码有三处硬编码假设了「房源相关的
操作者 == 房东本人」：

| 位置 | 现在的写法 | 问题 |
|---|---|---|
| `server/app/deps.py:56` | `require_staff`：role ∈ {landlord, admin} | 中介两者都不是，所有房源接口直接 403 |
| `server/app/main.py:2527` | `_require_house_owner`：`house.landlord_id != user.id` | 中介管不了受托房源 |
| `server/app/models.py` | `Conversation` 写死 `tenant_id` / `landlord_id` | 会话只能是租客↔房东两方 |

### J-01 角色：新增 `agent`，注册时直接选

`users.role` 保持单值（K-13 已经论证过改多角色会牵动全站，风险远大于收益）。
新增第四种取值 `agent`。

**入口最后落在注册，而不是 K-13 那条 tenant→agent 升级路。** 原方案写的是
复用升级入口，实现时改了，理由有两条：

- 中介是一份**职业**，不是租房租着租着升上去的身份。真实世界里没有
  「我先租两年房再转做经纪人」这条路径，贝壳的经纪人也是招进来的。
- 自助注册之所以安全，全靠资质审核这道闸：**`role == agent` 本身不给
  任何权限**，接不了单、管不了任何房源，工作台上除了「提交资质」什么
  都没有。既然如此，把注册也卡死只会逼着每个中介去找管理员开户。

反过来，**中介不能一键转房东**（`become-landlord` 对 agent 直接 400）。
这不是对称性洁癖：角色一旦变成 landlord，他手上在托房源的管理权立刻
全部消失（`can_manage_house` 要求 `role == "agent"`），而页面上不会有
任何提示，房东那边也不知道自己的委托已经失效。要转就先把委托解除干净——
那是一次需要本人确认的迁移，不该由一个「升级为房东」按钮顺手完成。
（回归用例：`TestAgentRole.test_agent_cannot_flip_to_landlord`）

**中介升级必须比房东更严**：房东只要实名 + 手机号，中介还要提交
从业资质材料并由管理员审核通过——因为中介是**代表平台去面对租客的人**，
房东只代表他自己。这一条直接复用 K-07 的核验状态机
（未提交 / 待审核 / 已通过 / 未通过），不用另发明一套。

同样**不提供反向降级**（与 K-13 一致）：手上还有在托房源的中介降回租客，
那些委托关系就没有受托方了。要退出得先解除全部委托。

### J-02 权限：从「是不是房主」改成「能不能管这套房」

把 `_require_house_owner` 换成一个能力判断，这是整个改造的枢纽：

```python
def can_manage_house(session, user, house) -> bool:
    """谁能管这套房。

    **不要在接口里散着写 role 判断**——现有代码就是因为把「房东」
    和「能管这套房的人」当成同一件事，才在加中介时处处要改。
    """
    if user.role == "admin":
        return True
    if house.landlord_id == user.id:
        return True                      # 房东永远管得了自己的房
    return has_active_delegation(session, house.id, user.id)   # 受托中介
```

三条必须写死的规则：

1. **房东的权限不因委托而丧失。** 委托是「多一个人能管」，不是「换人管」。
   房东随时可以自己回消息、自己改房源、单方面解除委托。
   反过来做（委托期间房东被锁住）是把工具做成了枷锁。
2. **中介只能管**「有生效委托」**的那几套房**，且**不能删房源、不能改
   房源归属、不能发起签约**。签约是钱和法律责任，必须房东本人点。
3. **委托一解除，权限立刻消失**，但已经产生的带看记录、会话记录留存
   （问责需要）。

### J-03 会话：两方不变，「对方」是谁随委托而变

`Conversation` 保持两方模型，不改成三方群聊——三方会话会立刻带出
「谁看得见哪条」「中介退出后历史归谁」一堆问题，而租客的心智里
本来就只有「我和这套房的负责人在聊」。

做法是给会话加一列 `responder_id`（当前答复人的 user_id）：

- 无委托：`responder_id = landlord_id`，和现在完全一样；
- 有委托：`responder_id = agent_id`，租客发的消息通知到中介；
- **房东对自己房源的会话始终有读权限**——他委托的是带看，不是知情权。
  这一条要在界面上明说，否则房东会觉得平台把他架空了。

## 4. 数据模型

**这批表必须赶在 9/24 数据库评审之前定稿**（与 K-04 同一个理由：
评审之后再动表要重走流程）。

### 表一 `agent_profiles` —— 中介档案

| 字段 | 类型 | 说明 |
|---|---|---|
| `user_id` | FK users | 一对一 |
| `real_name` / `phone` | — | 复用 users 上的，不重复存 |
| `license_no` | String(40) | 从业资格证号（对标贝壳的「经纪备案」） |
| `license_status` | String(20) | unsubmitted / pending / approved / rejected |
| `license_images` | Text | 资质材料图片，逗号分隔 |
| `reviewed_by` / `reviewed_at` / `reject_reason` | — | 审核留痕 |
| `service_districts` | String(120) | 主营区域，逗号分隔（对标「主营商圈」） |
| `intro` | String(300) | 自我介绍 |
| `years` | Integer | 从业年限，**唯一允许自填的展示字段** |
| `accepting` | Boolean | 是否接单（休假、满负荷时关掉） |

**统计字段一个都不存。** 累计成交、月带看量、好评率全部由明细表聚合
得出——这是需求 R-05 的原话「汇总数据必须由明细表自动聚合产生，
不允许人工另行录入」。让中介自己填成交数，那个数字就一文不值了。

### 表二 `house_delegations` —— 委托关系（核心表）

| 字段 | 类型 | 说明 |
|---|---|---|
| `house_id` / `landlord_id` / `agent_id` | FK | 三方 |
| `status` | String(20) | pending / active / rejected / ended |
| `initiated_by` | String(10) | landlord / agent，谁发起的 |
| `commission_rate` | Numeric(5,2) | 佣金比例，按**月租金的百分比** |
| `start_at` / `end_at` | DateTime | 委托期 |
| `end_reason` | String(100) | 解除原因 |

三条约束：

1. **双向确认才生效。** 房东可以邀请中介，中介也可以申请接单，
   但都要另一方点头。单方面就能建立委托，等于允许中介给自己派活。
2. **一套房同时只能有一个 active 委托。** 两个中介同时在托，
   带看归谁、佣金归谁就说不清了——这正是贝壳要用 ACN 那么复杂的
   一套规则去解决的问题，而我们没有解决它的必要。用唯一索引挡住。
3. **房源下架 / 签约生效时自动结束委托**，不留悬空关系。

### 表三 `viewing_records` —— 带看记录

贝壳把带看当成一等数据（ACN 里它直接参与分佣），我们也该如此。
现在系统里只有「预约」，**没有「预约之后发生了什么」**——
房东看得到有人约，看不到有没有来、看了觉得怎么样。

| 字段 | 类型 | 说明 |
|---|---|---|
| `appointment_id` | FK appointments | 从预约来 |
| `house_id` / `tenant_id` / `agent_id` | FK | 谁带谁看了哪套 |
| `showed_up` | Boolean | 租客是否到场（放鸽子率是有意义的信号） |
| `duration_minutes` | Integer | 看了多久 |
| `feedback` | Text | 中介填的租客反馈 |
| `concerns` | String(200) | 结构化的关注点/异议，逗号分隔 |
| `intention` | String(10) | high / medium / low，成交意向 |
| `created_at` | DateTime | — |

### 表四 `agent_commissions` —— 佣金

| 字段 | 类型 | 说明 |
|---|---|---|
| `contract_id` / `agent_id` / `delegation_id` | FK | 来源 |
| `base_amount` | Numeric(10,2) | 计佣基数（月租金） |
| `rate` | Numeric(5,2) | 比例 |
| `amount` | Numeric(10,2) | 应付金额 |
| `status` | String(20) | pending / settled / cancelled |
| `settled_at` | DateTime | — |

**不复用 `bills` / `payments`。** 那两张表描述的是「租客付给房东」的
交易链，字段（`contract_id`、`type`、`due_date`）全是按那条链设计的。
佣金是「房东付给中介」，付款方、收款方、触发条件都不同，
塞进去只会让两边的字段互相为空——和 K-08 不复用 `content_flags`
是同一条理由。

## 5. 业务流程

### J-04 委托的建立与解除

```
房东视角：工作台 → 我的房源 → 某套房 → 「委托中介带看」
          → 按主营区域看到候选中介（含带看量、好评率）
          → 选一个，填佣金比例，发出邀请
          → 中介接受 → 委托生效

中介视角：工作台 → 「接单」→ 看到按我的主营区域筛出的待委托房源
          → 申请接单 → 房东同意 → 委托生效
```

解除：任一方都可以解除，但**必须填原因**，且要通知对方。
有未完成的预约时给出提示（「这套房还有 2 条待看房预约，
解除后将转回你自己处理」），但不阻止——委托关系不该变成绑定关系。

### J-05 预约与带看

预约的通知路由跟着 `responder_id` 走：

```
租客提交预约
   ├─ 无委托 → 通知房东（现状不变）
   └─ 有委托 → 通知中介，**房东同时收到一条抄送**
                （他的房子有人要看，他有权知道）

中介确认时段 → 带看当天 → 中介填带看记录
   └─ 房东收到带看纪要（到场与否、反馈、意向）  ← 这是房东委托的核心收益
```

### J-06 成交与佣金

签约仍由**房东本人**发起（J-02 规则 2）。合同生效时：

1. 若该房源有 active 委托 → 生成一条 `agent_commissions`（pending）；
2. 合同上记一个 `agent_id`（促成中介），用于中介的「累计成交」统计；
3. 委托自动结束（房子已经租出去了）。

**佣金结算不接真实资金**——和《待完善清单》D-1 同一个边界，
状态机做全（pending → settled），钱由平台在线下结。

## 6. J-07 隐私：真手机号不给中介

贝壳用虚拟拨号平台，我们做不了电话，但**那条原则可以完整照搬**，
而且我们本来就是这么做的——`/api/houses/{no}/landlord` 的注释原话是：

> **刻意不返回联系方式。** 平台的价值就在于居间，把手机号直接摆出来
> 等于鼓励双方绕过平台私下成交。

中介这里要守同一条，而且更要紧——中介比房东更有动机把交易引到站外
（省掉平台佣金）。三条措施：

1. **租客与中介的联系一律走站内会话**，双方都看不到对方真号；
2. **手机号只在带看当天、且预约已确认的窗口内互相可见**（脱敏后四位），
   过期即收回。这是「虚拟号有效期」的可实现替代；
3. **免打扰**：租客可设置「不接受主动联系」，中介端的联系按钮随之置灰。

`app/moderation.py` 已有的「私下联系方式拦截」对会话生效
（`routers/conversation.py:127`），中介会话自动继承这条。

## 7. J-08 信用与问责

对标贝壳详情页那一行（发布人 / 备案 / 服务标准 / 投诉记录 / 处罚记录）。
我们的版本：

| 展示项 | 数据来源 | 是否可自填 |
|---|---|---|
| 备案号与核验状态 | `agent_profiles.license_*`，管理员审核 | ❌ |
| 主营区域 | 自填 | ✅ |
| 从业年限 | 自填 | ✅ |
| 累计成交 | `contracts` 按 `agent_id` 聚合 | ❌ |
| 近 30 天带看 | `viewing_records` 聚合 | ❌ |
| 好评率 | `reviews` 聚合 | ❌ |
| 被举报次数 / 处理结果 | `house_reports`（K-08）扩展举报对象 | ❌ |

**未核验的中介不得接单。** 这和 K-07 里「未核验不画成已核验的样子」
是同一条原则的两面：那边是不美化，这边是不放行——
一个没验过资质的人代表平台去见租客，风险比一条假房源大得多。

## 8. AI 角度 —— 这才是课程的得分点

前七节都是 CRUD 脚手架，必要但不加分。真正值得在答辩上讲的是下面三条，
而且**每一条都复用已有的智能体能力，不是新起炉灶**。

### J-09-a 需求摘要交接（最该做的一条）

贝壳的原文是「根据您向贝壳布丁发起的咨询向经纪人发送您的**个人需求摘要**」。
我们的链路更短，因为前半段已经有了：

```
租客说：「中山区两室一厅，租金三千以内，最好带电梯，
         主要是上班近，周末想看房」
   │
   ├─ /agent/parse（K-06 已有）→ 结构化条件
   │     {区域:中山区, 户型:两室一厅, 租价≤3000, 设施:[电梯]}
   │
   └─ 新增：把「条件 + 原话里条件表达不了的部分」整理成一段摘要
         → 随咨询一并发给中介

中介看到的：
   ┌─────────────────────────────────────────┐
   │ 需求摘要（由智能体整理，供参考）              │
   │ 硬条件：中山区 · 两室一厅 · ≤3000元 · 带电梯 │
   │ 其他：看重通勤距离；希望周末看房              │
   │ 已浏览：DL0032、DL0041（均为中山区两室）      │
   └─────────────────────────────────────────┘
```

**价值在哪**：中介不必让租客把需求再复述一遍。而「让用户重复说一遍
刚才已经说过的话」正是所有客服系统最招人烦的地方。

**为什么这条最该做**：它把 K-06 的产出接到了一个新场景上，
证明「智能体解析出来的结构化条件」是有复用价值的资产，
而不只是喂给一次查询就丢掉。

### J-09-b 智能派单：给这条需求推荐中介

租客发起咨询、或房东要选中介时，按规则打分排序：

| 因子 | 理由 |
|---|---|
| 主营区域是否覆盖该房源所在区 | 硬条件，不覆盖直接排除 |
| 近 30 天带看量 | 反映活跃度 |
| 当前在托房源数 | **负载均衡**——手上二十套的中介接不过来 |
| 好评率 | 质量 |
| 是否开启接单 | 硬条件 |

规则先算，大模型可选地在同分时给一句「为什么推荐他」的说明。
沿用 `app/fusion.py` 的三条护栏（大模型不可用照常工作、硬规则不接受
覆盖、输出必须能校验），**不新造融合逻辑**。

### J-09-c 带看纪要整理

中介带完看，口述或简写几句：

```
输入：「小两口，觉得朝向可以，嫌厨房小，问了能不能养猫，
       说要和家里商量下」

输出：{
  "showed_up": true,
  "intention": "medium",
  "concerns": ["厨房面积"],
  "positives": ["朝向"],
  "questions": ["是否可养宠物"],
  "summary": "看房人对朝向满意，主要顾虑是厨房偏小；
              询问可否养宠物；需回去商量，意向中等。"
}
```

这段结构化输出有三个下游：房东能看懂的纪要、房源的「常见异议」聚合
（同一套房被三个人嫌厨房小，房东该降价或该在描述里说明了）、
以及租客画像（喂给 AI-07 推荐）。

**降级要求同全项目**：大模型不可用时，规则提取关键词 + 原文照登，
纪要照样能存，只是不结构化。

## 8.5 后台系统：中介工作台与管理员治理

前面七节把「中介能做什么」定下来了，这一节定**「他们在哪儿做」**。
两个后台，加上平台层的统计。

### 统计的三条规矩（先定，后面所有数字都照这个来）

1. **一个数字都不许存。** 在托量、带看量、成交量、好评率全部由明细表
   实时聚合。这是需求 R-05 的原文：「汇总数据必须由明细表自动聚合产生，
   不允许人工另行录入」。存汇总字段的下场是它和明细对不上，
   而且对不上的时候没人知道该信哪个。
2. **一个页面一个接口。** 工作台十个卡片就打十次请求，是最容易写出来、
   也最容易把首屏拖慢的做法。房东工作台 `/api/landlord/dashboard` 已经
   是一次返回全部，照着做。
3. **比率必须带分母。** 「成交率 25%」和「12 次带看成交 3 单」是同一个
   数字，但前者在样本只有 4 次带看时是误导。所有比率一律
   `{"rate": 25.0, "hit": 3, "total": 12}` 这种形状，界面上把分母写出来。

### J-10 中介工作台

顶部导航复用房东那套（`role === 'agent'` 时显示「工作台」），
面板结构对齐 `LandlordPanel`，页签如下：

| 页签 | 内容 | 数据来源 |
|---|---|---|
| **今日待办** | 待我确认的委托邀请、今天要带看的、带看完没填记录的、有未读消息的会话 | 聚合 |
| **接单** | 按我的主营区域筛出的可接房源；已发出的申请 | `house_delegations` |
| **在托房源** | 我受托的房源，可编辑、上下架、传图、提交核验 | `house_delegations` + `houses` |
| **带看记录** | 我的带看流水，可补填 | `viewing_records` |
| **佣金** | 待结 / 已结明细 | `agent_commissions` |
| **我的档案** | 资质状态、主营区域、接单开关、对外展示的统计 | `agent_profiles` |

**数据卡片（`GET /api/agent/dashboard` 一次返回）：**

| 卡片 | 口径 | 为什么是这个口径 |
|---|---|---|
| 在托房源 | `status='active'` 的委托数 | — |
| 近 30 天带看 | `viewing_records` 按 `created_at` 计 | 对标贝壳的「月总带看」；用 30 天滚动而不是自然月，月初不会突然清零 |
| 本月成交 | 合同 `agent_id = 我` 且本月生效 | — |
| 带看成交率 | 成交数 / 带看数，**带分母** | 中介自己最该看的一个数 |
| 待结佣金 | `status='pending'` 求和 | — |
| 好评率 | 评价聚合，**带分母** | — |
| 放鸽子率 | `showed_up=false` / 总带看 | 这个数高说明预约确认流程有问题，不是中介的问题——**要能区分开** |

**空态要有内容。** 新中介进来看到的不该是一片 0 和三张空表格，
而是「你还没有在托房源，去『接单』看看有哪些房东在找中介」。
一屏零数据的后台会让人以为系统坏了。

### J-11 管理员：中介治理

管理后台加两个页签，并把中介口径并进已有的「数据看板」。

**页签一：中介资质审核**（对标已有的「房源审核」）

待审队列 → 看资质图片 → 通过 / 驳回并填理由。
驳回理由必填，理由同 K-08：「已处理」三个字对被驳回的人毫无意义。

**页签二：中介档案**（对标已有的「户主档案」`/api/admin/landlords`）

每个中介一行：资质状态、主营区域、在托、近 30 天带看、累计成交、
好评率、**被举报次数与处理结果**。支持按资质状态筛、按用户名搜。

这一页的作用是回答「这个中介靠不靠谱」，所以**被举报记录必须在这里**，
而不是只躺在举报页签里。

**并入数据看板的平台级指标**（`/api/stats` 扩展）：

| 指标 | 口径 |
|---|---|
| 中介总数 / 待审资质数 | 待审数要能点进去 |
| 在托房源占比 | 有 active 委托的房源 / 可租房源 |
| 平台近 30 天带看总量 | — |
| 委托房源 vs 自管房源的成交率对比 | **这是唯一能回答「中介到底有没有用」的数字**，做了中介功能就该敢于把它摆出来 |

最后一条要说明：如果委托房源的成交率反而更低，那说明这个功能没起作用，
应该如实显示。**看板不是用来证明功能有价值的，是用来发现它没价值的。**

### 接口清单

```
GET   /api/agent/dashboard          中介工作台一次取全
GET   /api/agent/delegations        我的委托（按状态筛）
GET   /api/agent/commissions        我的佣金明细
GET   /api/agent/viewings           我的带看流水
GET   /api/agent/open-houses        可接单的房源（按主营区域）

GET   /api/admin/agents             中介档案列表（含聚合统计）
GET   /api/admin/agent-queue        待审资质队列
PATCH /api/admin/agents/{user_id}   审核资质：通过 / 驳回 + 理由
GET   /api/stats                    扩展中介口径（不新增接口）
```

### 验收用例（直接抄进《测试说明》）

- **委托双向确认**：房东单方面发出邀请 → 委托为 pending，中介此时**管不了**这套房；中介接受后才管得了
- **一房一委托**：同一套房再委托第二个中介 → 拒绝
- **房东权限不丢**：委托期间房东仍能改房源、回消息、解除委托
- **权限即时回收**：解除委托后中介访问该房源的管理接口 → 403，但历史带看记录仍在
- **中介不能发房源**：中介调 `POST /api/houses` → 403
- **中介不能签约**：中介调 `POST /api/contracts` → 403
- **未核验不得接单**：`license_status != approved` 的中介申请接单 → 拒绝
- **预约抄送**：委托中的房源被预约 → 中介收到通知，**房东也收到一条**
- **带看纪要回流**：中介填完带看记录 → 房东在工作台看得到到场情况与反馈
- **佣金生成**：合同生效 → 生成一条 pending 佣金，金额 = 月租 × 比例；委托自动结束
- **统计不可自填**：中介试图 PATCH 自己的成交数 → 该字段不在可写白名单里
- **真号不外泄**：中介查看租客资料 → 手机号为掩码；未确认预约时不可见
- **AI 需求摘要**：租客用一句话咨询 → 中介端出现结构化需求摘要，且**智能体停掉时**咨询照常发出，只是没有摘要

> **命名提醒**：这一列叫 `responder_id`，不叫 `handled_by`。
> `ContentFlag.handled_by` 已经存在，是 `String(50)` 存用户名；
> 而这里要的是 users 的外键。同名不同型是最容易读错的一类字段，
> 宁可名字长一点。（`HouseReport` 用的是第三种写法 `handler_id`——
> 这三处口径不一致本身就该找个时间统一，但不要在这次改动里顺手做。）

## 12. 风险与建议

**三个必须说清楚的风险：**

1. **权限改造是真风险。** 现有代码把「房东」和「能管这套房的人」当成
   同一件事，30 多个接口依赖 `require_staff`。这一改动到全站，
   而且**改错的表现是越权**——不是功能不好用，是安全问题。
   建议：先写 `can_manage_house()` 和它的测试，再逐个接口替换，
   每换一批跑一次全量。

2. **它会挤占封版前的时间。** 8 天估时是顺利情况，而 10/16 之后
   只能修 bug。K 系列刚做完，测试全绿，现在动权限模型是有代价的。

3. **中介角色会让演示变长。** 现在答辩演示要切三个账号（租客/房东/管理员），
   加中介就是四个。建议演示脚本里**只保留一条中介链路**
   （委托 → 带看 → 需求摘要），不要每个功能都演。

**如果时间不够，我的建议是砍成这一版：**

> J-01（角色与资质）+ J-02（权限）+ J-04（委托）+ J-05（带看记录）
> + **J-09-a（需求摘要交接）**

理由：前四条是「中介存在」的最小闭环，缺一条链就断；
而 J-09-a 是唯一一条**在答辩上能讲出彩、且复用了已有 AI 能力**的。
佣金、免打扰、智能派单、带看纪要都可以留到之后，
少了它们中介功能依然是完整可用的。

反过来，**最不该先做的是佣金**——它看起来像核心（毕竟中介靠这个赚钱），
但钱在这个项目里本来就是假的（D-1），做出来只是一张状态机表格，
既不影响流程跑通，也没有可讲之处。
