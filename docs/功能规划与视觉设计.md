## 一、现状盘点

### 已经做完的

| 层 | 内容 |
|---|---|
| 数据表 | `users` `houses` `appointments` `favorites` `repairs` `chat_messages`（6 张） |
| 租客端 | 自然语言找房、房源列表与详情、收藏、智能预约、智能报修、个人中心 |
| 房东端 | 发布房源（接口）、上下架（接口）、确认／拒绝预约 |
| 管理员端 | 平台统计（接口） |
| 智能体 | AI-01 找房、AI-04 报修分派、AI-06 预约 |

### 明显的短板

对照真实租赁平台，我们目前的问题很集中：

1. **整条业务链在「预约看房」处断掉了。** 看完房之后的签约、交租、退租
   一个都没有——而这恰恰是租赁系统的主干。
2. **房东端几乎只有一个发布功能**，而且没有前端页面。真实平台上房东要管
   房源、看账单、处理工单、跟进租约到期。
3. **管理员端只有一个统计接口**，没有审核、没有用户管理、没有任何界面。
4. **房源没有图片。** 一个租房网站没有房屋照片，视觉上先输一半。

拿《需求分析说明书》自己列的 11 个业务模块逐条核对，
**只有 F-04 看房申请是完整的**：

| 完成度 | 模块 |
|---|---|
| ✅ 完整 | F-04 看房申请 |
| ⚠️ 部分 | F-01 房屋信息（缺编辑）· F-03 租客管理（缺资料维护）· F-08 报修（缺图片）· F-11 系统管理（缺配置） |
| ❌ 未做 | **F-05 租赁合同** · **F-06 收租信息** · **F-07 收租统计** · F-02 户主管理 · F-09 维修数据 · F-10 公告管理 |

F-05／F-06／F-07 这三个是同一条链上的，也就是上面第 1 条说的主干。

| `browsing_history` | 浏览足迹 | `user_id` `house_id` `viewed_at` |

**字段规范**（沿用现有约定，评审时能自圆其说）：
金额一律 `Numeric(10,2)`；时间点用 `DateTime` 不用 `Date`；
关联一律用外键；敏感信息展示前脱敏。

## 七、视觉设计方案

### 7.1 现状问题

当前界面能用，但离「像个真产品」还差几步：

| 问题 | 影响 |
|---|---|
| **没有任何图片** | 最致命。租房是看图决策的生意，纯文字卡片说服力极弱 |
| 首屏没有主视觉 | 打开就是一个搜索框加一排卡片，缺少「这是个租房网站」的第一印象 |
| 信息层级偏平 | 卡片上租金、户型、标签的视觉权重差不多，扫视时抓不住重点 |
| 缺少空状态与加载态 | 搜索时只有按钮文字变化，没有骨架屏，感觉卡顿 |
| 只有一种布局 | 没有列表／网格切换，没有地图视图 |

### 7.2 设计系统

**配色**——延续现有的双色编码，这个思路要保留：

```
主色（智能体/品牌）  #0F6F68  深青   智能体相关一律用它
辅色（房源/价格）    #A8452F  砖红   租金、重要数值
中性色                #16202B  墨黑   正文
                      #7A8B9C  灰    次要信息
                      #F2F4F7  底灰  页面背景
语义色  成功 #3F6B4F ｜ 警告 #8A6212 ｜ 危险 #B5342A
```

**为什么是这两个颜色**：深青代表 AI 智能体层，砖红代表房屋与租金。
翻页面时哪些是智能体的能力、哪些是传统业务一眼可分——
**答辩时这是个能讲的设计决策**，不是随便挑的。

**字体**：中文用系统默认（`PingFang SC` / `Microsoft YaHei`），
数字用 `font-variant-numeric: tabular-nums` 保证租金对齐。
标题与正文只用两级字重，不要花。

**间距**：以 4px 为基准单位，卡片内边距 16–20px，区块间距 24–32px。

### 7.3 关键页面

**① 首页主视觉**

```
┌──────────────────────────────────────────────┐
│  [大图：大连星海广场 / 城市天际线]              │
│                                              │
│      在大连，找到你的下一个家                   │
│      ┌────────────────────────────┬────────┐ │
│      │ 说一句话，比如「中山区两室…」  │ 智能找房 │ │
│      └────────────────────────────┴────────┘ │
│      101 套在租 · 6 个城区 · AI 秒懂你的需求    │
└──────────────────────────────────────────────┘
```

要点：**用大连真实地标图片**（星海广场、跨海大桥），比通用素材有辨识度；
搜索框压在图上，不要挤在图下面。

**② 房源卡片**

```
┌────────────────────────┐
│  [封面图 16:9]     ☆   │   ← 收藏浮在图上
│  ┌──────┐              │
│  │ 整租 │  ← 类型角标   │
│  └──────┘              │
├────────────────────────┤
│  中山区桂林街 两室一厅    │   ← 标题 15px 600
│  桂林街 · 11/33层        │   ← 次要 12px 灰
│                        │
│  ￥2650 /月             │   ← 砖红 22px 700
│  两室一厅 · 62㎡ · 朝东  │
│  [地铁] [电梯] [有阳台]  │
└────────────────────────┘
```

要点：图片占卡片上半部，租金是全卡最重的元素，标签用小圆角灰底。

**③ 房源详情**

左右分栏：左侧相册（大图 + 缩略图条）与描述，
右侧固定一个「租金 + 预约按钮」的卡片，滚动时跟随。

**④ 房东工作台 / 管理员看板**

数据卡片一行四个，下面接 ECharts 折线图（月度收入）与饼图（各区分布），
再下面是待办列表。**这类页面是信息设计，不是排版**：
数字要大、要能一眼扫到，异常项用语义色标出来。

### 7.4 交互细节

- **骨架屏**：搜索与加载时用灰块占位，不要空白
- **卡片悬停**：轻微上浮 2px + 阴影，已有，保持
- **空状态**：配一句引导文案和示例按钮，不要只有「暂无数据」
- **智能体思考态**：解析时逐条显示「正在理解需求 → 正在检索房源」，
  比一个转圈更能体现智能体在干活，**演示效果好**
- **移动端**：卡片单列，抽屉改成全屏，筛选器收进底部弹层

### 7.5 图片素材从哪来

房源图片是最大的缺口。三个方案：

1. **免费图库**（推荐）：Unsplash / Pexels 搜 `apartment interior`，
   下载 20–30 张放进 `server/static/houses/`，seed 时随机分配。合规、快。
2. **纯色卡片占位**：按户型生成不同色块 + 户型图标。零成本但观感一般。
3. 找同学拍几张实景——工作量大，不建议。

**建议方案 1**，并在页脚注明图片来源。

## 九、分工建议

五个人，按端切分而不是按层切分——**每人独立负责一条完整链路，
不用互相等**，也方便老师看清各自贡献：

| 人 | 负责 |
|---|---|
| A | 租客端：签约、租约、账单缴费（T-04/05/06） |
| B | 房东端：工作台、房源管理、预约处理（L-01～L-04） |
| C | 管理员端：看板、审核、用户管理（M-01～M-03） |
| D | 智能体：AI-03 客服、AI-02 合同审阅、对话记忆 |
| E | 视觉与公共组件：图片、首页主视觉、卡片改版、图表 |

**每条链路都要自己写测试**，沿用现有约定：
纯函数单测 + 接口测试，不依赖网络与大模型。
提交前跑通 `python -m unittest discover -s tests`。
