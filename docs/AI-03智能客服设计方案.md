# AI-03 智能客服问答（RAG）设计方案

> 本文只覆盖 **AI-03 智能客服** 一个功能点，是当前唯一未完成的需求项
> （见 [README](../README.md) 与 [功能规划](功能规划与视觉设计.md) 第 3 条短板）。

> 编写日期：2026-09-02 · 目标：9 月 24 日概要设计评审前定稿，10 月 16 日封版前落地

## 0. 这份方案要解决的核心矛盾

《需求分析说明书》7.3 节当初把 AI-03 搁置，理由是：

> 离线环境下要么内置一个嵌入模型（体积与首次加载成本都不小），
> 要么退化成关键词匹配（那就不是 RAG 了）。

这个判断里有一个**隐含的错误前提**：把「RAG」等同于「向量检索」。
RAG 的定义是 **检索增强生成**——约束在于「生成必须以检索到的材料为依据、
无依据必须拒答」，而**检索通道用什么算法并不在定义里**。
真正决定这个功能成败的是三件事：

1. **能不能召回正确的依据**（检索质量）
2. **没有依据时能不能闭嘴**（可答性判定 / Answerability Gate）
3. **回答里的每一句话能不能指回原文**（引用与可追溯）

第 2、3 点与向量库毫无关系，而第 1 点在**几十条 FAQ 的小语料**上，
词法检索与向量检索的差距远小于在百万级语料上的差距。

因此本方案的结论是：**AI-03 可以做，而且可以零新增依赖地做。**
详见 §3 的三个关键决策。

## 2. 调研：抄什么，不抄什么

### 2.1 开源智能客服项目

| 项目 | 值得借鉴 | 为什么不直接用 |
|---|---|---|
| [huabeitech/cs-ai-agent](https://github.com/huabeitech/cs-ai-agent)（贝壳 AI 客服） | **Answerability Gate**（可答性闸门）这个设计点——检索完先判「这些材料够不够回答」，不够就走兜底并推荐人工，而不是硬答；以及会话转工单的闭环 | Golang + Gin + Qdrant，技术栈与本项目完全不同 |
| [SR88888888/zhiwei-ecommerce-cs-agent](https://github.com/SR88888888/zhiwei-ecommerce-cs-agent) | **意图分流：事务型问题走 Function Calling 查库，知识型问题才走 RAG**；先按「型号」过滤再检索；评测走真实工具链而非 mock | 依赖 PostgreSQL + pgvector + BGE 本地模型，离线不可行 |
| [zhimaAi/chatwiki](https://github.com/zhimaAi/chatwiki) | 知识库切片与检索日志的产品形态 | 平台级产品，体量远超课设 |
| [JC0v0/Customer-Agent](https://github.com/JC0v0/Customer-Agent) | 关键词触发转人工的交互 | 无 RAG |
| [a1013177358/Intelligent_Customer_Agent_Demo](https://github.com/a1013177358/Intelligent_Customer_Agent_Demo) | 意图分类 + 对话状态跟踪 + 转人工决策的模块划分 | 无 Function Call，知识侧较弱 |

**共同结论（三个项目一致）**：成熟的客服 Agent 都不是「一个 RAG」，
而是 **意图分流 → 事务型走工具调用 / 知识型走 RAG → 可答性闸门 → 转人工兜底**
这一条链。本方案照搬这条链，因为它同时也正好落在课程「基于 AI 智能体」的题面上。

### 2.2 自有项目的实证结论（RedMansionRAG / 多跳图增强检索）

这些是另一个项目里**跑过配对显著性检验**的结论，可以直接复用，
不必在课设里重新试错（原文见该项目 `FINDINGS.md`）：

| 结论 | 对本方案的影响 |
|---|---|
| 向量检索显著优于 BM25（+0.10~0.13，p=0.001） | 承认差距存在，所以**留出可插拔的向量通道**（§3 决策二），但不作为默认路径 |
| BM25 不依赖任何外部服务，是最稳的 baseline | 默认通道用 BM25，**离线、无 Key、无网络都能跑** |
| 精排只在极小的 k 上有增益（top-2 有效、top-5 归零） | 检索取 top-8，精排后**只送 3 条**进生成，不贪多 |
| 融合词法通道能在已有基础上再获小幅提升 | 采用多路 RRF 融合而非单路 |
| 中文语料上共现建图物理性失效（平均度 73~1002） | **不引入图检索**——语料只有几十条，图结构没有意义 |
| 方法论：阈值必须在独立的调参集上标定，不能在测试集上调 | §7 把 30 题验收集与 20 题调参集**严格分开** |

> 另一条方法论教训同样适用：该项目有 5 条结论因为「把噪声当成效应」被撤回。
> 所以本方案的验收数字一律**打印分子分母**（`24/30`），不写「约 80%」。

## 3. 三个关键决策

### 决策一：默认检索通道用字符 n-gram BM25，不引入嵌入模型

中文 BM25 通常要 `jieba` 分词，但在**检索**任务上，
字符 unigram + bigram 的效果与词级分词相当，而且：

- **零依赖**：纯标准库实现，约 80 行，`agent/requirements.txt` 一行不加
- **无 OOV 问题**：「押一付三」「二房东」这类词分词器可能切错，字符 bigram 不会
- **对错别字更宽容**：客服场景用户会打「压金」「水电废」，bigram 仍有部分重合

`jieba` 作为**可选增强**：装了就用词级 + 字符级双通道，没装自动降级——
与项目里 `LLMProvider` 未配置 Key 时降级为 `NullProvider` 是同一个模式，
也与 RedMansionRAG 里 `tokenize()` 的 jieba 可选写法一致。

### 决策二：向量通道设计成可插拔 + 预计算缓存，而不是「不做」

新增 `EmbeddingProvider` 抽象（照 `LLMProvider` 的样子写），
配置了 Key 就走 API 嵌入（硅基流动 BGE / 智谱 / 通义 text-embedding，都有免费额度），
**语料侧向量一次性算好，量化后作为 JSON 提交进仓库**——语料只有几十条，
文件不到 100 KB，是数据不是模型权重，不违反「不内置模型」的原则。

于是运行模式变成三档，**必须在答辩时如实说明**：

| 模式 | 条件 | 检索 | 生成 |
|---|---|---|---|
| A 完整 | 有 LLM Key + 有嵌入 Key | 词法 + 向量 RRF 融合 | 大模型生成 + 引用 |
| B 常规 | 只有 LLM Key | 词法多路 RRF | 大模型生成 + 引用 |
| C 离线 | 都没有 | 词法多路 RRF | **抽取式**：返回最相关 FAQ 原文 |

> **C 档为什么仍然成立**：客服问答的答案本来就写在 FAQ 里，
> 抽取式回答（返回原文 + 引用）在这个场景下是可用回答，不是降级到不可用。
> 项目全部自动化测试跑在 C 档，与现有 676 条测试的口径一致。
>
> 需要诚实承认的边界：**离线时查询侧无法嵌入**，所以 A 档只在联网时成立。
> 缓存覆盖的是语料侧，不是任意用户提问。

### 决策三：先分流，再决定要不要 RAG

「我这个月账单还差多少没交」不是知识问题，是**查库问题**。
用 RAG 去答它必然编造。因此客服智能体第一步是二分类：

- **事务型** → 调后端现成接口（`/api/bills/mine`、`/api/contracts/mine`、`/api/repairs`），
  用前端带来的 token，智能体不持身份——与 AI-07 推荐的做法一致
- **知识型** → 走 RAG
- **未登录问事务型** → 引导登录，不猜

这一步同时是本功能相对于「一个 RAG demo」的主要区分度，
也正面回答评审老师大概率会问的「它跟接个大模型有什么区别」。

## 5. 知识语料与切片

### 5.1 三类来源

| 来源 | 内容 | 更新方式 | 切片粒度 |
|---|---|---|---|
| **静态 FAQ** `agent/knowledge/faq.md` | 平台规则、费用、流程、账号、安全等 **40 条以上** | 随代码提交 | 一问一答为一片 |
| **动态公告** `GET /api/notices` | 管理员发布的公告（现有 5 条） | 启动时拉取 + 每 10 分钟刷新 | 标题 + 正文按段落切，200~400 字 |
| **房源详情** `GET /api/houses/{no}` | 单套房源的配套、朝向、押付方式 | 提问带房源编号时**定向**取 | 整条为一片 |

FAQ 文件格式（人也要能直接改；管理端维护页列为 P2）：

```markdown
## 押金什么时候退？怎么退？
id: faq-deposit-refund
category: 押金
alias: 保证金退还 / 押金退款 / 押金能退吗

租约正常到期并办完退租手续后……（正文）
```

`alias` 一行是刻意加的：**客服场景里同义表述的杀伤力远大于语义相似度**，
把别名直接写进语料比指望模型泛化更可控，也更好解释。

### 5.2 语料怎么写才够 30 题验收

40 条 FAQ 按需求点名的五个主题铺开，每个主题 6~10 条：
**押金 / 水电物业费 / 看房与预约 / 报修 / 退租与续租**，
再加账号安全、合同、缴费方式、房东侧规则各若干。
公告的 5 条已经覆盖同样五个主题——**刻意重叠**，用来验证「同一问题
在 FAQ 与公告里都有依据时，引用是否合并、是否重复啰嗦」。

## 6. 检索算法

### 6.1 查询归一与扩展

1. 全角转半角、去标点、大小写归一
2. **同义词表**（约 60 组，写在 `corpus.py` 里，与 FAQ 的 `alias` 合并）：
   `押金 ↔ 保证金 ↔ 押一付三`、`水电费 ↔ 水费 ↔ 电费 ↔ 公摊`、
   `退租 ↔ 解约 ↔ 搬走 ↔ 提前走`、`维修 ↔ 报修 ↔ 坏了 ↔ 修一下`……
3. 扩展后的查询作为**独立一路**参与检索，不覆盖原查询

### 6.2 多路检索 + RRF 融合

| 路 | 索引对象 | 作用 |
|---|---|---|
| L1 | 片正文（字符 n-gram BM25） | 主通道 |
| L2 | 片标题 / FAQ 问句（独立索引） | 客服场景里「问句 vs 问句」的信号最强 |
| L3 | 同义扩展查询 × 正文 | 补召回 |
| L4（可选） | 向量余弦 | 有嵌入 Key 时启用 |

融合用 **RRF**（`score = Σ 1/(k + rank)`，`k=60`）而不是分数加权——
BM25 分数与余弦相似度量纲不同，直接加权需要标定，RRF 只用排名，稳。

### 6.3 精排

取融合后的 top-8，若大模型可用，用一次 JSON 调用让它挑出**最多 3 条**真正相关的；
不可用则直接取 top-3。依据是自有实验的结论：精排的增益集中在很小的 k 上，
再往下就归零，所以**不做全量重排，只做候选裁剪**。

## 7. 可答性闸门（Answerability Gate）

需求原文：「知识库中无依据时必须回答『暂无相关信息』，**不得编造**」，
拒答率要 ≥ 90%。这一条靠提示词是保证不了的，必须做成代码里的硬闸门。

**三个条件，任一不满足即拒答：**

| 条件 | 判据 | 拦的是什么 |
|---|---|---|
| G1 词法覆盖 | 查询实词在 top-1 片中的字符 bigram 命中率 ≥ `τ_cover` | 「今天股市怎么样」这类完全无关的问题 |
| G2 分数门槛 | top-1 的 BM25 归一化分数 ≥ `τ_score` | 「有点沾边但不够」的问题 |
| G3 模型判据（大模型可用时） | 让模型只回答 `yes/no` + 引用句，`no` 即拒答 | 「字面像但语义不对」，例如问「买房贷款」命中了「租房付款」 |

**阈值 `τ_cover` / `τ_score` 在独立的 20 题调参集上标定，
绝不用 30 题验收集调**——这是 RedMansionRAG 吃过亏的地方（把噪声当效应，撤回过 5 条结论）。
调参集与验收集分别落在 `tests/fixtures/support_tune.py` 与 `support_eval.py`。

拒答时的输出不是一句「暂无相关信息」就完，而是：

```
暂时没有查到相关规定。
你可能想问：  · 押金什么时候退   · 提前退租要付违约金吗
需要人工处理的话，我可以帮你留言给管理员 →〔转人工〕
```

「猜你想问」用同一套检索的 top-3 标题给出——**检索失败也要给出口**，
这是客服产品与检索 demo 的区别。

## 8. 生成与引用校验

生成阶段把 3 条依据编号后给模型，要求返回：

```json
{"answer": "...", "citations": ["faq-deposit-refund", "notice-3"], "refuse": false}
```

**回答产出后还要过三道校验，不通过就整条丢弃、退回抽取式回答：**

1. **引用合法性**：`citations` 里的 id 必须都在本次候选集合内（模型会编 id）
2. **数字可追溯**：回答里出现的金额、天数、比例，必须在引用材料原文里出现过
   ——与 AI-05 经营报告「不允许模型编造数据」是同一条规则
3. **长度与语气**：超过 300 字截断；不出现「根据我的知识」这类无依据措辞

前端把 `citations` 渲染成可点击的来源卡片（公告可跳到公告详情页），
**每条回答都能当场点开原文**——这是答辩时最有效的一个动作。

## 9. 转人工 / 转工单

拒答、连续两轮未解决、或用户明说「转人工」时触发：

- **优先复用现有能力**：走消息中心给管理员留一条待处理消息；
  若问题是设施故障，直接引导到已有的 AI-04 智能报修（一句话建单）
- 智能体侧只负责**判定与引导**，落库调后端现成接口

> 待与后端同学确认一件事：现有 `messages` 表有没有「用户 → 管理员」方向的
> 写入接口。若没有，**降级方案是引导用户去报修入口**，不为此改后端。

## 10. 接口设计

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/agent/support` | 独立客服问答。入参 `text` / `token` / `house_no?` |
| POST | `/agent/chat` | **已有**，把 `support` 意图从 `not_implemented` 改为真正路由 |

统一出参形状（与其他子智能体一致，前端只处理一种形状）：

```json
{
  "intent": "support",
  "status": "answered | refused | need_login | escalate",
  "ok": true,
```

## 一、最终指标

跑在**离线档**（无大模型、无向量嵌入，纯词法检索 + 抽取式回答），
命令 `python -m unittest tests.test_acceptance.TestAI03SupportAccuracy`：

## 三、被数据推翻的三个设计

这三条都是先写出来、跑了才发现不对的。**它们的共同点是：
直觉上都很合理，只有量化测试能证伪。**

### 1. 别名不能拼成一篇文档

最初把标题和所有别名拼成一个字符串建索引。结果「保证金能退吗」
命中了只有 1 条别名的「提前退租押金还退吗」，而不是写了 4 条别名、
其中一条就是「押金能退吗」的正确条目。

原因是 BM25 的 `b` 参数按文档长度惩罚词频——**别名写得越全，
这一片越长，排得越靠后**，等于惩罚认真写语料的人。
别名是并列的问法变体，不是更长的文档，正确做法是各自成篇、取最大值。

### 2. 「措辞新不新」不是「答得了答不了」的代理量

可答性闸门第二条判据最初是「查询里有多少词在语料里没出现过」，
两种算法都不成立：

- 算 bigram**太严**：54 条语料里的 bigram 组合本来就稀疏，任何新说法
  都会造出一堆没见过的组合。七条本该回答的问题被拒，
  而它们的正确答案还都排在检索第一位（Recall@3 = 7/7）。
- 只算单字**太松**：「天气」的天、「发票」的发在租房语料里都是常见字，
  负例几乎全放行，拒答率掉到 64%。

换成「**问的那个东西，在选中的材料里提没提**」才对上：
「装修能报销吗」检索到「自己找人修能报销吗」，覆盖率高达 0.74，
但「装修」在那一片里一次都没有——它答的是维修报销，不是装修。

### 3. RRF 负责召回，精排负责精度

RRF 只用排名、丢掉分数量级，这让它对量纲免疫（BM25 分数与余弦相似度
不可直接相加），但也让它丢掉置信度。实测「保证金能退吗」在标题路上
以 24.44 : 8.28 压倒性指向正确条目，到了 RRF 里只是「第 1 名 vs 第 2 名」，
被正文路一个平庸命中翻了盘。

所以两段分开：**RRF 召回**（对量纲免疫，把该看的都捞进来），
**确定性精排**（在小候选集内部把分数量级用起来）。

## 四、还没做到的

诚实记录，不粉饰：

1. **有依据正确率 80.0% 是压线过的**，4 个失败样本的正确答案都在 top-3 里
   （Recall@3 = 100%），失败全在闸门与精排。要再往上走，
   靠的是**词级分词**（引 jieba）或**向量通道**，不是继续加规则——
   叠规则的路已经试到头了，三次尝试都是按下葫芦浮起瓢。
2. **向量通道本机没验过。** 代码按 OpenAI 兼容的 `/v1/embeddings` 写好了，
   本机没有本地模型，需要队友在装了 LM Studio / Ollama 的机器上
   配 `EMBED_BASE_URL` 与 `EMBED_MODEL` 后验证。
   注意 **DeepSeek 不提供 embeddings 接口**，不能复用 `LLM_*` 的地址。
3. **大模型档（配了 DeepSeek Key）没跑过验收。** 闸门的第三条判据
   与生成式回答都只在桩替身下测过。按设计，大模型只能让拒答更严，
   所以拒答率不会低于 100%；但生成式回答的质量需要真机确认。
4. **多轮指代消解只做了规则版**（短句 + 指代词才拼接上一句），
   没有调用大模型改写。

## 五、事务型问答覆盖的 13 类数据

**客服能查到的，恰好是用户自己在页面上点得开的那些**——每一类都对应一个
已有的后端接口，一个都不新造。权限判断全部留在后端：租客问「我的房源」
会拿到 403，智能体只负责把原因翻译成人话（「这是房东端的数据」），
而不是自己判断谁能看什么。那样等于把鉴权逻辑抄了第二份，两份迟早不一致。

| 类型 | 后端接口 | 典型问法 |
|---|---|---|
| bill 账单 | `/api/bills/mine` | 我还欠多少房租 |
| contract 租约 | `/api/contracts/mine` | 我的租约什么时候到期 |
| repair 报修 | `/api/repairs` | 我的报修到哪一步了 |
| booking 预约 | `/api/appointments/mine` | 我预约的看房通过了吗 |
| favorite 收藏 | `/api/favorites` | 我收藏了哪些房子 |
| history 浏览记录 | `/api/history` | 我看过哪些房源 |
| message 站内消息 | `/api/messages` | 我有未读消息吗 |
| review 待评价 | `/api/reviews/pending` | 我有哪些租约没评价 |
| handoff 转人工工单 | `/api/support/handoffs/mine` | 我的转人工处理了吗 |
| profile 账号信息 | `/api/auth/me` | 我的账号是什么身份 |
| **house 我的房源**（房东） | `/api/landlord/houses` | 我发布的房子有几套 |
| **income 经营数据**（房东） | `/api/landlord/dashboard` | 预期收入 |
| **tenant 我的租客**（房东） | `/api/landlord/tenants` | 我的租客有谁欠费 |

加一类事务要在**三处**各加一行：`classify_ask.TOPICS`、`account.HANDLERS`、
`toolcall.TOOL_SPECS`。漏掉任何一处，用户看到的是「暂时查不了这类记录」
——一句看不出原因的话，所以有一条测试专门盯着这三张表是否同步。

### 关键词表的顺序不是随意的

`TOPICS` 先匹配到的胜出，三条排序都是实测撞出来的：

| 必须排前面 | 否则被谁抢走 | 症状 |
|---|---|---|
| `handoff` | `repair` 的「工单」 | 「我的转人工工单处理了吗」答成报修进度 |
| `review` | `contract` 的「租约」 | 「我有哪些租约没评价」答成租期到期时间 |
| `income` | `bill` 的「租金」 | 「这个月收了多少租金」答成欠费金额 |

规律一样：**含义更窄的排前面**，宽泛的业务名词垫底。

### 两条容易漏的判定

- **自明词**：「预期收入」「出租率」没有人称代词，但没人会拿这几个词
  问平台的公共规则。原先一律要求「我的」，结果这类问法被判成知识型，
  去检索 FAQ 自然什么也查不到——上线后用户反馈的「不理解」就是它。
- **问进度 ≠ 要转人工**：「我的转人工工单处理了吗」里有「转人工」三个字，
  `wants_handoff()` 先跑，于是又给用户建了一张新工单。
  必须先把「处理了吗」「到哪一步」这类进度询问词排除掉。
