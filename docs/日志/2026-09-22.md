## 上午到下午：长对话测试 @A107586

### 为什么现有测试测不到

原来的 741 条用例是单句进、单句出。跨轮的毛病有个共同点：
**每一句拿出来看都对**。「这套有电梯吗」答「有电梯」，没错；
问题在于这个「这套」跟上一句指的不是同一套房。
要抓它只能连着问，并且按前端真实的方式维护
`history` / `last_house_nos` / `pending`——自己另造一套上下文管理，
等于测了一个不存在的系统。

### 两批共 12 个剧本

第一批 A–F（57 轮）盯指代与条件累积：找房-筛选-追问-预约、
条件反复修改、连续六个「这套」、空结果之后继续对话、
租后混合话题、房东视角。

第二批 G–L（74 轮）盯此前完全没覆盖的几类：

| 剧本 | 盯什么 |
|---|---|
| G 中介带看全流程 | 不是租客也不是房东的第三种人，助手认不认 |
| H 管理员视角 | 平台侧的人问业务问题，会不会被当成租客答 |
| I 24 轮超长会话 | 第 3 轮说的条件，第 22 轮还记不记得 |
| J 话题来回横跳 | 找房→租后→报修→再跳回找房，跳回去能不能接上 |
| K 确认卡生命周期 | 卡片发出来之后插话、改主意、真的执行 |
| L 中英混输错别字 | 不是单句噪声，是一整段都这么说话 |

最终 131 轮 0 处不一致，中位 2.2s，最慢 8.5s。

### 找出来的六个

**一、长会话里的条件会被闲聊挤掉。**（`memory.replay`）

`replay` 无差别取最近 `MAX_TURNS=10` 句。I 剧本里用户第 3 轮说了
「沙河口 / 三千以内 / 两室一厅」，中间问了十几轮合同、账单、评价，
到第 22 轮说「还有更便宜的吗」时那三个条件早被挤出窗口，
重放出来是空的——系统答**「建议把租价上限从 9 元提高一些」**。

窗口本来要限的是「一个条件说出来之后还算数多久」，
而这个「多久」该按**他又提了几次条件**来数，不是按他说了几句话。
改成只有带条件的轮次才占窗口。

这个改动**没有改变任何一轮自身的语义**：被滤掉的轮次本来就是空操作
（没有重置、没有清除、解析不出条件），`apply_turn` 对它们什么也不做，
所以只改变了「谁能留在窗口里」，重放依然是纯函数、依然可重现。
100 轮历史重放实测 1.78 ms，对 2 秒一轮可以忽略。

**被否决的另一种改法**：把槽位直接存进会话状态、不再每轮重新推导。
那样确实不会丢，但会推翻 `memory.py` 立的规矩——
「记忆是推导出来的，同一串对话重放两次结果必须完全一致」。
存下来的状态一旦和历史对不上（比如用户改了前面某句），
就会出现「界面上显示的条件」和「实际用的条件」两套各自漂移，
比丢条件更难查。

**二、「更便宜」一条都不认。**（`RELATIVE_RULES`）

表里有「再便宜」「便宜点」「太贵」「有点贵」，**偏偏没有「更便宜」**。
字面上确实一个都对不上，于是预算纹丝不动，
系统把上一轮那套 2950 元的原样又端了回来。
补「更便宜 / 更贵 / 更大 / 更小」，并加用例盯住它们不互相撞
（「更贵」不能命中 cheaper 里的「太贵」）。

**三、问「还有几天」答的是日期。**（新增 `dates.py`）

「租到 2027-09-01」内容没错，但答非所问。新增 `until_text()`
把换算做掉，边界单独处理——「还有 0 天」「还有 -5 天」都是病句，
改成「就是今天」「已经过期 12 天」。租约与账单两处都用上；
逾期几天正是催缴时最该先说的一句。

**四、中介这个角色，助手一个工具都没有。**

G 剧本问「我这个月佣金多少」「我带看过几次」「我代理了哪些房源」，
三句全答不上来——**而后端这三个接口一直都在**。
补三个读工具并按角色可见。金额直接取返回体里算好的
`pending_amount` / `settled_amount`，不在客户端再求一遍和：
那会把「作废的佣金算不算」的口径抄成两份，
而这是中介照着对工资的数字。

**五、「渗水」不在紧急词表。** 同一处渗漏，写「漏水」判紧急、
写「渗水」判一般。按这张表自己定的口径（宁可宽一点）补上。

**六、`/agent/chat` 的 history 混进助手的话会被当成用户的条件。**

接口约定只放用户说过的话，前端与后端存储那条路都照做了，
但约定是口头的，端上谁都能调。混进去的后果既严重又完全看不出来：
助手说了句「2026-09 加入平台」「61 平」「平均 4.4」，
重放出来的槽位就成了「租价 9–2026 元、面积 51–70 平」。
纯字符串列表没法反推哪句是谁说的，所以不猜——改成**也接受**
`{"role","content"}` 这种带署名的条目，老调用方一个字不用改。

## 下午：本地模型的视觉头接进报修 @A107586

### 先量再做

模型自带视觉头，一直没用。**先量它到底行不行**：如果它在正常房间
照片上能看出「水管漏水」，这个功能就不能上——用户拍一张干净的厨房，
系统派个水暖工上门，比没有这个功能糟糕得多。

拿仓库里 14 张真实房源照片（标准答案是一张张看出来的，不是从文件名猜的）：

| 项 | 结果 |
|---|---|
| 房间类型（客厅/卧室/厨房/外观） | **14/14** |
| **完好房间上误报损坏** | **0/14**，加 4 张网页截图 → 0/18 |
| 厨房设施清点 | 燃气灶、微波炉、烤箱、水槽、橱柜，三张全中 |
| 图片说明 | 14 张都是能直接用的文案 |
| 单张耗时 | 中位 0.8s，最慢 1.1s |
| 显存 | +1.06 GB（9336 → 10393 MiB） |

复跑：模型带 `-Vision` 启动后 `python scripts/try_repair_photo.py 照片`。

### 接法：识图只当翻译

照片 → 一句中文 → **仍旧交给原来那套 `classify_repair`** 去定类型、
紧急程度、工种。那套有 50 个用例盯着（AI-04），
让识图另起一套判断，等于把一个测过的东西换成没测过的。

价值是实测的：「厨房有点问题」单独送进去 → 其他 / 可延后 / 综合维修工；
配上「照片显示：厨房水槽下方管接口渗水」→ 水暖 / 紧急 / 水暖工。

三条护栏：

1. **第一行只回「有」或「没有」，由这一行决定后面那句作不作数**，
   而不是去猜描述里有没有「漏」字——「没有」里面也有个「有」，
   用 `in` 判断就在这里翻车。
2. **识图失败不影响报修**，原样退回纯文字。`complete_vision` 的默认
   实现抛 `LLMUnavailable` 而不是 `NotImplementedError`：识图是后加的
   能力，测试里那些只实现了 `complete` 的假 provider 也完全合法。
3. **照片读出来的那句话摆在用户眼前**，并写进工单正文。
   拿一个用户没看过的句子去派单，师傅上门发现不是这回事时谁也说不清。

安全上，图片只收 data URI 和本站 `/static/` 路径，外链一律丢弃：
识图是**模型那一端**去取图的，放任意地址进去等于让用户指定
「服务器去访问哪里」。跟 C1 里「评价配图只收本系统上传的地址」
防的是同一件事。

### 没做的与没量的

- **正例没量过。** 14 张全是完好房间，只证明了「不会无中生有」；
  「真坏了能不能看出来」缺一批真实故障照片，到现在仍是未知数。
  留了 `scripts/try_repair_photo.py` 给拿得到照片的人。
- **图片审核这个场景不能用。** 拿 4 张网页截图当负例，
  问「这是房屋照片吗」，**3 张答「是」**。要做上传审核得换一套提法。

## 顺带量的：向量模型 CPU vs GPU

嵌入模型之前挪到了 CPU。把「效果」拆成两件事各量一遍：

**质量——没有差别。** 同一批 16 句两个后端各算一遍，
逐句余弦最小 0.999574、中位 0.999797；**同一查询下 15 个候选的
检索名次完全一致**。不是 bit 级相同（单维最大差 3.2e-3），
但排序一个都没变。

**速度——看批量。**

| 批大小 | CPU | GPU |
|---|---|---|
| 1 | 20.8 ms | 24.4 ms |
| 4 | 85.6 ms | 50.5 ms |
| 16 | 329.7 ms | 171.8 ms |
| 64 | 1330.7 ms | 637.6 ms |

本项目的负载是「一次一条查询」，这一档两边没差别；
GPU 只在建索引的批量上快一倍。**挪到 CPU 是对的**，
省下的显存正好够装视觉头。

另量到一条值得记的：**向量通道开/关，验收集上 Recall@1 与 Recall@3
都是 20/20，但单次检索 32.8 ms → 1.1 ms。**
这不能证明这一路没用，只能说**现有的 20 个用例分不出它的价值**
（词法通道已经满分）。想留着它就得先有一批词法答不好的用例。

## 晚上：换个账号登录，助手恢复的是上一个人的对话 @A107586

### 现场

退出租客、登录房东，助手面板铺出来的是租客那一段：他找过哪几套房、
预算多少、报修留的电话，连 `pending` 里那张还没点的确认卡片
（上面写着账单号和金额）都在。

后端一直是干净的——`GET /api/chat-messages` 同时按 `user_id` 过滤。
**漏的是浏览器本地那一份**：三个键都是写死的常量，一台电脑一份，
跟谁登录没有关系，而 `logout()` 清了 favorites 却没清它们。

### 改法：键里带身份，而不是「记得在退出时清一下」

新增 `web/src/storage.js`，键统一是 `基础名:用户id`，未登录记作 `anon`。

为什么不是「在 logout 里清」：**清理这种事漏一个入口就前功尽弃**，
而入口不止退出一个——令牌过期、换标签页、直接换账号登录都不走
`logout()`。键里带了身份，就算一次都不清也串不了；
顺带各自的对话各自留着，换回来能接着聊。

**只改存储还不够。** React 不会因为 `user` 变了就丢掉组件 state。
`ChatPanel` 挂 `key={identity}`，换人时整个重挂；
`useSearchHistory` 挂在 App 上、App 不会因换人卸载，
只能自己盯着身份变化重读。

`purgeLegacy()` 在启动时删掉三个旧键。**这一步是在清数据，不是清代码**：
那几个键里现在就躺着某个人的整段对话，而这台电脑后来可能已经换人用了。

## 深夜：一台电脑登录多个账号 @A107586

上一条修完，顺着往下问了一句：**那同时登录多个账号呢？**

先查，不先改。把所有可能按「浏览器 / 机器」而不是按「令牌」记事的
地方过了一遍：

| 地方 | 结论 |
|---|---|
| `_whoami_cache`（智能体） | **按令牌做键**，且只存「是不是登录 / 什么角色」 |
| `_kb` / `_TOPIC_INDEX` / `_SYNONYM_INDEX` | 语料派生，与用户无关 |
| `BrowsingHistory` | `user_id` 过滤 |
| 按 IP 记事的 | 只有登录限流、找回密码、操作日志三处，都该按 IP |

登录限流**只统计失败、成功立刻清零**，所以一台电脑接连登几个账号
不会互相牵连。没有 Cookie，令牌是无状态 HMAC，登录不吊销别人的令牌。

**服务端这一侧本来就是对的，需要的是把它盯住。**
新增 `server/tests/test_multi_account.py`（11 条）：两个房东 + 一个租客
+ 一个管理员，交替与并发地打同一批接口。其中一条特意让两个账号
用**同一个 `session_id`**——前端现在按账号分开存编号了，
但服务端不能指望这件事，编号是客户端给的。

真找出一处要改的：**401 不该把别人的登录状态一起抹掉。**
前端原先在 401 时调 `setToken('')`，它会把 `localStorage` 里那份
「下次开新标签页默认用谁」一并清掉——而那份可能是另一个账号的。
改成只清自己的，`localStorage` 里恰好是同一个令牌时才清。
浏览器里验过：本页种 `EXPIRED-TAB-A`、localStorage 种
`STILL-VALID-TAB-B`，刷新触发 401 后，前者被清、后者原样还在。

## 收尾：三份文档各说一个测试数，全是错的 @A107586

分支推上去之后回头核文档，撞见一组很难看的数字：

    docs/测试说明.md       智能体 493 + 后端 700 = 1193
    docs/技术架构说明.md    server 813 + agent 632 = 1,445
    docs/概要设计说明书.md   1,580 条

最难看的是《测试说明》里那张用例清单——**同样七行被复制粘贴了四遍**。
没人发现，因为没有人会去数一张五十行的表。

这类数字有个共同点：**改代码的人不会想起来改它，而看文档的人
没有办法发现它已经不对了。** 9-21 那天建立的规矩正是为此——
文档该生成就生成，然后用测试盯住。于是新增
`scripts/gen_test_counts.py`，与 `gen_api_list.py` 并列进
`test_design_artifacts.py`。

三个实现上的判断值得记：

1. **真的把用例装载一遍数**，不是数源码里有几个 `def test_`。
   参数化、继承、`load_tests` 都会让这两个数对不上。
2. **两个项目分别起进程数。** `agent/` 和 `server/` 下各有一个顶级包
   都叫 `app`，同一个解释器里先导入谁，后面那个就被挡住。
3. **接口数与表数从《概要设计说明书》里读，不自己再数一遍。**
   那份已经由 `gen_api_list.py` 生成且有 `--check` 盯着，
   再造一套口径，出分歧时谁也说不清该信哪个。

生成器第一版自己也错了一处：数子智能体时把 `toolbox` 算了进去，
报 11 个，而全篇别处都写着 10 个——`toolbox` 是「让模型挑哪个工具」
的选路层，挑完才轮到子智能体干活。**生成不等于正确，口径仍然要想清楚。**

### 同一批里还修了两处

**评测集漏了三个工具。** 补完中介那三个工具之后，`toolbox_eval`
还是 42 句、覆盖 28 个，而工具表已经 31 个——**评测照跑、照出一个
好看的百分比，只是那个数字跟新工具没有关系**。补三句，
并在 `test_suite_hygiene.py` 加两条覆盖率用例（删掉一句复跑，
确认它真的会红）。

**一处会变成 SyntaxError 的非法转义。** `test_upload_api.py` 里
`"/static/uploads/..\..\seed.py"`，`\.` 和 `\s` 都不是合法转义，
现在只告警、照旧当字面量，**将来的 Python 会直接报错，
整个文件都加载不了**。

## 踩的坑

### 一、测试把真正会执行的那几行整个绕开了（验证手段本身出错）

`safe_images` 的八个用例全部传了假的 `fetch`，于是 `_fetch` 里
`_PNG_MAGIC` 根本没定义都没人发现——**测试全绿，实际一调

> 桩打在哪里，哪里就没人看着。

### 二、长对话测试的脚本自己错了三次（验证手段本身出错）

- **history 里混了助手的回答**，于是"测出"了一个不存在的槽位污染 bug。
  真正的前端只回传 `role === 'user'`。
- **history 被截成最近 10 条**，而前端是全带；服务端的
  `MAX_TURNS` 才是被测对象，在客户端先截一刀等于测了个别的东西。
- **`pending` 没有回传**，于是"测出"了一个不存在的序号 bug：
  「那就第一套」之后助手追问时间，下一轮没带 pending，
  自然落回当前房源。补上之后确认卡上写的是对的编号。

三次都是先报"发现 bug"、再发现是脚本的问题。
**判据写死也算一种**：E 剧本判据找「到期/合同/天」三个字，
而回复是"DL0005 租到 2027-09-01"——内容完全正确，只是措辞不在表里。

### 三、`npm run build` 通过不代表页面能打开（环境相关）

`const identity = whoami(user)` 放在了 `user` 声明之前（166 行 vs 207 行），
暂时性死区。**构建照样通过**，页面一打开是
`ReferenceError: Cannot access 'C' before initialization`，
整页被 ErrorBoundary 接住、什么都不显示。
vite build 不跑组件，这类错只有真打开页面才看得见。

### 四、PowerShell 5.1 读无 BOM 的 UTF-8 会按本地代码页解（环境相关）

中文注释乱掉还只是难看；乱掉的中文一旦落在双引号字符串里，
就会凑出一个提前终止的引号——**整份脚本连解析都过不去**，
报的错却是几十行之外的「字符串缺少终止符」。
`start-local-llm.ps1` 改存 UTF-8 with BOM。

### 五、并发用例先红了四条，而错的是测试装置（验证手段本身出错）

`tests/base.py` 用内存 SQLite + `StaticPool`——**整个进程共用一条连接**。
单线程完全正确，可多个线程各拿一个 Session 同时读写时，
这条连接上的事务会互相打断：三个账号并发打 `/api/auth/me`，
36 次里偶尔冒出一两次 401「请先登录」。

**差一点就去"修"一个不存在的并发 bug。** 做了对照实验：
同一份压力换成文件库 + `QueuePool`（每个 Session 一条连接，和线上一样），
36/36 全部 200、身份一个都没错。

所以并发那一组自己建一个带池的库，`tearDownClass` 里还回去；
全套复跑 909 条确认没有外溢到别的用例。

> 装置和产品用的不是同一套连接策略时，**装置暴露的并发问题不算数**。

### 六、同一个输出文件被两个进程同时写

长对话测试跑了两遍没跑完就又起了一遍，两个进程写同一个
`long_chat2.json`，结果文件里是两次运行交错的内容。
后来杀干净、单跑一遍才是可信的数字。
