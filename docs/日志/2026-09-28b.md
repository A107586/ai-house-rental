## 三、踩的坑

### 1. 限流又被转发头绕过了——这次在 uvicorn 那一层

**现象**（对着 `python -m uvicorn app.main:app` 起的真服务，没设任何环境变量）：

```
同一来源连错 10 次: 401 401 401 401 401 401 401 401 429 429
带 X-Forwarded-For: 8.8.8.8 → 401      ← 又放行了
不带转发头          → 429
```

而 `test_client_ip.py` 七条全绿，其中一条正是端到端的「换个头看看还限不限」。

**根因**：uvicorn 的 `proxy_headers` **默认就是开的**，并且默认信任
127.0.0.1——只要连接来自本机，它就在请求到达应用之前拿 `X-Forwarded-For`
改写 `request.client.host`。9-21 修的 `app/netaddr.py` 在 `TRUSTED_PROXY_HOPS=0`
时读的正是 `request.client.host`，拿到的已经是被改写过的值。

**测试为什么看不见**：`TestClient` 直接调 ASGI 应用，**不经过 uvicorn 的中间件**。
这不是测试写得不好，是这一层在测试的视野之外。

**更难堪的一处**：9-21 写的部署单元里有一句注释「刻意不加 `--proxy-headers`」。
**不加等于开着**——那句话描述的是一个不存在的状态，而且我当时就是照着它
以为这件事已经处理了。

**改法**：

- 每个启动 uvicorn 的地方都显式写 `--no-proxy-headers`：
  两份 systemd 单元、`start-all.ps1`、`.claude/launch.json`；
- 新增 `server/tests/test_launch_flags.py` 盯住它：找出仓库里所有 uvicorn 启动命令，
  缺这个参数就红，有人加回 `--proxy-headers` 也红。
  **先断言「确实找到了启动命令」**——找不到就全绿，是最危险的一种绿；
- 反向验证过：临时删掉一处，测试红；还原，绿。

**线上会不会中招**：按手册的部署形态（uvicorn 只听 127.0.0.1、前面一层 nginx），
uvicorn 0.52 取的是链上**最右边**那个非受信地址，也就是 nginx 追加的真实客户端，
所以线上其实是对的。**但对的原因是巧合，不是设计**——换一个 uvicorn 版本、
换一种代理拓扑就不一定了。转发头只让一层管，这一层是应用。

### 2. 部署手册的冒烟表写错两处

- 「连错 9 次，**换个 VPN 再试**，计数不该重置」——错的。换了 VPN 就是换了一个
  真实 IP，**本来就该另算**；要验的是**伪造的转发头**不能重置计数。
- 「停掉智能体后首页状态变『未连接』」——也不对。顶栏的状态点只在**业务后端**
  连不上时出现（此前改版时有意为之），智能体停了是在用到它的地方就地提示。

两处都是照着想象写的，没对着真系统点过。已改，并把能自动化的部分换成 `smoke.py`。

### 3. 线上根本问不到智能体的健康检查

核对 nginx 配置时发现：`/agent/` 是原样转发，而智能体的健康检查在 `/health`。
所以 `https://域名/agent/health` 是 404，裸的 `/health` 又会落到前端 `index.html`
上——**返回 200 和一页 HTML**。手册里「每分钟 curl 一次两个 /health」照做的话，
监控会一直报智能体健康，其实问的是另一个东西。

改在 nginx：单独一条 `location = /agent/health` 转到智能体的 `/health`。
冒烟脚本先问 `/agent/health`，404 再退回本机直连的 `/health`，
并且**按返回 JSON 的 `status` 判，不只看状态码**。

> 起初是在智能体里加一个 `/agent/health` 别名路由。那样会改路由表，
> 进而要求重新渲染类图——而**本机只有 Node 16，mermaid-cli 12 要 Node 18**
> （报 `ReferenceError: ReadableStream is not defined`）。
> 装新版 Node 属于下载安装，没问过不做；何况这本来就是部署路由的事，放 nginx 更对位。
