## 三、三个值得记下来的判断

### 1. 智能体调后端慢了 2 秒，是 `localhost` 的锅

智能体每次调业务后端都固定花 2050 ms，而规则解析本身只要 0.03 ms。

根因：配置里写的是 `http://localhost:8080`，而后端只绑 IPv4。
**Windows 上 `localhost` 会先解析成 IPv6 的 `::1`**，连不上再回退 ——
这一次回退就是 2 秒。改成 `127.0.0.1` 之后降到 29 ms。

```
http://127.0.0.1:8080/api/houses      32ms / 5ms / 30ms
http://localhost:8080/api/houses    2037ms / 2026ms / 2038ms
```

**每一个 AI 功能之前都在白等这 2 秒。**

### 2. 验收标准写了准确率，却从没统计过

需求给 AI-01/02/04/06 定了「准确率 ≥ 85%」这类可量化标准，
但没有任何测试统计过这些比率 —— 答辩被问一句「85% 怎么算出来的」就答不上来。

补了量化基准之后**第一次跑四项都不满分**，逐条查下来全是真实的规则遗漏：

- 「全屋断电了」判成一般 —— 紧急词表只有「停电」「没电」，
  **而需求原文点名「漏水、断电、煤气必须判紧急」**，这条漏判是可能出事的
- 「明早九点」解析不出 —— 只认「明天」，不认这类合成词
- 十份样例合同全都抽不到「付款方式」—— 正则只认「按每 N 个月支付一次」，
  **那恰好是本平台自己生成的合同的写法**，拿外面的合同来审必然抽不到

修完全部达标。

### 3. 架构从「二选一」改成「融合」

原先是规则置信度够高就不调大模型，不够才调。两头都有问题：规则确定时
大模型完全不参与，可规则再全也覆盖不了所有说法；规则不确定时又把它的结论
整个丢掉，大模型得从零猜。

改为**规则始终先跑，结论作为「参考答案」写进提示词，由大模型给最终结果**。
配三条护栏：

| 护栏 | 依据 |
|---|---|
| 大模型不可用时照常工作 | 需求 N-07 |
| 硬性规则不接受覆盖 | 需求 AI-04「漏水断电煤气必须判紧急」 |
| 输出必须能校验 | 白名单 + 类型 + 枚举 |

第二条值得展开：把「必须判紧急」写进提示词只是「请你注意」，大模型可以
不照做；**写成护栏才是无论它怎么答都改回来**。反过来允许它把「一般」升成
「紧急」—— 多派一次工只是多跑一趟，与漏判的代价完全不对等。

成本上，融合意味着每次请求都调一次大模型。需求 N-08 要求 Token 消耗受控，
所以留了 `FUSION_ENABLED` 开关。

## 四、当天踩的坑

**PowerShell 脚本必须存成带 BOM 的 UTF-8。** 不带 BOM 时
Windows PowerShell 5.1 按系统 ANSI 读，中文字符串全部乱码，
连带把变量赋值也弄坏。

**测试之间共享状态会互相污染。** 两个测试文件各自在模块顶层建数据库引擎，
第二个把第一个的覆盖掉，先导入的那批用例全部报「表不存在」。
共享状态只能有一处初始化。
