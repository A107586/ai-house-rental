## 二、时间线

### 先确认「项目变化」到底是什么

git：工作区干净，`main` 与 `origin/main` 同一个提交，
磁盘上最新的文件时间停在 9-14 01:28。**没有代码变化。**
三个服务（8080/8000/5173）都不在监听——机器重启过，不是代码的事。

两套测试跑一遍：server 870 条全绿（627 秒）；agent **红一条**。

### 定位：是功能坏了，还是用例过期了

那条用例把预约钉在 2026-09-12 / 09-20 / 09-21，
句子说「取消 9 月 20 号那个看房」，期望筛到 09-20 那一条。

直接问解析器：

| 句子 | 今天（9-21）解析成 |
|---|---|
| 9 月 20 号 | **2027-09-20** |
| 9 月 21 号 | 2026-09-21 |
| 9 月 25 号 | 2026-09-25 |

它按的是「这个日子已经过去，那说的是下一次」——这条规则本身有单元测试，
写得明明白白（`test_booking.py`：「说『3月5号』时指的是下一个 3 月 5 号」）。

于是 `_narrow_by_time` 拿 2027-09-20 去筛，一条都筛不到，按设计**退回全部候选**
（宁可多问一句，也不能悄悄缩到错误的那一条上），返回 `need_slot`。

**每一步都是对的。错的是用例把日期写死了。**

### 修：改用例，不改功能

预约和句子都从今天推算，offset 限在一年以内——
只有在这个范围里，「X 月 Y 号」才会被还原回同一天。

这个前提不靠推理，靠量：从 2026-01-01 起连续四年、每一天、四个 offset
（2/9/30/45 天），共 **5856 次**，没有一次还原不回同一天。闰日、跨年都在里面。

### 补：`scripts/run_at_dates.py`

思路很简单——**把「今天」挪到别的日子，再跑一遍全套**。
先照常 discover，然后遍历 `sys.modules`，只在本仓库的模块里，
把引用到 `date` / `datetime` / datetime 模块的名字换成「今天 = 指定那天」的版本；
每个日子开一个子进程（同一进程里挪第二次无效，模块已经导入过了）。

**是平移，不是冻结**：`now()` 返回「真实此刻 + 固定偏移」，时间照常在走。
为什么不能冻死，见下面第四条。

挑的十个日子：七个星期几各一次，加月末、年末、闰日 2-29、闰年次年 2-28。

## 三、这个脚本连着给了四次假结果

**本来是拿它抓 bug 的，结果它自己先造了四个。** 逐条记下来，
因为四次的形状都不一样。

### 第一次：全局换掉两个类 → SQLAlchemy 不认自己算出来的日期

第一版在导入之前把 `datetime.date` / `datetime.datetime` 整个换掉，
拿 server 的 870 条一跑，**红了 15 条**，差点当成「服务端也有日期腐烂」报出去。

    sqlalchemy.exc.StatementError: (builtins.TypeError)
    SQLite DateTime type only accepts Python datetime and date objects

根因：SQLAlchemy 的 SQLite 方言在**调用时**才取 `datetime.datetime` 做
`isinstance`，取到的正是被换掉的子类；而 CPython 的 `datetime + timedelta`
**返回基类、不返回子类**——应用里算出来的日期于是全都不被认。

**红的 15 条全是脚本造的，和项目无关。**

### 第二次：给子类加元类放宽 isinstance → pydantic 直接导不进来

    TypeError: metaclass conflict: the metaclass of a derived class
    must be a (non-strict) subclass of the metaclasses of all its bases

pydantic 要拿 `date` 当基类去建校验器类，撞上自定义元类，
`app/main.py` 整个导不进来，两个测试模块直接加载失败。

这两次的教训是同一条：**三方库有权假定 `datetime.datetime` 就是那个类。**
要拨钟，就只在自己的代码里拨。

### 第三次：脚本把自己也当成项目模块，于是谁都没换到

改成「只换本仓库的模块」之后，十个日子**全绿**。看着很好，
但顺手看了一眼替换计数，只有 **3**——一个 111 个模块的工程，
怎么可能只有 3 个地方引用日期。

一查，换掉的那 3 个是：

    __main__._datetime
    __main__._REAL_DATE
    __main__._REAL_DATETIME

**脚本自己就放在仓库里，跑起来叫 `__main__`。** 它先把自己这三个名字
换掉，之后循环里 `value is _REAL_DATE` 的右边已经是新类，
于是**项目模块一个都没换到**——十个日子全绿，因为**根本没拨钟**。

四次里这一次最危险：别的几次是红的，会逼人去看；
**这一次是绿的，不数一眼替换计数就过去了。**

### 第四次：把时间冻死 → 「时间会走」的功能全塌

改对之后拿 server 试，**对照跑（挪到今天，等于不挪）就红了 5 条**：
登出全部设备、改密码、降权之后旧令牌该失效，合同时间线该记下结束时刻。

道理很直白：**发令牌和吊销令牌之间本来是有时间差的**，
把钟焊死之后两个时刻一模一样，「晚于签发时间」的判断就不成立了。
这不是 bug，是我把时间焊住了。改成**平移**——整条时间轴挪，时刻照常走。

### 顺带量清楚了一件事：这个脚本扫不了服务端

平移版再跑 server，对照跑过了，两个未来日期上各红 8 条。
**这 8 条还是脚本造的**，因为服务端有三处钟不在同一条轴上：

- `models.py` 里 `default=datetime.now`——这个引用在**定义表类的时候**
  就绑到了真的 `datetime` 上，换模块级的名字换不到它；
- `auth.py` 的令牌用 `time.time()` 发 `iat` / `exp`，压根不走 datetime；
- 有些用例在**函数体里**才 `from datetime import datetime`，取的是真的那个。

于是「应用以为现在是五个月后，数据库盖的还是今天的戳」，
工单刚建出来就被算成超时、令牌刚发就被算成过期。

**所以脚本只保留 agent 这一档，并在文件头写明为什么。**
要真扫服务端，得先让应用的「现在」从一个地方来（比如 `app.clock.now()`），
而不是散落在 `datetime.now` / `time.time()` / 列默认值里——
那是一次改动，不是一个脚本能绕过去的。
**一个会报假红的工具，比没有工具更糟。**

### 现在怎么防

1. **排掉脚本自己**，并且比较用的真类先取到局部变量里，换不掉。
2. **换完当场验**：逐个问「今天几号」，答不上那天就停；
   再反扫一遍，项目模块里还能找到真 `datetime` 就算漏网。
3. **每次扫描先拿今天做对照跑**：挪到今天还红，说明红的不是日期，
   是脚本或者代码——直接停下，不往下扫，免得又去「修」一批没坏的用例。
   （第四次就是被这一条拦下来的。）
4. **端到端验一次**：临时塞一条「断言今天是 2026-09-21」的用例，
   挪到今天绿、挪到 2027-02-27 红，而且红的正是它。验完删掉。
