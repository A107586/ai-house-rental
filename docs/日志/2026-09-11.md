## 四、踩的坑

### 一、我警告过的那个错，我自己犯了，而且测试是绿的

`runner._filters_from` 把工具参数翻译成筛选条件。我在这个函数上面
写了一段注释：

> **键名对不上是这类翻译层最常见的错**，而且不会报错——
> 传一个 `rent_max` 进去，`apply_filters` 直接忽略它，
> 用户得到的是「全部房源」，看起来完全正常。

然后我写的是后端接口的键名（`rent_price_max`），而系统内部用的是
拼音键（`zujia_max`）。实测：

```
搜索：10 套 / 共 95 套          ← 应该是 61 套
为你找到 95 套符合条件的房源，租价 950–4650 元    ← 上限 3000 呢
route  = {"tool": "search_houses", "reason": "工具选择：search_houses（把握 100%）"}
context = {"rent_price_max": 3000}               ← 条件明明解析出来了
```

**每一处日志都显示一切正常**，只有结果是错的。

更该记的是**单元测试为什么没拦住**：我给它写的断言用的也是后端键名。
两边一起错，自然对得上。

修法不只是改键名，还改了测试的写法——断言**直接引用被调用方的键表**
（`search_properties._PASS_THROUGH` / `_RANGE_MAP`），再加一条端到端
断言：走完 `build_params`，后端参数里必须真的出现 `rent_price_max=3000`。

> 教训：**翻译层的测试不能拿「我以为的名字」去断言**，
> 那测的只是「我和我自己想的一样」。

### 三、`set` 让同一个问题两次跑出不同答案

上面那个「失败数每次不一样」，环境只解释了一半。另一半是真 bug：

```python
tokens = set(tokenize(query))
...
return max(candidates, key=lambda t: idf.get(t, unseen))
```

IDF 打平时 `max` 取哪一个，**取决于本次运行的字符串哈希种子**。

测试层面的表现是时红时绿；**线上的表现是同一个用户问同一句话，
今天能答、明天拒答，而谁也复现不出来**——可答性闸门就挂在这个词上。

改成 `list(dict.fromkeys(...))` 保序去重，并列时取句子里先出现的那个。
这个选择本身是任意的，但它是稳定的，而且和句子有关系，比按哈希取讲得通。

### 四、「报修平均 −24 小时处理完」

问「这个房东靠谱吗」，答里有这么一句。根因在种子数据：

```python
finished_at=datetime.now() - timedelta(days=repair_index + 1)
```

而工单的 `created_at` 默认是 `now`——**完成时间比报修时间还早**。

三处一起改：

- `seed.py` 改成 `repair.created_at + timedelta(hours=after_hours)`。
  **有先后关系的两个时间，后一个必须从前一个推出来**，
  各自随手取值是最容易埋这种反常识记录的写法
- 接口侧丢弃负数（不是取绝对值——取绝对值等于把坏数据当好数据用）；
  全是坏数据时返回 None，那一栏干脆不显示
- 已有库里那三条按新规则改正

### 五、进不去的 `#/work` 会让首页大图整块消失

未登录打开 `#/work`：整页工作台的守卫不通过，落到常规渲染；
但 `bg.name` 仍是 `'work'`，而首屏大图是 `bg.name === 'home'` 才渲染的。

**结果是大图整块不见，页面其余部分照常**，看着像加载了一半。
退出登录、或者把工作台链接发给一个租客账号，都会撞上。

两处都补：守卫不通过时把地址栏退回首页；`bg` 只记 `home` / `list`
这两种「有背景内容」的路由，其余一律当首页——不这么兜的话，
一个拼错的 hash（`#/wrok`）也会让大图消失，而排查时完全看不出
是路由的问题。
