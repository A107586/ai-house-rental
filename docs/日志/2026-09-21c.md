## 一、限流被一个请求头绕过

### 现象

限流按 IP 计数，连错 8 次锁 5 分钟。实测：

```
同一个伪造 IP 连打 10 次: [401, 401, 401, 401, 401, 401, 401, 401, 429, 429]
换成 8.8.8.8: 401      ← 又放行了
换成 7.7.7.7: 401      ← 又放行了
```

**撞库脚本每次换个头就行**，限流等于不存在。

### 根因

IP 取的是 `X-Forwarded-For` 的**第一段**：

```python
forwarded = request.headers.get("x-forwarded-for")
if forwarded:
    return forwarded.split(",")[0].strip()[:45]
```

那条头是**从左往右累加**的链，最左边是「最初的客户端自己声称的地址」。
谁都可以随手写一个。

更糟的是 nginx 的标准写法恰恰会把它原样带上：

```
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
# 展开 = "$http_x_forwarded_for, $remote_addr"
#          ↑ 客户端发来的，可以是任何值   ↑ nginx 亲眼看见的
```

所以**取第一段 = 取攻击者自己填的那个值**，加了反向代理也一样。

### 同一份代码有两份

`ratelimit.py` 和 `oplog.py` 各写了一遍一模一样的函数，于是一起错。
第二处的后果是：**操作日志（M-07）里「谁在哪个 IP 上做了什么」也可以伪造**，
而那一栏存在的全部意义就是事后追溯。

### 改法

`app/netaddr.py` 一处实现，两边共用：

- 默认**不信任**转发头，用 TCP 对端地址；
- 部署在代理后面时设 `TRUSTED_PROXY_HOPS=n`，**从右往左数第 n 段**。

**从右边数是关键。** 左边可以无限伪造，右边由各层代理逐跳追加——
攻击者塞进来的内容只会把自己挤得更左。

复测：换头不再重置计数（429 保持）。7 条测试盯住这件事，
其中一条是端到端的「换一个头看看还限不限」。

## 二、带着开发默认密钥上公网

两个密钥有「不设就用默认值」的兜底，方便本地开发：

```
AUTH_SECRET         = "dev-only-secret-change-me"
PAYMENT_SIGN_SECRET = "rental-pay-dev-secret"
```

**但这份代码在 GitHub 上是公开的。** 后果不是「不太安全」：

- 拿 `AUTH_SECRET` 可以**自己签一个管理员令牌**，不需要密码；
- 拿 `PAYMENT_SIGN_SECRET` 可以**伪造一份支付回调**，把任意账单改成已付
  （那个接口按设计就没有登录态，唯一的门是签名）。

原先的防线是 `/health` 里返回一句 `auth_secret_is_default: true`。
两个问题：**警告会被滚上去**；而且它顺带把「这台机器用的是公开默认密钥」
告诉了每一个访问者。

改成 `app/prodcheck.py`：`APP_ENV=production` 时逐项检查，
不合格**直接拒绝启动**，并一次把问题列全（一次报一条的话，
上线的人得改一条、重启一次、再看下一条，五项配置能折腾五轮）。

开发环境一行配置都不用写——检查再有道理，也不该让组员拉下代码跑不起来。

## 三、前端在 https 站点上会直接废掉

生产模式下智能体地址是写死的：

```js
const AGENT_BASE = isDev ? '' : `${location.protocol}//${location.hostname}:8000`
```

放到 https 站点上踩两个坑：

1. **混合内容**：https 页面发 http 请求被浏览器拦掉，
   控制台报 Mixed Content，而**界面上只表现为「智能体没反应」**；
2. 8000 得对公网开着，而**智能体服务本来就不该暴露**——
   它自己没有登录态，鉴权全在业务后端，它只是转发用户令牌。
   把它摆在公网上，等于把一个按次计费的接口摆在外面。

改成：https 页面一律走同源 `/agent`（由 nginx 转发），
需要时用 `VITE_AGENT_BASE` 覆盖。构建产物里确认过这段判断进去了。

## 四、交付出去的东西

| 文件 | 内容 |
|---|---|
| `docs/上线部署手册.md` | 从备案、个人信息、「钱是假的」三条前提开始，到冒烟清单与回滚 |
| `deploy/rental.env.example` | 生产环境变量，逐项写明「为什么必须改」 |
| `deploy/nginx-rental.conf` | TLS、按接口分桶限流、智能体长超时与关缓冲、静态直发 |
| `deploy/rental-api.service` / `-agent.service` | 只监听回环、**刻意不加 `--proxy-headers`** |
| `scripts/preflight_prod.py` | 发布前预演，九项检查 |

几处值得单独记的判断：

- **nginx 给 `/agent/` 单独开一个限流桶**（每 IP 1r/s）。它后面接着按次
  计费的大模型，而应用内的熔断只防上游故障，不防有人故意刷。
- **`proxy_read_timeout` 给到 120 秒**：线上实测中位 9.1 秒、p95 28 秒，
  默认 60 秒会把慢的那一批截断，表现同样是「助手没反应」。
- **systemd 里不加 `--proxy-headers`**：uvicorn 那个开关会拿
  `X-Forwarded-For` 的第一段去改写 `request.client.host`——正是这次修掉的
  那个错法。转发头由应用按 `TRUSTED_PROXY_HOPS` 自己处理，
  两套一起上只会让「到底信哪个」说不清。
- **证书与 nginx 配置的顺序不能反**：正式配置里写着证书路径，
  而证书在签出来之前不存在，直接套用会让 `nginx -t` 失败、nginx 起不来，
  接着 certbot 也没法通过 80 端口验证，**卡成一个环**。
  手册里给了先上临时 80 配置的走法。

也记下来，免得下次重复查：

## 六、留给上线那天的

手册第九节列了七条「上线后仍然存在的不足」，其中三条最值得先处理：

1. **应用内限流是进程内计数**，4 个 worker 等于阈值放大 4 倍
   （现在靠 nginx 再限一道兜着，根治要换 Redis）；
2. **找回密码没有邮件/短信通道**，重置码得管理员在后台发；
3. **上传存在本地磁盘**，单机没问题，多机要换对象存储。

另外，**个人信息那一条是会影响页面文案的**：一旦面向真实用户开放并收集
姓名、手机号、身份证，《个人信息保护法》的要求就都适用了。
手册里给了三个方案，推荐的是「只放演示数据 + 关闭实名录入 +
首页标注教学演示」。
