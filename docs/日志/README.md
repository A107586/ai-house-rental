## 写法约定

### 总原则

**提交信息记录「做了什么」，日志记录「为什么这么做」。**
两者重复就等于日志没写。半个月后回头看，
「为什么押金没收到就不生成退款记录」比「修改了 `end_contract`」有用得多。

宁可长，不要略。**写日志的十分钟，省的是别人（和一周后的自己）
重新读代码的两小时。**

---

### 每篇必须有的六块

#### 1. 表头

| 项 | 内容 |
|---|---|
| 提交 | N 条（`起始哈希` HH:MM → `结束哈希` HH:MM） |
| 改动 | X 个文件，+Y / −Z 行 |
| 结果 | 一句话说清今天推进到哪 |
| 测试 | 起始条数 → 结束条数，是否全绿 |
| 参与 | 当天有提交的人，用 GitHub 用户名，按提交数排 |

数字从 git 取，不要估；参与者也从 git 取，不要凭印象：

```bash
git log --since="今天 00:00" --format="%h|%an|%ad|%s" --date=format:"%H:%M"
git log --since="今天 00:00" --format="%an" | sort | uniq -c | sort -rn
git diff --shortstat <当天第一条>~1 HEAD
```

#### 2. 主线

**一段话说清今天在解决什么问题。** 不是流水账的开头，
而是「为什么今天做的是这些事、不是别的事」。

#### 3. 时间线

按时段分块，每块写清楚四件事：

- **谁做的**——小标题末尾挂上 GitHub 用户名，见下面「署名约定」
- **做了什么**——具体到功能或模块，不是「优化了一下」
- **为什么这么做**——当时的判断依据
- **怎么验证的**——跑了什么、看到什么

**被否决的方案也要写。** 比如「预约并发本来想加唯一约束，
但那个约束既太严（取消的预约会永久占住时段）又太松（管不了一小时的
重叠判断），所以改用行级锁」——**这段推理比最终结论更有价值**，
它能防止以后有人再提一次同样的方案。

#### 4. 可量化的结果

改动前后各是多少，以及**怎么复跑**：

```
| 指标 | 前 | 后 |
|---|---|---|
| 房源列表 SQL（50 条数据） | 109 条 | 5 条 |

复跑：python scripts/bench.py（需先启动后端）
```

**不写「快了很多」「明显改善」。** 没测过就写「未测量」，
那也是有效信息。

#### 5. 踩的坑

**这一节最容易被略掉，也最值钱。** 每个坑写清楚：

- 现象是什么（贴报错原文或实测输出，不要转述）
- 根因是什么
- 怎么发现的

三类必须记：

| 类型 | 为什么重要 |
|---|---|
| **验证手段本身出错** | 会让人去修根本不存在的问题 |
| **文档与实现不一致** | 后来的人会照着错的文档做 |
| **环境相关** | 换台机器就复现不了，最难查 |

举例：`localhost` 在 Windows 上先解析成 IPv6 导致每次请求白等 2 秒——
这种坑不记下来，下次换个模块还会再踩一遍。

#### 6. 留给明天的

**具体到可执行**，不写「继续优化」：

- ✅ 「在另一台干净电脑上复测安装流程」
- ❌ 「继续完善」

卡住的事也写在这里，写清楚卡在哪、试过什么。

### 署名约定

**每段工作都要写清楚是谁做的，一律用 GitHub 用户名**，不用中文名、
不用昵称、不用「我」。理由有三条：

1. **对得上 git。** 日志里写 `@A107586`，`git log --author=A107586`
   就能查到对应的提交，两边可以互相印证。
2. **答辩要说清分工。** 「谁做了哪部分」被问到时，有日志可以直接指，
   不用现场回忆。
3. **出问题知道找谁。** 一个月后看到某处奇怪的实现，能直接找到当时写的人问
   「当时为什么这么写」——这是署名最实际的用途。

写法：

| 位置 | 写法 |
|---|---|
| 表头 | `\| 参与 \| @A107586（26）、@little-rain-666（2） \|` |
| 时间线小标题 | `### 14:17–15:59 · 合同档案页与 B 档五项 · @A107586` |
| 段落里点名 | 「支付流程改造由 **@little-rain-666** 完成」 |
| 「对其他人的影响」表 | 影响到具体某人时直接 `@` 他 |

**三条细则：**

**一、协作完成的写两个人，并写清楚各做了哪半边。**
写 `@A 与 @B` 而不说分界，等于没署名。
例：「接口 @A107586，前端页面 @little-rain-666」。

**二、别人的工作要写在日志里，不能只写自己的。**
组员并行做的部分，即使自己没参与，也要写进当天的时间线并署上他的名字 ——
日志是全组的进度记录，不是个人周报。

**三、补写的日志按 git 作者署名，不要替人认领。**
事后补写时，`git log` 里作者是谁就署谁。分不清的地方写「作者不明确」，
不要猜。

> 当前三位贡献者：`A107586`、`little-rain-666`、`yangyiwu123`。
> 用 `git log --format='%an' | sort -u` 可以查全。

### 四条硬要求

**一、贴原文，不要转述。** 报错、实测输出、执行计划、命令，
一律原样贴。转述过的信息没法用来搜索，也没法验证。

    押金账单已支付数: 0  ← 一次都没交
    生成的退款记录: 1 条

比「发现退款逻辑有问题」有用一百倍。

**二、写清楚对别人的影响。** 加了字段要说明组员是否需要重新 seed；
改了公共文件要说明谁的分支可能冲突；改了接口返回结构要说明前端哪里要跟着改。
**这一条是日志在协作里的主要价值。**

**三、不写「基本完成」「差不多了」。** 要么写清楚还差哪几项，
要么写完成。含糊的进度在协作里等于没有信息。

**四、补写的日志要标注。** 事后按 git 补写的，开头注明数据来源，
并说明哪部分是还原不了的——把「记录」和「回忆」分清楚。
