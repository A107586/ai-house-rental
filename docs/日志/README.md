## 写法约定

**一、写清楚「为什么」，不只是「做了什么」。**
提交信息已经记录了做了什么。日志的价值在于记下当时的判断依据 ——
半个月后回头看，「为什么押金没收到就不生成退款记录」比
「修改了 end_contract」有用得多。

**二、踩到的坑单独列出来。** 尤其是**验证手段本身出错**、
**文档与实现不一致**这两类 —— 它们最容易重复发生，也最难从代码里看出来。

**三、数字要能复跑。** 写「快了 70 倍」就要给出压测命令；
写「测试全绿」就要给出具体条数。

**四、不写「基本完成」「差不多了」。** 要么写清楚还差哪几项，
要么写完成。含糊的进度描述在协作里等于没有信息。
