### 08:39 / 08:55 · K-10 智能体提速，以及它的代价 · @A107586

融合架构下**每一次请求都要等一趟大模型往返**，哪怕规则已经百分之百确定。
用户问「有没有两室的」，规则 5 毫秒能答，却要为此多付一次网络往返。

两个改动，性质完全不同：

1. **`LLM_TIMEOUT` 30 秒 → 8 秒**，无条件改。等三十秒的助手等于没有助手。
2. **`FUSION_SKIP_WHEN_CONFIDENT` 短路开关**：08:39 加进来时**默认关闭**，
   08:55 团队决定改成**默认开启**。

第二条的代价必须记下来，别只记住它变快了：

> **置信度高只说明规则「认得出」，不等于它「认得对」。**
> 开着短路，「规则认得出但认错了、本可由大模型纠正」的那类查询，从此不会被纠正。
> 觉得漏判变多时，**先调高 `RULE_CONFIDENCE_THRESHOLD`**（让「多确定才算确定」
> 更严），而不是整个关掉开关。

**测试的改法值得单独说**，因为它不是把断言改成新值就完事。默认值一翻转，
`test_fusion.py` 与 `test_trajectory.py` 里 7 条用例变红。它们测的是
**融合机制本身**——规则结论有没有进提示词、护栏挡不挡得住幻觉、
大模型输出不可用时退不退得回去——必须让大模型真的被调用一次，
否则测的就是别的东西。所以给这两个测试类加了 `_FusionAlwaysOn`，
**显式把开关钉死为关闭**。

> 测机制的测试，不该跟着一个会变的产品默认值飘。
> 这类测试要显式声明自己依赖的前提，而不是继承默认配置。

## 五、踩的坑

### 1. 同一个仓库有两个会话在并行写 🔴 协作

这是今天最值钱的一条。19:27 左右，日志线执行 `git pull origin main`
想同步最新代码，接连出了三个问题：

| # | 问题 | 后果 |
|---|---|---|
| 1 | 以为在 `main`，实际在 `feat/agent-broker` | 生成了一条多余的合并提交 `8ef1828` |
| 2 | 说「`git reset --hard` 不影响未提交改动」 | **说法是错的**，它会清掉工作区 |
| 3 | `git stash` 备份 | 差点把另一条线正在写的 `web/src/api.js` 带走 |

关键在于时间差：

```
19:27  日志线：git pull → 产生合并提交 8ef1828
19:29  中介线：把工作区那 447 行提交成 a591760   ← 两分钟后
19:30  日志线：git diff --stat 只剩 47 行，且是别人的文件
```

**要撤的那条合并，已经被别人的新提交压在下面了。** 这时候 reset 不再是
「回退一步」，而是重写一条正在被使用的历史。

**处理结论：不撤，留着。** 那条合并没有引入任何代码改动，只是把 origin/main
已有内容并进来，坏处仅仅是提交历史里多一行噪音。
**一条无害的合并提交，远好过重写别人正在往上叠加的历史。**
stash 已原样 pop 回去，工作区恢复成动手之前的样子。

**以后在这个仓库动 git 的规矩：**

- 先跑 `git status -sb` 和 `git log --format='%h %ad %an %s' --date=format:'%H:%M' -5`，
  确认分支、确认工作区的改动是不是自己的
- 工作区有不是自己改的内容时，**不用** `stash` / `reset --hard` / `checkout .`
- 要撤的提交如果已经不在分支顶端，**默认不撤，先问**
- 提交只提交自己动过的文件，**不用 `git add -A`**

### 2. 提交时间与实际时间对不上 🟠 记录

日志规范那条提交 `29afe4a` 是今天写的，但 git 里的日期是
**09-03 18:19**。本篇按 git 日期归到 9-03，没有按体感归到今天。

**约定：日志一律以 `git log` 的日期为准。** 体感时间不可复核，git 日期可以。
两者不一致时，在日志里注明，不要挑一个顺眼的写。

### 3. 端口已被占用，说明服务本来就在跑 🟡 环境

```
ERROR: [Errno 10048] error while attempting to bind on address ('127.0.0.1', 8080)
```

第一反应是「启动失败」，实际是**已经有一个实例在跑**。
这种情况下真正该做的不是反复重启，而是**去确认在跑的那个是不是最新版**
（见第四节的包名比对）。
