### 16:34–17:14 · 蓝色现代简约改版 · @A107586

**做了什么。** 新建 `web/src/theme.css`（约 1,900 行），在 `main.jsx` 里
排在 `styles.css` 之后加载；新建 `HeroBanner.jsx` 做首页三图轮播。

**为什么另开一个文件而不是改 `styles.css`。** `styles.css` 是四天里
一层层长出来的，2,700 多行，改动它意味着每改一处都要确认没碰坏别的页面。
`theme.css` 只做**覆盖**：全部靠层叠优先级压在原样式之上，
出问题时整个文件注释掉就回到改版前——**一个能一键退回的改版，
和一个改坏了要逐行回滚的改版，是两种风险等级。**

**轮播的三处细节：**

- 单一可取消定时器，不是每次渲染新建一个
- 鼠标悬停、键盘聚焦、滚出视口、标签页隐藏，四种情况都暂停
- `prefers-reduced-motion: reduce` 时直接不自动播

第三条不是可选项。首页最大的那块东西自己动起来，对前庭功能敏感的人
是实打实的不适。

**验证。** 浏览器实测三张图轮转、悬停停下、点暂停按钮停下。

A 组是列表页（9 项），B 组是检索条件区（4 项）。挑两项说：

**A6 是数据正确性 bug，不是样式问题。**
现象：从「优选好房」进列表页，改一下排序方式，结果变成了全部房源。
根因在 `FilterBar.jsx` 的 `apply()`——它只把自己认识的字段回传上去，
`min_rating`、`published_days` 这两个是入口带进来的，不在它的字段表里，
于是切换排序时被悄悄丢掉了。**页签名字还写着「优选好房」，
内容已经是「全部房源按评分排」。**

修法是加一张 `CARRY_KEYS` 白名单，把入口条件原样带过去：

```js
const CARRY_KEYS = ['published_days', 'min_rating', 'keyword', 'features']
```

下面的筛选条件」，下面是一排可删的条件胶囊。两者说的是同一件事，
一个用文字复述、一个可操作。**同一屏把同一件事说两遍，
用户还得判断哪个才算数。** 留了可操作的那个。

一个既出租又租房的账号，「我租的房」和「我出租的房」并排躺着，

加了 `side=tenant|landlord`，由**发起请求的那一屏**说清楚要哪一半。

「系统配置」和「房源审核」看着一样重；默认第一屏是数据看板。
**后台是干活的地方，不是仪表盘。** 改成三组——审核与治理 / 运营与数据 /
系统，默认落在待审队列，上面加一条待办条（`FocusBar`）。

待办条只放审核类的几项，工单没放进去。工单也有人等，

**H1 智能体思考动效。** 转圈弧线 + 随步骤上滚的短语

这里有个诚实性问题值得记：服务端不是流式的，前端在拿到回复之前
**不可能知道它此刻具体在做什么**。所以短语只写流程里确实存在、
且顺序固定的阶段。写成「正在浏览第 3 套房源」那种具体到对象的句子
就成了编造——**编出来的进度比没有进度更糟**，
它让用户以为系统知道一些它并不知道的事。走到最后一句就停住不循环：
真慢下来时反复轮播只会让人以为卡在死循环里。

## 四、踩的坑

### 一、`stats["in_progress"]` —— 键名是猜的，没去看返回值

现象：

```
File "C:\Competition1\rental\server\app\routers\agent.py", line 935,
    in agent_directory
KeyError: 'in_progress'
```

`GET /api/agents/directory` 一直 500，中介名录整个打不开。

根因：写 `agent_directory` 时直接用了 `stats["in_progress"]`，
以为 `agent_stats()` 会返回这个键。它实际返回的是：

```
active_delegations / recent_viewings / recent_days / deal_total /
month_deals / conversion / no_show / praise /
commission_pending / commission_settled
```

**根本没有 `in_progress`。** 同一个函数今天还踩了另外几处同类的：
字段叫 `service_districts` 不是 `districts`，`_score_agent(stats)`
只收一个参数不收两个，`leasing.notify` 不是裸 `notify`。

怎么发现的：跑接口报 500，翻 traceback 定位到行号，
然后**去读 `agent_stats()` 的 return 语句**——这一步本来应该在写之前做。

教训不是「要小心」，是**调别人写的函数之前先看一眼它的返回值，
比事后读 traceback 便宜**。

### 二、白屏：`useEffect` 放在了 `const [user]` 声明之前

现象（生产构建里被压缩成一个字母，看不出是什么）：

```
ReferenceError: Cannot access 'F' before initialization
    at Gm (index-c228c5b4.js:40:100948)
```

整个首页白屏，只剩一个「页面出错了」的兜底框。

怎么定位的：压缩后的 `F` 什么信息都没有，于是重新跑了一次不压缩的构建：

```
npx vite build --mode development --minify false --outDir dist-dbg
```

替换 `dist` 之后错误变成：

```
ReferenceError: Cannot access 'user' before initialization
    at App (index-24b48828.js:9666:40)
```

再去编译产物里找 `const [user, setUser]` 的行号，发现它在 9704 行，
而引用它的那个 `useEffect` 在 9696 行——**引用比声明早了 8 行。**

根因：上一轮做 F3/F4（经纪人、管理员登录后直接进后台）时，
那个 `useEffect` 被插在了 `const [user, setUser] = useState(null)` 上面。
`const` 有暂时性死区，读到就抛。

**这个坑上一轮就埋下了，今天才炸**——上一轮改完只跑了 `npm run build`
（构建当然过，这是运行期错误），没有真的把页面打开看一眼。
**「编译通过」和「打开是好的」之间隔着一整个运行时。**

顺带记一个可复用的手段：**生产构建的报错看不懂时，
用 `--minify false` 重新构建一次**，比对着 sourcemap 猜快得多。

### 三、自己上一轮留了个半成品：规则写好了，没有地方能批

做 D1 的时候在前端全局搜 `role-request`，**一条结果都没有。**

后端该有的都有：`RoleRequest` 模型、迁移 `0013` 的待审队列索引、
`GET /api/admin/role-requests`、`POST /api/admin/role-requests/{id}`，
连「驳回必须填理由」都拦好了。前端也做了：注册页标了「需管理员审核」，
提交后不再当场变角色。

**唯独没有任何一个界面能批准。** 申请进队列里攒着，用户被拦在外面，
而没有任何人有能力放行。

这比不做更糟：不做的话用户能正常发房源；做成这样，用户被一道
**没有出口的闸**关住了。

补法是新建 `RoleRequestPanel.jsx` 挂进管理后台「身份升级」页签。

**怎么发现的：** 不是测出来的，是做 F5 重排页签时逐个数
「管理后台到底有几件待办」，数到「身份升级」时发现没有对应的页签。
**如果不是恰好去数页签，这个洞会一直留到答辩现场。**

教训：**一个新规则至少涉及三处——写入、拦截、放行。**
今天只做了前两处就以为完事了。

### 五、竖排组名：省下的宽度换来一个读不出来的标签
