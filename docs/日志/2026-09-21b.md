## 一、这半天的主线

参考文档给的是一套「**先画设计稿，再导出 SQL**」的流程
（ER-Studio 或那份 `shengyadb.xls`）。这套流程有一个前提：
**设计稿是唯一的源**。

我们这个项目不满足这个前提。表结构早就在 `server/app/models.py` 里跑着，
测试、接口、迁移全依赖它。这时候再摆一份设计稿进来，就有了两个源，
而两个源必然分叉。

所以方向反过来：**模型是唯一的源，SQL、数据库设计书、接口清单
全部从它生成。** 交付要求「能导出 SQL 直接建库」照样满足，
还多一条保证——导出的东西和正在跑的代码永远是同一份。

**这不是推演出来的担心。** 做这半天的活，一共撞见五处已经分叉的地方，
每一处都是「改了代码、没人改文档」：

| 分叉 | 差在哪 |
|---|---|
| 《数据库设计说明书》第三章 | 少了 `role_requests` 整张表 |
| 同上 | 少了 `users.accept_contact`、`houses.building` / `unit`、`reviews` 的五个字段 |
| 《技术架构说明》 | 写着「145 个接口 / 35 张表」，实际 150 / 36 |
| 概要设计初稿（我自己写的） | 三条接口路径根本不存在，其中一条连 HTTP 方法都错 |
| 概要设计初稿的模块统计表 | 九个模块加起来 160，而全站只有 150 |

第三章本来就是生成的，只是模型改了没人重跑。**这说明「记得重跑」
这件事靠不住**，得把它交给测试。

## 二、做了什么

### 1. 建库脚本：两份，都真跑过

`scripts/gen_db_sql.py` 从模型生成两份 DDL：

- **MySQL 8**：交付格式（对标 `ticketServer.sql`），InnoDB + utf8mb4，
  表注释与字段注释写进 `COMMENT`；
- **SQLite**：`db.py`、`seed.py`、测试套件实际在用的那份结构。

不是「看着像能跑」：

| 验证 | 结果 |
|---|---|
| `sqlite3 verify.db < 建库脚本_SQLite.sql` | 36 表 / 388 字段 / 98 索引，与模型**逐表逐字段比对一致** |
| 临时起 mysqld 9.3 跑 MySQL 脚本 | 建库成功：36 表 / 388 字段 / 60 外键 / 170 索引条目 |
| **同一份脚本连跑两遍** | 第二遍照样成功（自带 `DROP TABLE IF EXISTS`） |
| 注释有没有落库 | `table_comment`、`column_comment` 都查得到中文说明 |

**列默认值有意不写进 DDL**：模型里的 `default=datetime.now`、`default=""`
是 Python 侧的，由 ORM 插入时填。写进 DDL 就等于多一份由数据库执行的语义，
两边不一致时「谁说了算」会变成一个没人能回答的问题。

### 2. 数据库设计书：对标参考版式，改了三处并写明原因

`scripts/gen_db_xlsx.py` 生成 40 个工作表
（封面 / 说明 / 表清单 / 需求追溯 + 36 张表各一页）。

版式照搬 `shengyadb.xls`（表头四行 + 逐字段一行 + 末尾 `END`），
**但改了三处，每一处都写在工作簿的「说明」页里**，免得评审时以为是抄漏了：

1. 去掉 `扩展 / 左 / 类型 / 右 / List显示` 五列——那是给界面生成器用的
   （某字段在页面上是 input 还是下拉），我们前端是手写 React，
   留着就是五列空白；
2. 加一列「键」（PK / FK→目标 / UQ / IDX）——参考文档里表间关系全靠
   字段名对暗号，**而本项目建的是真外键**，这是主要区别，得看得见；
3. `id`、`created_at` 这类列照列不误——参考文档省掉由工具补，
   我们没有那个工具，省掉就等于文档和库对不上。

### 3. 需求追溯：36 张表逐张挂到需求编号上

`db_meta.py` 新增两张登记表：`MODULES`（9 个模块的表归属）与
`REQUIREMENTS`（表 → 需求编号）。工作簿里因此多了一页「需求追溯」，
是反过来的「这条需求落在哪几张表上」——**评审问的往往是这一个方向：
哪条需求没有任何表接着，就是漏做了。**

编号**只用《需求分析说明书》里的稳定编号**（F/M/K/J/T/R/N/AI）。
《改进清单》那种按天编的 D1、B2 不进来：同一个 D1 在三天的清单里
指三件不同的事，拿它做追溯等于给自己挖坑。
（`role_requests` 的说明原本就写着「D-1」，而《待完善清单》的 D-1
是「钱是假的」，两者无关——顺手改成《改进清单 2026-09-10》D1。）

### 4. 概要设计说明书

按《概要设计模板》的五章结构写：文档概述、系统结构图、模块详细概述
（9 个业务模块 + 智能体服务）、数据库设计、接口设计，外加附录 A 接口清单。
导出的 Word 版 38 页、36 张表。

**源是 Markdown，交付的是 Word。** 用 Word 当源文件，这份文档就没法被
git 管——看不出改了什么、谁改的、为什么改，评审前一晚两个人的修改
只能靠「你先别动我来改」。

## 三、三处交给脚本，因为手写必然出错

### 接口路径：初稿写了三条不存在的接口

```
POST  /api/role-requests              实际是 POST /api/auth/become-landlord
PATCH /api/admin/role-requests/{id}   实际是 POST（方法也错了）
POST  /api/password-reset/request     实际是 POST /api/auth/forgot
```

评审时没人按图索骥去试，这三条会一直躺在文档里；真有人照着调，
就会得到 404 并开始怀疑是自己搞错了。

所以 `gen_api_list.py` 除了生成清单，还**把正文里每一条 `METHOD /path`
拿去和运行中的应用对一遍**。第一次跑，除上面三条外又报出 11 条——
路径参数名写成了 `{id}` 而实际是 `{repair_id}`、`{contract_no}`。
全部改对之后，**83 条引用逐条核对通过**。

### 模块统计表：加起来 160，而全站只有 150

手写的那版九个模块的接口数是估的。差出来的 10 个不会有人发现，
**因为没人会去把一列数字加一遍**。改成按路径前缀归并统计后生成。

### 接口清单：差点少了 63 条，而且不会报错

从两个 FastAPI 应用的路由表导出，不从代码里正则抓装饰器
（抓装饰器会漏掉 `include_router` 的前缀）。

这里踩了个坑：`app.routes` 里挂的不全是普通路由，
`include_router` 进来的是 `_IncludedRouter` 对象，**它没有 `.path`**。
第一版没顺着 `original_router` 往下走，导出 87 条，看起来很正常——
**清单少一截是不会报错的，只会悄悄地少。** 走下去之后是 150 条。
