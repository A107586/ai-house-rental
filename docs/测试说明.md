# 测试说明

> 面向组员的测试指引，也是 10 月 19–23 日黑盒测试周《黑盒测试书》的基础。
> 对应版本：v0.3（前端可用版）。

---

## 一、五分钟跑起来

### 前置条件

| 需要 | 说明 |
|---|---|
| Python 3.10+ | 后端与智能体 |
| Node.js **16.x** | 前端。Node 18+ 会因 webpack/OpenSSL 问题报错 |
| MySQL | ❌ **不需要**。本地开发用 SQLite，零配置无密码 |
| 大模型 API Key | ❌ **不需要**。没有 Key 时系统降级为纯规则模式，核心功能全部可用 |

### 第一步：装依赖

```
pip install fastapi uvicorn pydantic sqlalchemy
cd web && npm install
```

### 第二步：生成演示数据

```
cd server
python seed.py
```

预期输出：

```
用户 13 个（管理员 1、房东 8、租客 4）
房源 108 套，其中可租 101 套
看房预约 15 条，报修工单 4 条
```

数据用固定随机种子生成，**每个人跑出来完全一致**，所以用例里可以写死房源编号。

### 第三步：启动三个服务

```
powershell -ExecutionPolicy Bypass -File .\start-all.ps1
cd web && npm run dev
```

| 服务 | 地址 | 说明 |
|---|---|---|
| **前端网站** | <http://localhost:5173> | **主要测试入口** |
| 业务后端 | <http://localhost:8080/docs> | 接口文档 |
| 智能体服务 | <http://localhost:8000/docs> | 接口文档 |

## 三、手工测试用例

全部在 <http://localhost:5173> 操作，除非特别注明。

### 3.1 AI-01 自然语言找房

首页搜索框输入后点「智能找房」。

| 编号 | 输入 | 预期结果 |
|---|---|---|
| S-01 | 中山区两室一厅，租金三千以内，最好带电梯 | 页面出现绿色标签 `区域：中山区` `户型：两室一厅` `租价 ≤ 3000 元` 和红色标签 `偏好：电梯`；带电梯的房源排前面 |
| S-02 | 帮我找一个月租3000以内，两室一厅，距离学校近一点，最好有地铁的房子 | 解析出 `两室一厅` `≤3000`，偏好 `地铁`、`近学校` |
| S-03 | 沙河口 合租 单间 1500以下 | 区域补全为 `沙河口区`，户型 `一室`，类型 `合租` |
| S-04 | 甘井子区 80平以上的三室 预算不超过五千 | 面积下限 80，租价上限 5000 |
| S-05 | 有没有金州区2000到3000的一居室 | 识别为**区间**，同时出现租价上下限，不能拆成两个上限 |
| S-06 | 中山区两室一厅，租金两千五以内 | 「两千五」解析为 **2500**，不是 2005 |
| S-07 | 旅顺口区三室两厅一千以内 | 结果为空，提示**建议把租价上限提高一些** |
| S-08 | 你好啊 | 提示「没听懂你的找房需求」 |
| S-09 | 任意搜索后点「重置」 | 回到最新房源列表，标签区消失 |
| S-10 | 不搜索，滚到底点「加载更多」 | 追加 12 套，计数变为「已显示 24 / 101」 |

**每次搜索都要检查标签区括号里的说明**，未配 Key 时应显示「规则解析，未调用大模型」。

### 3.2 AI-06 智能预约看房

点任意房源卡片 → 抽屉「预约看房」标签页。

| 编号 | 输入 | 预期结果 |
|---|---|---|
| B-01 | 这周六下午两点 | 绿框「已为你预约 X月X日（周六）14:00」，上方「已被预约的时段」立即多一条 |
| B-02 | 重复提交 B-01 | 黄框提示已被预约，并列出其它空闲时段按钮 |
| B-03 | 点 B-02 给出的任一时段按钮 | 直接预约成功 |
| B-04 | 这周六 | 黄框列出当天可选时段，**不含已被占用的** |
| B-05 | 最近三天都可以 | 黄框跨天列出候选时段 |
| B-06 | 这周六晚上十点 | 提示看房时间为 09:00–18:00 |
| B-07 | 上周一下午两点 | 拒绝，提示时间已过去 |
| B-08 | 我想看房 | 提示「可以说这周六下午两点」 |
| B-09 | 下周一下午三点半 | 日期是**下周那个周一**，不是两周后 |

> 相对日期取决于运行当天是星期几，手工测试时请自行换算。

### 3.3 AI-04 报修工单智能分派

房源抽屉 → 「报修」标签页。

| 编号 | 输入 | 预期分类 | 预期紧急程度 | 预期派单 |
|---|---|---|---|---|
| P-01 | 卫生间水管漏水了，地上都是水 | 水暖 | **紧急** | 水暖工 |
| P-02 | 空调不制冷 | 家电 | 一般 | 家电维修师傅 |
| P-03 | 客厅灯泡坏了，不急，有空再说 | 电路 | **可延后** | 电工 |
| P-04 | 闻到煤气味了 | 燃气 | **紧急** | 燃气专员 |
| P-05 | 卧室门锁打不开 | 门窗 | **紧急** | 门窗维修师傅 |
| P-06 | 衣柜门掉了 | 家具 | 一般 | 木工 |
| P-07 | **厨房水管漏水，不急，有空来看看就行** | 水暖 | **紧急** | 水暖工 |

> **P-07 是重点用例**：租客自己说「不急」，但涉及漏水这类安全隐患，
> 系统**必须**判为紧急，不能被客气话降级。

提交后检查：绿框显示三个标签（类型 / 紧急程度 / 派单），
上方「该房源的报修记录」立即出现新工单，紧急的带红色徽章。

### 3.6 业务规则校验

| 编号 | 操作 | 预期 |
|---|---|---|
| C-01 | 对已租房源（`DL0003` 类）提交预约 | 409 |
| C-02 | 预约时间填过去的时间 | 400 |
| C-03 | 同一房源同一时段提交两次 | 第二次 409 |
| C-04 | 同一房源相隔 30 分钟提交 | 409，一次看房占用一小时 |
| C-05 | 同一房源相隔 1 小时提交 | 200 |
| C-06 | **取消一个预约后，再约同一时段** | **200，取消后时段应释放** |
| C-07 | `GET /api/houses` 不带参数 | 只返回可租房源 |
| C-08 | `GET /api/houses?limit=5&page=2` | 返回 5 条，`total` 是总数不是本页条数 |
| C-09 | `GET /api/houses/DL0008` 连续两次 | `view_count` 递增 |

### 3.7 降级与容错（重点）

对应需求 N-07，**答辩大概率被问**。

| 编号 | 操作 | 预期结果 |
|---|---|---|
| F-01 | 不配置 `LLM_API_KEY` 启动 | `GET localhost:8000/health` 显示 `mode: 纯规则（降级模式）` |
| F-02 | 降级模式下跑完 S-01～S-08、B-01～B-09、P-01～P-07 | **全部正常**，核心功能不依赖大模型 |
| F-03 | 关掉业务后端（8080），前端搜索 | 提示「房源服务暂时不可用」，页面不白屏、不报 500 |
| F-04 | 关掉业务后端，前端提交预约 | 提示「预约服务暂时不可用」 |
| F-05 | 关掉智能体（8000），前端搜索 | 提示连不上服务器，顶栏状态灯变红 |
| F-06 | 填一个无效的 `LLM_API_KEY`，问一句规则识别不了的话 | 自动回退规则，`source` 为 `rules_fallback`，不报错 |
