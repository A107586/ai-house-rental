## 1. 规则与大模型融合

**文件**：`agent/app/fusion.py`，核心函数 `fuse()` 在第 80 行。

### 1.1 函数签名

```python
def fuse(rule_result, provider, system, prompt, sanitize,
         guards=(), enabled=True, trace=None, confidence=None,
         confidence_threshold=None):
    """
    :returns: (final, source, divergence)
    """
```

各参数的作用：

| 参数 | 作用 |
|---|---|
| `rule_result` | 规则算出的结构化结果（dict） |
| `provider` | 大模型提供方，`None` 或不可用时直接退回规则结果 |
| `sanitize` | `fn(raw) -> dict|None`，白名单与类型校验，返回 `None` 表示输出不可用 |
| `guards` | `[fn(rule_result, fused) -> (fused, note)]`，硬性规则兜底 |
| `confidence` | 规则解析的置信度，够高就短路不调大模型 |

### 1.2 第一道防线：大模型不可用

```python
if not enabled or provider is None or not getattr(provider, "available", False):
    return dict(rule_result), SOURCE_RULES, []
```

**这一行是需求 N-07 的实现**。全部 1,445 条自动化测试都走这条分支——
没有 API Key 的机器上，`provider` 为 `None`，函数立刻返回规则结论。

> **技术点：为什么用 `getattr(provider, "available", False)` 而不是 `provider.available`**
> 防的是「provider 存在但没有这个属性」的情况。第三个参数是默认值，
> 属性不存在时返回 `False` 而不是抛 `AttributeError`。
> 这类写法在插件式结构里很常见——你不能假设别人的实现一定完整。

### 1.3 短路：置信度够高就不问大模型

```python
if (confidence is not None and confidence_threshold is not None
        and confidence >= confidence_threshold):
    if trace:
        with trace.step("规则置信度足够，跳过大模型") as step:
            step.says("置信度 %.2f ≥ 阈值 %.2f"
                      % (confidence, confidence_threshold))
    return dict(rule_result), SOURCE_RULES, []
```

**注意方向：置信度高才跳过。** 低的时候恰恰最需要大模型补救。
这个判断写反是很容易犯的错——直觉上「不确定就别麻烦大模型了」，
但那正好是最该问的时候。

这段是 9-07 加的（K-10），把「押金怎么退」从 42.1 秒降到 3.5 秒。

### 1.4 三层输出校验

```python
try:
    raw = provider.complete_json(system, prompt)
except LLMUnavailable as exc:
    step.says("不可用：%s" % exc)
    return dict(rule_result), SOURCE_FALLBACK, []
except Exception as exc:
    # 提供方实现里的任何意外都不该把整条请求带崩
    step.says("异常：%s" % type(exc).__name__)
    return dict(rule_result), SOURCE_FALLBACK, []

if isinstance(raw, str):
    try:
        raw = json.loads(raw)
    except (ValueError, TypeError):
        step.says("输出不是合法 JSON，已退回规则")
        return dict(rule_result), SOURCE_FALLBACK, []

if not isinstance(raw, dict):
    step.says("输出不是对象，已退回规则")
    return dict(rule_result), SOURCE_FALLBACK, []

cleaned = sanitize(raw)
if not cleaned:
    step.says("输出未通过校验，已退回规则")
    return dict(rule_result), SOURCE_FALLBACK, []
```

四种失败，**每一种都退回规则、都不抛异常**：调用失败、不是 JSON、
不是对象、没通过白名单。

> **技术点：`except Exception` 通常是坏味道，这里是刻意的**
> 一般不该捕获所有异常，因为会掩盖 bug。但这里跨的是「我们的代码」与
> 「provider 实现」的边界——第三方实现里的任意错误不该让整个用户请求崩掉。
> 关键是**捕获后记了日志**（`step.says`），没有静默吞掉。
>
> 9-03 就吃过反面亏：房源查询只捕获自定义的 `BackendError`，别的异常直接
> 穿透，用户看到 500 而不是「房源服务暂时不可用」。

### 1.5 硬性规则守卫

```python
divergence = _diff(rule_result, cleaned)

for guard in guards:
    cleaned, note = guard(rule_result, cleaned)
    if note:
        divergence.append(note)
```

`guards` 是一串函数，逐个执行、每个都能改写结果并记一条说明。
AI-04 的「漏水断电煤气必须判紧急」就是这样一个 guard。

> **技术点：这是策略模式（Strategy Pattern）**
> 把「怎么兜底」抽成可插拔的函数列表，`fuse` 本身不知道有哪些规则。
> 好处是新增一条硬性规则不用改 `fuse`，只要多传一个函数；
> 每个 guard 也能单独写测试。

## 2. 意图路由与短路

**文件**：`agent/app/supervisor.py`，`INTENT_KEYWORDS` 在第 23 行，
`classify_by_rules()` 在第 82 行。

### 2.1 强弱特征词

```python
INTENT_KEYWORDS = [
    ("repair",
     ["报修", "漏水", "堵了", "不制冷", "维修", "跳闸", "停电"],   # 强
     ["坏了", "修一下", "不好使"]),                              # 弱
    ("support",
     ["退租", "水电费", "物业费", "平台规则", "怎么收费"],
     ["怎么", "如何", "可以吗", "能不能", "为什么"]),
]
```

**规则**：只有命中强特征词的意图才成为候选，弱特征词仅用于加权区分。

为什么必须这样分——「怎么」「如何」几乎出现在任何提问里。若与「退租」
同等看待，一句「今天股市怎么样」会被判成客服问答，**而且置信度足够高、
根本不会转交大模型复核**，错得很自信。

### 2.2 置信度分档

```python
if ...:
    confidence = 0.9      # 强特征词命中多个
elif ...:
    confidence = 0.8
else:
    confidence = 0.65
return best, confidence, hits[best]
```

这三个数字与 1.3 节的短路阈值配合：阈值取自 `settings.rule_confidence_threshold`，
0.9 和 0.8 通常在阈值以上（直接短路），0.65 在阈值以下（交给大模型复核）。

> **技术点：列表顺序即优先级**
> `INTENT_KEYWORDS` 是**列表**不是字典，顺序有意义：越靠前的意图越具体。
> 「报修」排在「客服」前面，因为「漏水怎么办」既像报修又像问规则，
> 但按报修处理更安全（能派单）。
>
> Python 3.7+ 的 dict 虽然保序，但**用列表表达「顺序是语义的一部分」更清楚**，
> 读代码的人一眼知道不能随便调换。

## 3. BM25 检索

**文件**：`agent/app/retrieval/bm25.py`，公式在第 10 行注释，
`scores()` 在第 60 行。

### 3.1 算法本身

BM25 是信息检索里的经典打分函数，用来衡量「一个查询和一篇文档有多相关」：

```
score(q, d) = Σ_t  IDF(t) · f(t,d)·(k1+1) / (f(t,d) + k1·(1 - b + b·|d|/avgdl))
```

拆开看三个部分：

| 部分 | 含义 | 直觉 |
|---|---|---|
| `IDF(t)` | 逆文档频率 | 词越罕见越有区分度。「押金」比「的」值钱 |
| `f(t,d)·(k1+1) / (f(t,d) + k1·...)` | 词频饱和 | 出现 10 次不该比出现 5 次得分翻倍，收益递减 |
| `1 - b + b·|d|/avgdl` | 长度归一化 | 长文档天然容易命中，要按长度惩罚 |

两个超参：`k1=1.5` 控制词频饱和的快慢，`b=0.75` 控制长度惩罚的强度，
都是文献常用值。

### 3.2 代码实现

```python
def scores(self, query_tokens):
    if not self.total or not query_tokens:
        return {}

    # 查询里重复出现的词只算一次。
    # 「押金押金什么时候退」不该比「押金什么时候退」得分更高——
    # 用户重复用词是口语习惯，不是相关性信号。
    raw = {}
    for token in set(query_tokens):
        posting = self.postings.get(token)
        if not posting:
            continue
        idf = self.idf[token]
        for index, freq in posting.items():
            norm = 1 - self.b + self.b * (
                self.doc_len[index] / self.avgdl if self.avgdl else 1.0)
            weight = freq * (self.k1 + 1) / (freq + self.k1 * norm)
            raw[index] = raw.get(index, 0.0) + idf * weight

    return {self.doc_ids[i]: s for i, s in raw.items()}
```

三处值得学的写法：

**一、`set(query_tokens)` 去重。** 这不是性能优化，是**语义决定**——
注释写清楚了为什么。

**二、倒排索引（postings）。** `self.postings` 是 `{词: {文档号: 词频}}`。
遍历的是「查询里的词」而不是「所有文档」，**只有命中的文档才参与计算**。
语料几十条时无所谓，几万条时这就是能不能用的分别。

**三、`if self.avgdl else 1.0` 的除零保护。** 空索引时 `avgdl` 为 0，
不保护会 `ZeroDivisionError`。

### 3.3 稳定排序

```python
ranked = sorted(scored.items(), key=lambda kv: (-kv[1], str(kv[0])))
```

**同分时按 doc_id 排序。** 不这样做，同分文档的顺序会随字典遍历顺序变化，
测试会随机失败——这类「有时过有时不过」的测试最难查。

> **技术点：`key` 返回元组实现多级排序**
> `(-kv[1], str(kv[0]))` 表示「先按分数降序（取负号），分数相同再按 id 升序」。
> Python 比较元组是逐位比较的，这是多级排序的标准写法。

## 4. RRF 排名融合

**文件**：`agent/app/retrieval/rrf.py`，`DEFAULT_K = 60` 在第 19 行，
`fuse()` 在第 22 行。

### 4.1 算法

```
RRF(d) = Σ_路  w_路 / (k + rank_路(d))
```

**只用排名，不用分数。**

为什么这很重要——本项目有四路检索：正文 BM25、标题 BM25、同义扩展 BM25、
向量余弦。BM25 分数没有上界、随语料规模漂移；余弦相似度固定在 [-1, 1]。
**直接加权必须先归一化，而归一化本身又要标定参数。**

RRF 把每一路的输出降级成「第几名」，天然免疫量纲问题。

`k=60` 的含义是「排名靠前的差距别拉得太夸张」：第 1 名与第 2 名的权重比是
61/62 ≈ 0.98，而不是 1/2。对小语料尤其合适——几十条文档里第 3 名和第 1 名的
真实差距往往很小。

### 4.2 代码

```python
totals = {}
best_rank = {}   # 记录每个文档在各路里的最好名次

for channel, ranked in enumerate(ranked_lists):
    weight = weights[channel]
    if not weight:
        continue
    for rank, item in enumerate(ranked, start=1):
        doc_id = item[0] if isinstance(item, (tuple, list)) else item
        totals[doc_id] = totals.get(doc_id, 0.0) + weight / (k + rank)
        if doc_id not in best_rank or rank < best_rank[doc_id][1]:
            best_rank[doc_id] = (channel, rank)
```

**`enumerate(ranked, start=1)`** —— 排名从 1 开始，不是 0。
从 0 开始会让第一名的分母是 `k+0`，与公式不符。

**`best_rank` 是为答辩留的。** 它记录每个文档是被哪一路捞出来的，
可以当场展示「这条答案是标题路命中的，正文路根本没排进前十」。

> **技术点：为什么 `weights` 要补齐**
> ```python
> weights = list(weights or [])
> weights += [1.0] * (len(ranked_lists) - len(weights))
> ```
> 调用方传三个权重却给了四路时，第四路按 1.0 处理而不是 `IndexError`。
> **接口对不完整输入要有确定行为**，这是库代码和业务代码的区别之一。

## 5. 可答性闸门

**文件**：`agent/app/agents/support/tools/gate.py`，
`COVER_STRONG = 0.42` 在第 54 行，`evaluate()` 在第 87 行。

### 5.1 为什么不靠提示词

需求 AI-03 要求「无依据时必须回答『暂无相关信息』，不得编造」，
指标是拒答率 ≥ 90%。

**提示词保不住这个指标。** 写「没有依据就说不知道」，模型照做与否是
概率问题；而 90% 是一条硬线。所以拒答做成代码里的闸门，
**大模型只能让它更严，不能让它更松**。

### 5.2 三条判据

| 判据 | 内容 |
|---|---|
| G1 覆盖率 | 查询的 IDF 质量有多少落在选中的材料上 |
| G2 关键词命中 | 查询里区分度最高的那个词，材料里出现了吗 |
| G3 大模型判据 | 只在 G1/G2 判「可答」但覆盖率不高时调用，**只能推翻成拒答** |

### 5.3 阈值是标定出来的，不是拍的

```python
# 阈值在 `tests/fixtures/support_tune.py` 的调参集上标定，
# **不是在验收集上调的**——验收集全程不参与任何阈值选择。
# 标定脚本：`python -m tests.calibrate_gate`
COVER_STRONG = 0.42
```

> **技术点：调参集与验收集必须分开**
> 这是机器学习里最基本的一条纪律。在验收集上调阈值，等于拿考卷答案去
> 复习，报出来的指标虚高。本项目单独建了 `support_tune.py` 作调参集，
> 验收集全程不参与。
>
> **答辩时这一条很值得讲**——它说明指标是真的，不是调出来的。

### 5.4 一个真实的调参教训

```python
# **取值 0.42 是可行区间 [0.41, 0.43] 的中点，不是边缘。**
# 语料从 54 条扩到 70 条之后，IDF 分布变了，原先定在 0.45 的阈值把一条
# 覆盖率 0.4497 的正例卡在了门外——它的正确答案还排在检索第一位。
# 更糟的是标定脚本当时用 0.05 的粗网格，正好跨过了 0.41~0.43 这段
# **更优且更宽**的平台（回答率 86.2% vs 82.8%，拒答率同为 92.9%）。
```

两条教训写进了标定脚本：**网格细到 0.01**，并且**在可行区间里取中点**——
取边缘的阈值经不起语料增长。

### 5.5 G2 改过两次

原先用「查询里有多少词在语料里没出现过」判断，两个方向都不对：
只算整词太严（七条本该回答的问题全被拒），只算单字太松（拒答率掉到 64%）。

**结论是「措辞新不新」不是「答得了答不了」的正确代理量**，
换成「问的那个东西提没提」才对上。

第二次修的是「那个东西」怎么挑：原先在字符 bigram 里挑 IDF 最高的，
而**没见过的组合 IDF 必然最高**，于是系统性地挑中「久说」「扫干」「约完」
这种切在词缝上的碎片。改成先用 jieba 判断是不是词，
有依据正确率 80% → 85%。

> **这就是为什么 jieba 从「可选」变成「必装」依赖。**

## 6. HMAC 无状态令牌

**文件**：`server/app/auth.py`，`_sign()` 第 41 行、`create_token()` 第 47 行、
`decode_token()` 第 71 行。

### 6.1 签名

```python
def _sign(payload_b64):
    digest = hmac.new(SECRET.encode("utf-8"),
                      payload_b64.encode("ascii"), hashlib.sha256).digest()
    return _b64encode(digest)
```

令牌形如 `base64(payload).base64(signature)`。

> **技术点：HMAC 是什么**
> HMAC（Hash-based Message Authentication Code）用一个**密钥**和一段消息
> 算出摘要。没有密钥的人改了消息就算不出对应的摘要，服务端一验就发现。
>
> 它与单纯的哈希不同：`sha256(消息)` 谁都能算，`hmac(密钥, 消息)` 只有
> 持密钥的人能算。这就是「无状态令牌」成立的基础——服务端不存会话，
> 靠签名确认这个令牌是自己签发的。

### 6.2 签发

```python
payload = {
    "uid": user.id,
    "username": user.username,
    "role": user.role,
    # 带小数：吊销基线是 datetime，精确到微秒。iat 若只存整秒，
    # 「同一秒内签发又吊销」会因为 1000 < 1000 不成立而漏掉，
    # 改完密码立刻用旧令牌仍然能访问。
    "iat": time.time(),
    "exp": int(time.time()) + TTL_SECONDS,
}
```

**`iat` 用浮点数是修过的 bug。** 原本写 `int(time.time())`，
同一秒内签发又吊销时判断失效——这类问题在测试里几乎撞不到，
因为测试跑得快，恰好都在同一秒。

### 6.3 校验

```python
payload_b64, _, signature = token.rpartition(".")
# 先比签名再看内容，避免有人伪造 payload 探测行为差异
if not hmac.compare_digest(signature, _sign(payload_b64)):
    return None
```

两个安全细节：

**一、先验签名再解析内容。** 顺序反了的话，攻击者可以构造畸形 payload
观察服务端的不同反应来试探。

**二、`hmac.compare_digest` 而不是 `==`。**

> **技术点：时序攻击（Timing Attack）**
> Python 的 `==` 比较字符串是**短路**的——第一个字符就不同会立刻返回。
> 攻击者可以通过测量响应时间，一个字符一个字符地猜出正确签名：
> 猜对第一个字符时响应会慢那么一点点。
>
> `hmac.compare_digest` 是**常数时间**比较，无论哪里不同都走完全程，
> 时间不泄漏任何信息。凡是比较密钥、令牌、签名，都要用它。

### 6.4 吊销

用户表有 `token_valid_after` 字段，改密码时写入当前时间，
比它早签发的令牌一律失效。

**好处**：保留无状态的全部优点，又能立刻踢掉旧令牌，
不用维护黑名单表，也不用每次请求查缓存——因为鉴权本来就要查一次 `User`。

## 7. ORM 与 N+1 问题

**文件**：`server/app/models.py`，`House` 的关系声明在第 192–201 行。

### 7.1 什么是 N+1

```python
# lazy="selectin"：列表接口一次查 12 套房，若按默认的懒加载，
# to_dict 里每读一次 landlord 就发一条 SQL——实测 12 套房发了 32 条。
# selectin 会把这一批的关联对象用一条 IN 查询取回来。
landlord: Mapped["User"] = relationship(back_populates="houses",
                                        lazy="selectin")
images: Mapped[list["HouseImage"]] = relationship(
    back_populates="house", order_by="HouseImage.sort_order",
    lazy="selectin")
reviews: Mapped[list["Review"]] = relationship(lazy="selectin")
```

> **技术点：N+1 查询**
> 查 N 条主记录发 1 条 SQL，然后为每条主记录各查一次关联对象，
> 又发 N 条——总共 N+1 条。
>
> 危险在于**它不会报错，只会变慢，而且随数据量线性恶化**。
> 开发时 5 条数据看不出来，上线 500 条就崩了。
>
> SQLAlchemy 的加载策略：
> - `lazy="select"`（默认）：用到时才查 → N+1
> - `lazy="selectin"`：主查询后用一条 `WHERE id IN (...)` 批量取回
> - `lazy="joined"`：JOIN 进主查询，一条 SQL 搞定，但一对多时会让主表行重复
>
> **选 `selectin` 而不是 `joined`**：一对多关系用 JOIN 会产生笛卡尔积
> （12 套房 × 3 张图 = 36 行），还要在应用层去重。`selectin` 多一条 SQL，
> 但结果干净、行数可控。

本项目 28 处关系声明了 `selectin`，房源列表从 109 条 SQL 降到 5 条，
**且不随数据量增长**。

### 7.2 类型标注写法

```python
rent_price: Mapped[float] = mapped_column(Numeric(10, 2), nullable=False, index=True)
```

`Mapped[float]` 是 SQLAlchemy 2.0 的写法，好处是编辑器和类型检查器
能看懂字段类型。1.x 的 `Column(...)` 做不到。

**金额一律 `Numeric(10, 2)`，不用 `Float` 也不用 `varchar`。**

> **技术点：为什么金额不能用浮点数**
> 二进制浮点数表示不了 0.1，`0.1 + 0.2 == 0.30000000000000004`。
> 金额累加多次会产生肉眼可见的误差，对账对不平。
> `Numeric`/`DECIMAL` 是定点数，按十进制精确存储。
>
> 这条写成了需求 R-04——对照的原型系统里租价字段有的 `int` 有的 `varchar`，
> 那是真实存在的坏例子。

## 8. 连接池

**文件**：`server/app/db.py`，第 40 行起。

```python
_pool_options = {}
if DATABASE_URL != "sqlite://" and not DATABASE_URL.endswith(":memory:"):
    _pool_options = {
        "pool_size": 20,
        "max_overflow": 40,
        "pool_timeout": 5,
        "pool_pre_ping": True,
    }

engine = create_engine(DATABASE_URL, connect_args=_connect_args, future=True,
                       **_pool_options)
```

### 8.1 四个参数各管什么

| 参数 | 含义 | 本项目取值与理由 |
|---|---|---|
| `pool_size` | 常驻连接数 | 20，默认 5 太少 |
| `max_overflow` | 峰值可临时多开的连接数 | 40，上限合计 60 |
| `pool_timeout` | 等不到连接时等多久 | **5 秒**，默认 30 秒 |
| `pool_pre_ping` | 取出连接前先探活 | 开，防 MySQL 掐掉空闲连接 |

### 8.2 超时为什么反而调小

默认上限 15 条连接、超时 30 秒。实测 100 并发时 85 个请求排队等满
30 秒后失败，成功率一度只有 1/100。

**排队 30 秒才失败是最糟的结果**——用户早走了，连接还占着不放。
压到 5 秒是让它快点失败、快点把连接还回池子，前端也能及时提示
「服务繁忙」而不是干等着转圈。

> **技术点：快速失败（Fail Fast）**
> 系统过载时，让请求快速失败比让它长时间排队更健康。排队的请求仍占着
> 内存、连接、线程，会把过载放大成雪崩。这条原则在限流、熔断、
> 超时设置里反复出现。

### 8.3 为什么参数要条件传

```python
if DATABASE_URL != "sqlite://" and not DATABASE_URL.endswith(":memory:"):
```

内存库（测试用的 `sqlite://`）走的是 `SingletonThreadPool`，
它**压根不接受** `max_overflow` / `pool_timeout`，传了会在 `create_engine`
阶段直接抛 `TypeError`。

这个坑真的踩过：一次无条件传参数，474 条测试全部跑不起来。

## 9. 数据库迁移

**文件**：`server/app/migrations.py`，`step()` 在第 28 行。

### 9.1 注册机制

```python
_STEPS = []

def step(version, description):
    def register(func):
        _STEPS.append((version, description, func))
        return func
    return register
```

用法：

```python
@step("0005", "users 表加 token_valid_after")
def _0005(connection, engine):
    _add_column(connection, engine, "users", "token_valid_after", "DATETIME")
```

> **技术点：带参数的装饰器是三层函数**
> - 最外层 `step(version, description)` 接收参数，返回真正的装饰器
> - 中间层 `register(func)` 接收被装饰的函数
> - 返回 `func` 本身，不改变函数行为，只是**顺手把它登记进列表**
>
> 这是「注册表模式」的常见实现。Flask 的 `@app.route`、
> pytest 的 `@pytest.fixture` 都是这个套路。

### 9.2 三条约束

**有序执行**、**只跑一次**（`schema_migrations` 表记录已执行版本）、
**每步幂等**（重复执行不出错）。

### 9.3 一个必须分清的返回值

```python
def _columns(engine, table):
    """表的列名集合。**表不存在时返回 None，不是空集合。**

    这两者必须分开：空集合表示「表在、但没有这一列」，该执行 ALTER；
    None 表示「表根本不存在」，该整步跳过。混为一谈会去 ALTER 一张
    不存在的表，直接报 no such table。
    """
    try:
        return {c["name"] for c in inspect(engine).get_columns(table)}
    except Exception:
        return None
```

> **技术点：空值与不存在是两回事**
> `name not in set()` 恒为真，所以返回空集合会导致「表不存在」被当成
> 「缺这一列」，然后去 ALTER 一张不存在的表。
>
> 这类 bug 在 Python 里很常见，因为 `None`、`[]`、`{}`、`0`、`""`
> 在布尔上下文里都是假。**需要区分时必须显式判断 `is None`。**

## 10. 退租结算

**文件**：`server/app/leasing.py`，押金退款逻辑在第 500–520 行。

### 10.1 一个真实的账目 bug

```python
# 押金退款：**只有真的收到过押金才生成退款记录**。
#
# 原先这段是无条件创建的，押金账单没付过时只把 payment_id 置空，
# 退款记录照样生成——于是一分钱没收，账上却挂着一笔「已退 3000 元」。
# 那不是记录不准，是凭空造了一笔支出，对账时对不平。
deposit_bill = next((b for b in contract.bills
                     if b.type == "deposit" and b.status == "paid"), None)
refund = None
if deposit_bill:
    refund = Refund(
        refund_no=_serial("TK"), contract_id=contract.id,
        payment_id=(deposit_bill.payment.id
                    if deposit_bill.payment else None),
        original_amount=deposit, deduct_amount=deduct,
        refund_amount=deposit - deduct, reason=reason or "退租押金结算",
    )
    session.add(refund)
    # 押金账单本身也要标记已退，否则重复退租会再退一次
    deposit_bill.remark = (deposit_bill.remark + " · 已退款").strip(" ·")
```

### 10.2 两个概念必须分开

| 字段 | 含义 |
|---|---|
| `contract.deposit_refund` | **应退多少**——结算结论，照常写 |
| `Refund` 记录 | **实际退了多少**——资金流水，没发生就不该有 |

**押金没收到时也不需要「退 0 元」的记录**：没有发生的资金流动不该留痕，
留了反而让对账的人以为退过。

> **技术点：`next(生成器, 默认值)` 找第一个满足条件的元素**
> ```python
> next((b for b in bills if 条件), None)
> ```
> 比 `[b for b in bills if 条件][0]` 好：找不到时返回 `None` 而不是
> `IndexError`，而且**找到第一个就停**，不会遍历完整个列表。

### 10.3 幂等

`deposit_bill.remark` 加「已退款」标记，防止重复退租再退一次。

> **技术点：涉及资金的操作必须幂等**
> 网络重试、用户手抖双击、消息重投——同一个请求到达两次是常态。
> 要么用唯一约束（本项目支付用的幂等键），要么用状态标记（这里的做法）。

## 11. 前端哈希路由

**文件**：`web/src/useHashRoute.js`，`useHashRoute()` 在第 31 行。

### 11.1 解析

```javascript
function readHash() {
  const raw = window.location.hash.replace(/^#\/?/, '')
  if (!raw) return { name: 'home', param: '' }
  const [name, param = ''] = raw.split('/')
  return { name, param: decodeURIComponent(param) }
}
```

`#/house/DL0017` 解析成 `{ name: 'house', param: 'DL0017' }`。

### 11.2 订阅浏览器事件

```javascript
useEffect(() => {
  // 前进后退、以及用户直接改地址栏，都靠这个事件同步
  const onChange = () => setRoute(readHash())
  window.addEventListener('hashchange', onChange)
  return () => window.removeEventListener('hashchange', onChange)
}, [])
```

> **技术点：`useEffect` 的清理函数**
> `return () => ...` 返回的函数会在组件卸载时执行。**不移除监听器就是
> 内存泄漏**——组件没了，闭包还挂在 `window` 上，还持有旧的 `setRoute`。
>
> 依赖数组 `[]` 表示只在挂载时执行一次。

### 11.3 只有一处更新状态

```javascript
if (replace) {
  window.history.replaceState(null, '', next)
  setRoute(readHash())
} else {
  // 直接改 hash 会触发 hashchange，状态由上面的监听器统一更新，
  // 不在这里 setRoute，免得同一次跳转更新两遍
  window.location.hash = next
}
```

**两条路径不对称，是刻意的**：`window.location.hash = next` 会触发
`hashchange`，监听器自会更新状态；而 `replaceState` **不触发**该事件，
所以必须手动 `setRoute`。

在两条路径里都写 `setRoute` 会让普通跳转渲染两次。

### 11.4 兜底

```javascript
const back = useCallback(() => {
  if (window.history.length > 1) window.history.back()
  // 没有历史可回时退到首页——直接从分享链接进来的用户
  // 按「关闭」不该被弹出整个站点
```

> **技术点：为什么用 hash 而不是 path**
> 后端把 `web/dist` 挂在 `/` 上，访问 `/house/DL0017` 会被当成静态文件
> 去找，直接 404。支持 path 路由要在后端加「所有未匹配路径都返回
> index.html」的兜底，会和现有的静态挂载打架。
>
> **hash 部分不会发给服务器**，浏览器只在本地处理，所以零改动。
>
> 代价：搜索引擎对 hash 路由的收录不如 path。真实平台不能这么做，
> 本项目是权宜之计。
