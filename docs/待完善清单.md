## 0. 怎么读这份清单

分成四档，**档位越靠前越该先做**：

| 档 | 含义 | 建议 |
|---|---|---|
| **A** | 已有功能不闭环，用户会当成 bug | 封版前必做 |
| **B** | 并发或安全隐患，出事就是事故 | 封版前必做 |
| **C** | 真实系统必备，但属于新增功能 | 有余力就做 |
| **D** | 受客观条件限制做不了（牌照、资质、第三方资源） | 答辩时主动说明边界 |

A、B 两档加起来大约两到三天，是投入产出比最高的部分。
D 档不是「偷懒没做」，是学生拿不到支付牌照、CA 证书、公安核验接口——
**答辩时主动讲出来，比被问出来强得多**。

## A 档 · 已有功能不闭环

这一档的共同点：后端接口都已经写好并测过了，缺的只是前端把它接上。
用户遇到时不会觉得「这个功能没做」，只会觉得「这个功能坏了」。

### A-1 租客看不到自己的报修 ✅ 已完成

**现象**：租客提交报修之后，个人中心里再也找不到它——不知道有没有人接单、
修没修好。只能记住是哪套房，回到那套房的详情页去看。

**根因**：`MyPanel` 没有「我的报修」标签页。

**后端已就绪**：`GET /api/repairs` 不带 `house_no` 时，会按角色自动过滤
（`server/app/main.py:1229`，租客只看到 `Repair.tenant_id == user.id`）。
**一行后端都不用改。**

**做法**：

1. `MyPanel.jsx` 的 `TABS` 加一项 `{ key: 'repairs', label: '我的报修', n: 未完成数 }`
2. `load()` 里并入 `api.listRepairs()`
3. 列表项显示：房源号、故障描述、AI 判定的类型与紧急程度、当前状态、提交时间
4. 已完成的工单展示维修记录（维修人员、处理说明）——`RepairRecord` 里都有

**量**：约 60 行前端。

### A-2 预约与租约里点不开房源 ✅ 已完成

**现象**：「我的预约」「我的租约」里，房源名是死文字。想再看一眼自己约的
那套房长什么样，只能回首页重新搜一遍。

**根因**：`MyPanel` 已经接收了 `onOpenHouse` 回调，但**只在收藏和足迹里用了**
（`MyPanel.jsx:354` 与 `:399`）。预约、租约两处漏了。

**做法**：

1. 预约列表项的 `<strong>{item.house_title}</strong>` 改成可点，调 `onOpenHouse`
2. `ContractCard` 增加 `onOpenHouse` 属性，房源标题同样可点
3. 列表里只有 `house_no`，需要先 `api.getHouse(house_no)` 拿完整对象再打开抽屉

**注意**：`ContractCard` 在 `MyPanel` 和 `LandlordPanel` 两处都用了，
属性要同时补上，否则房东侧点了没反应。

**量**：约 30 行。

### A-3 账单这条线断了三处 ✅ 已完成

| 断点 | 现状 | 该怎样 |

### A-4 「我的租约」没有详情，只有一张摘要卡 ✅ 已完成

**现状**：`ContractCard` 是一屏静态信息——起止日期、月租、押金、剩余天数。
缺的是「这份合同上发生过什么」。

**该有的**：

- **账单明细**：这份合同排了几期、交了几期、还欠多少、哪期逾期
- **报修记录**：租期内这套房报修过几次、都修了什么
- **状态时间线**：何时创建 → 何时生效 → 何时续租/退租，各由谁操作

**做法**：新建 `ContractDetail.jsx` 抽屉，点合同卡片打开。三块数据分别来自
`GET /api/bills?contract_no=`、`GET /api/repairs?house_no=`、
以及 `Contract` 上已有的 `signed_at` / `ended_at` / `end_reason` 字段。

时间线不需要新表——现有字段拼得出来。

**量**：约 180 行前端 + 后端账单接口加一个 `contract_no` 筛选参数。

**价值**：这是「我的租约」真正该有的样子，答辩演示交易链完整性时最有说服力。

## B 档 · 并发与安全隐患

这一档不影响演示，但**任何一条被现场问到都答不上来**。四条加起来不到一天。

### B-1 登录可以无限重试 🔴

**现状**：`POST /api/auth/login` 没有任何限流、没有验证码、没有失败计数。
撞库脚本可以不受限制地跑。

**做法**（不引第三方库）：

```python
# 内存里存 {ip: [失败时刻...]}，超过阈值直接拒绝
# 单进程部署下够用；将来上多 worker 再换 Redis
FAIL_WINDOW = 300      # 5 分钟
FAIL_LIMIT = 8         # 同一 IP 5 分钟内最多失败 8 次
```

命中后返回 429，提示「尝试过于频繁，请 5 分钟后再试」。

**注意两点**：

- 计数只统计**失败**，成功要清零——否则正常用户换设备登录几次就被锁
- 按 IP 而不是按用户名。按用户名限流反而给了攻击者**锁死他人账号**的手段

**量**：约 40 行 + 5 条测试。

---

### B-2 令牌无法吊销 🔴

**现状**：`app/auth.py` 是无状态 HMAC 令牌，有效期 7 天。这意味着
**用户改完密码、管理员禁用账号之后，旧令牌照样能用满 7 天**。

**做法**（保持无状态的优点，只加一个失效基线）：

1. `User` 表加一列 `token_valid_after: DateTime`
2. 改密码、禁用账号、用户主动「退出所有设备」时，把它设为当前时间
3. `current_user()` 校验时比对：令牌签发时间早于这个基线 → 视为无效

比维护一张黑名单表轻，也不需要每次请求查缓存——`current_user` 本来就要查 `User`。

**注意**：令牌 payload 里现在没有签发时间，需要加 `iat` 字段。
加了之后**旧令牌全部失效**，属于预期行为，但要在发版说明里写清楚。

**量**：约 50 行 + 6 条测试。

---

### B-3 预约在并发下会双重占用 🟠

**现状**：`create_appointment` 是「先查有没有冲突，再插入」。两个请求同时
通过检查、同时插入，两条都会成功。

**为什么当初没加唯一约束**：`models.py` 里有一段注释解释过——
`UNIQUE(house_id, viewing_time)` 既太严（取消掉的预约会永久占住时段），
又太松（管不了「一次看房占用一小时」的重叠判断）。这个判断至今成立。

**做法**：不用唯一约束，改用**行级锁**。查询冲突时对该房源加锁：

```python
session.execute(select(House).where(House.id == house.id).with_for_update())
```

后来的请求会阻塞到前一个提交完，再查冲突时就能看到那条记录。

**限制要写清楚**：SQLite 不支持 `SELECT FOR UPDATE`（它是库级写锁，反而天然
不会出这个问题）。这行在 MySQL 上才真正生效——**这正是「本地 SQLite、
部署 MySQL」这个架构选择需要付出的代价之一**，答辩时值得说。

**量**：约 15 行 + 一条并发测试。

### B-4 连接池只有 15 条，100 并发直接垮 ✅ 已完成

**实测**（`scripts/bench.py`，2026-09-03）：

| 并发 | 结果 |
|---|---|
| 30 | 全部成功，中位 36–288ms |
| 60 | 全部成功，中位 217ms |
| **100** | **成功 1–11/100，中位 20–30 秒** |

不是某个接口的问题，匿名的 `GET /api/houses` 一样垮。

**根因**：`server/app/db.py:24` 用了 `create_engine` 的默认连接池——
`pool_size=5` + `max_overflow=10` = **上限 15 条连接**，`pool_timeout=30s`。
100 个并发请求里 85 个排队等满 30 秒后失败。30004ms 这个数字与
SQLAlchemy 的默认超时严丝合缝，是决定性证据。

**需求 N-01 写的是「传统 CRUD 接口响应时间 < 1s（100 并发）」，所以这条不达标。**

**做法**：

```python
engine = create_engine(
    DATABASE_URL, connect_args=_connect_args, future=True,
    pool_size=20, max_overflow=40, pool_timeout=5, pool_pre_ping=True)
```

- `pool_timeout` 从 30 秒降到 5 秒：**排队 30 秒才失败是最糟的结果**，
  用户早走了、连接还占着。快速失败反而更健康
- `pool_pre_ping` 防止 MySQL 掐掉空闲连接后拿到死连接

**注意**：SQLite 是单写锁，调大连接池对写操作帮助有限，读操作会明显改善。
真正的解法是部署到 MySQL，这也是架构里早就留好的开关（`DATABASE_URL`）。

**量**：3 行 + 重跑 `scripts/bench.py` 验证。

**实际做完的结果**（2026-09-03）：连接池调整后 6 项里 5 项达标，
只剩 `/api/stats` 仍是 1114ms。查下来它是另一个问题——
把五张表全量拉进内存再用 Python 循环聚合，100 并发就是 100 次全表扫描。
改成 COUNT / SUM / GROUP BY 下推到数据库后降到 **285ms**，
**N-01 六项全部达标**。

改写聚合最大的风险是「快而算错」，所以补了一组对照测试：
同一份数据用 SQL 聚合与逐行统计各算一遍，结果必须完全一致。
其中逾期判定尤其要盯——`Bill.overdue` 是 Python 属性，SQL 里得重写一遍，
两处只改一处就会悄悄对不上。

## C 档 · 真实系统必备的新增功能

### C-1 租客与房东之间没有任何对话通道 🔴

**这是本次核查发现的最大功能缺口。**

系统里 AI 对话有两套（AI-09 助手、AI-03 客服），但**人与人之间不能聊**。
现有的人际沟通只有三个孤立触点，每个都只能来回一次：

| 触点 | 形态 |
|---|---|
| 预约 `remark` → `reply` | 租客留一句、房东回一句，完了 |
| 转人工 `question` → `reply` | 用户问一句、管理员答一句，完了 |
| 站内信 `Message` | **单向通知**：只有 `user_id` 收件人、没有发件人，回不了 |

租客看中一套房，想问「能不能养猫」「几月能入住」「押一付一行不行」——
没有地方问。只能约看房时当面问，或者根本不问就走了。
真实平台（贝壳、自如）里 IM 是转化率最高的一环。

#### 四个设计决策

**① 会话锚定在房源上，不是锚定在人上**

不做通讯录式的「给某人发消息」，而是 **每套房源 + 每个租客 = 一个会话**：

- 租客同时看十套房，问的都是「能养猫吗」，按人聚合会混成一团
- 房东手里二十套房，需要一眼知道对方问的是哪套
- 会话天然带上下文，进来就显示房源卡片，双方不用先对暗号

数据上就是 `UNIQUE(house_id, tenant_id)`。

**② 新建表，不复用 `Message`**

`Message` 是**通知**——只有收件人、没有发件人、不成串、读完即弃。
硬套上会话语义会把两件事都做坏：通知要的是「未读数清零」，
会话要的是「对方读到哪了」，这是不同的东西。

但两者要**联动**：收到新消息时用现成的 `leasing.notify()` 往 `Message`
写一条通知，用户在消息中心也能看到红点。

**③ 用轮询，不用 WebSocket**

WebSocket 在这个项目里性价比很低：要改部署形态（单 worker 撑不住长连接）、
要处理断线重连、要做在线状态。改用**轮询**——面板打开时每 10 秒拉一次增量
（`after_id` 参数），关掉就停。

租房不是即时通讯，对方隔十分钟回复是常态。
**答辩时这句话值得讲**：我们评估过 WebSocket，但它的部署复杂度与本场景的
实时性收益不匹配。

**④ 联系方式必须拦**

这是最容易忽略、却最该做的一条。平台上线后第一件事就是有人在聊天里
发微信号绕过平台，或者骗子发链接。

项目里**已经有 M-08 内容审核模块**（`server/app/moderation.py`），
`check(text, scene)` 直接可用：

- 确定违规（微信号、手机号、外链）→ **拒发**，提示
  「为保障双方权益，请在平台内沟通」
- 存疑 → 放行但进人工复核队列

这既是业务需要，也正好把 M-08 从「只审房源和评价」扩展到真正高发的场景。

#### 数据模型

```python
class Conversation(Base):
    """租客与房东围绕某套房源的会话。

    会话锚定在「房源 + 租客」上而不是「人」上：租客同时看十套房，
    问的都是「能养猫吗」，按人聚合会混成一团；房东手里二十套房，
    也需要一眼知道对方问的是哪套。
    """
    __tablename__ = "conversations"
    __table_args__ = (UniqueConstraint("house_id", "tenant_id"),)

    id, house_id(FK), tenant_id(FK), landlord_id(FK)
    last_message: String(100)   # 冗余最后一句，列表页不用再查明细表
    last_at: DateTime           # 排序用
    tenant_unread: Integer      # 各存各的——同一条消息对双方含义不同
    landlord_unread: Integer
    status: String(20)          # active / archived
    created_at: DateTime


class ChatLine(Base):
    """会话里的一条消息。"""
    __tablename__ = "chat_lines"

    id, conversation_id(FK, index), sender_id(FK)
    content: Text
    kind: String(10) = "text"   # 未来发图/发房源卡片靠它区分，先只做 text
    created_at: DateTime
```

两个点值得在答辩时说：

- **`last_message` 与未读数是刻意冗余的**。会话列表要显示「最后一句 + 未读数」，
  不冗余就得对每个会话再查一次明细——十个会话十次查询。
  代价是写入时要同步更新，收益是列表页一次查询搞定。
- **未读数必须分两个字段**。同一条消息，对发送方是已读、对接收方是未读。

#### 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| `POST` | `/api/conversations` | 开启会话（**幂等**：已存在就返回原有的） |
| `GET` | `/api/conversations` | 我的会话列表，按 `last_at` 倒序 |
| `GET` | `/api/conversations/{id}/lines` | 消息明细，支持 `after_id` 增量拉取 |
| `POST` | `/api/conversations/{id}/lines` | 发一条，**先过内容审核** |
| `POST` | `/api/conversations/{id}/read` | 标记已读，未读数清零 |

**权限是这里最容易出错的地方**：每个接口都必须校验「调用者是这个会话的
tenant 或 landlord」。少一处，改个 id 就能读别人的私聊——
这类漏洞本项目**已经修过两次**（报修接口 `GET /api/repairs`、
对话记录接口 `GET /api/chat-messages`），是同一类错误，务必逐个接口写测试。

#### 界面

- **入口**：房源详情页加「咨询房东」按钮，放在「预约看房」旁边。
  这是唯一自然的入口——用户正在看这套房时才会想问
- **租客侧**：个人中心加「咨询」标签，左侧会话列表（房源封面 + 最后一句 +
  未读红点），右侧消息流
- **房东侧**：工作台加「咨询」标签带未读角标。房东最关心「谁在问我哪套房」，
  列表项要显著显示房源编号

| 部分 | 量 |
|---|---|
| 两张表 + 五个接口 + 权限校验 | 约 200 行 |
| 内容审核接入 | 约 20 行（复用现成的） |
| 前端会话面板（两侧共用一个组件） | 约 250 行 |
| 测试（越权、审核拦截、幂等、未读数） | 约 25 条 |

**合计半天到一天。**

### C-2 通知只有站内信 🟠

没有短信、没有邮件、没有微信推送。**租金到期不发短信 = 没催过；
看房前一小时不提醒 = 大概率放鸽子。** 真实系统里短信触达是运营命脉。

**做法**：抽一层 `notifier` 接口，实现三个通道：

```python
class Notifier:
    def send(self, user, template, params): ...

# 站内信（已有）→ InAppNotifier
# 邮件 → SmtpNotifier（标准库 smtplib，零新增依赖）
# 短信 → SmsNotifier（需要第三方账号，见 D 档）
```

**建议做到邮件为止**。邮件用标准库就能发，能演示完整链路；
短信需要实名认证的服务商账号，属于 D 档。

**量**：抽象层 + 邮件实现约 80 行。

---

### C-3 前端没有路由 🟠

**现状**：整站一个 URL，`react-router` 都没装。后果：

- 房源详情**分享不出去**——发给朋友只能打开首页
- 浏览器前进/后退不可用
- 刷新回到首页，正在填的表单没了
- 搜索引擎收录不到任何房源（真实平台的主要获客渠道）

**做法**：装 `react-router-dom`，至少做三条路由：

```
/                    首页
/house/:houseNo      房源详情（当前是抽屉，改成可深链的抽屉）
/me/:tab             个人中心各标签
```

**注意**：抽屉式交互不必推翻——`react-router` 可以只负责同步 URL，
打开抽屉时 `pushState`，关闭时 `back`。改动比想象中小。

**量**：约 120 行。

### C-4 工单没有 SLA 与超时升级 🟡

报修判定为「紧急」之后就没有下文了——没人处理也不会催。

**做法**：`SystemConfig` 加两项（紧急工单 N 小时、一般工单 M 小时），
后台定时任务扫描超时未处理的工单，给房东发通知、给管理员进待办。

M-09 系统配置已经支持「配置真的生效」的模式，接进去即可。

**量**：约 60 行 + 一个定时任务入口。

---

### C-5 六处硬删除，数据删了就没了 🟡

`server/app/main.py` 里有 6 处 `session.delete()`。真实系统里租赁数据
涉及纠纷取证，删除必须可追溯。

**做法**：涉及业务实体的（房源、合同、工单）改为软删除——加
`deleted_at` 字段，查询时过滤。纯个人数据（收藏、足迹）可以保留硬删除。

**量**：约 80 行。

## D 档 · 受客观条件限制做不了

**这一档不是「没做完」，是学生拿不到相应资质。答辩时主动讲出边界，
比被问出来强得多，而且能顺势说明「能做实的部分我们都做实了」。**

### D-1 钱是假的

`server/app/leasing.py:230` 的 `pay_bill()` 直接把 `status` 改成 `paid`，
没有任何支付网关。真实系统这块最重：

- 接支付宝/微信支付，处理**异步回调**（`notify_url`），而不是前端点一下就算付了
- 回调**幂等**——支付宝会重复推送同一笔，处理两次就多记一笔流水
- 每日对账文件核对
- 退款链路（现在押金退还只是改个数字）
- **资金监管**：多地住建部门强制要求租金进监管账户，不能直接进平台账户

**拿不到的**：支付牌照 / 商户号（需要企业营业执照）。

**可以做的替代**：把 `pay_bill` 重构成「发起支付 → 等待回调 → 确认到账」
三段式，用一个假的回调接口模拟。**结构对了，将来换成真网关只改一个适配器**。
这个改造本身就是可以讲的设计。

### D-2 合同没有法律效力

现在生成的是一段纯文本，双方点一下按钮就"生效"。真实合同需要：

- **电子签章**（CA 数字证书 + 可信时间戳），否则出纠纷法院不认
- 签署过程留痕（IP、设备、意愿确认）
- 第三方存证

**拿不到的**：CA 机构签发的数字证书。

### D-3 实名认证只是格式校验

`server/app/idcard.py` 校验的是**校验位算法**——能挡住手滑打错，
但**编一个校验位正确的号码照样能过**。

真实系统必须对接公安部人口库做二/三要素核验 + 活体检测 + 证件 OCR，
确保"人证合一"。

**拿不到的**：公安核验接口（需企业资质与备案）。

### D-4 房源没有核验

任何人注册成房东就能发房源。真实平台（尤其北京、深圳）要求上传
不动产权证、与登记数据核验、生成**房源核验码**，未核验不得展示。
这是防虚假房源的核心，也是监管硬性要求。

**拿不到的**：不动产登记数据接口。

**可以做的替代**：加一个「证件上传 + 管理员人工核验」流程，
把状态机做出来（未核验 / 待核验 / 已核验 / 核验失败），
真实系统里也需要这套状态机，只是核验方从人变成接口。

### D-5 运维能力

- 无监控告警（服务挂了没人知道）、无错误聚合（Sentry 类）
- 无备份策略（SQLite 单文件，误删就没了）
- 单进程部署，崩了不自动重启

**受限于**：没有服务器与运维预算。可以在文档里写出部署方案
（多 worker + 进程守护 + 定时备份），作为"设计已考虑"的证据。
