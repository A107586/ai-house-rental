### K-01 退租弹窗点「取消」也会真的退租 ✅ 已完成

**问题**（报告 4.6）：`web/src/components/ContractCard.jsx:71-81` 用
`window.prompt` 收扣款金额，用户点「取消」时返回 `null`，
`null || 0` 得到 `0`，`Number.isNaN(0)` 为假，代码继续往下走把租约退掉。
一个本意是「我再想想」的操作直接结束了合同，且不可撤销。

**做法**：换成组件内的正式弹窗（`EndLeaseDialog`），
出租方填扣款金额、双方都填退租原因，点「确认退租」才发请求；
点「取消」或按 Esc 一律不发请求。弹窗里写清「此操作不可撤销」。

**验收**
- 房东点「退租」→ 弹窗点「取消」→ 合同状态**保持 active**，无任何网络请求
- 扣款金额填非数字或负数 → 就地报错，不发请求
- 扣款金额大于押金 → 后端已有校验，前端把错误显示在弹窗里而不是关掉弹窗
- 租客侧退租不出现扣款输入框

**改动**
- 新增 `web/src/components/EndLeaseDialog.jsx`：取消 / 叉 / Esc 三条路径一律不发请求；
  金额校验在提交前完成；请求失败时弹窗不关，用户填的内容不丢；
  当场摊开「押金 − 扣款 = 预计退还」三行结算。
- `web/src/components/ContractCard.jsx`：删掉 `window.prompt`，
  `endLease()` 改为只在弹窗按下「确认退租」时才发请求。
- `web/src/styles.css`：新增 `.settle` 结算行样式。
- 这条是纯前端改动，回归靠手工用例（见上「验收」），没有自动化测试。

### K-02 押金：房源上填的和合同上签的是两个数 ✅ 已完成

**问题**（报告 4.4）：房东发布时填的 `houses.deposit` 是详情页展示的数
（`HouseDrawer.jsx:235`），但 `server/app/leasing.py:84` 签约时算的是
`rent * deposit_months`，`deposit_months` 来自系统配置默认值，
**完全没读 `house.deposit`**。房东填 800，合同上签的是另一个数。

**做法**：`create_contract()` 的押金口径改为——
签约方**显式传** `deposit_months` 时按月数算（房东主动选了「押二付一」）；
**没传**时以 `house.deposit` 为准；`house.deposit` 也为空才回落到系统配置。
合同正文、押金账单、退租结算全部走同一个数。

**验收**
- 房东发布填押金 800 → 发起签约不传 `deposit_months` → 合同押金 = 800，
  正文里「押金人民币 800 元」，押金账单 800，详情页展示一致
- 显式传 `deposit_months=2` → 合同押金 = 租金 × 2，覆盖房源上的值
- 房源押金为 0 且未传月数 → 回落到系统配置 `deposit_months`
- 免押（显式传 `deposit_months=0`）不能被当成「没填」而回落到房源押金

**改动**
- `server/app/leasing.py`：新增 `resolve_deposit()`，**押金从此只有这一处口径**；
  `create_contract()` 的 `deposit_months` 默认值由 `1` 改为 `None`
  （`1` 表示「明确押一」，`None` 表示「没指定」，用 `1` 当默认就分不开这两件事）；
  `renew_contract()` 不再写死押一，续租押金跟房源走。
- `server/app/main.py`：不再在接口层把 `None` 替换成配置值，
  原样传给 `resolve_deposit` 裁决。
- `web/src/components/SignContractDialog.jsx`：押金月数输入框提示改为
  「留空按房源押金」，并在助手条里直接显示房源上填的押金。
- 回归测试：`server/tests/test_contract_terms.py::TestDepositMatchesListing`
  与 `::TestDepositThroughApi`（9 条）。

### K-03 合同乙方姓名退化成登录名 ✅ 已完成

**问题**（报告 4.5）：`server/app/leasing.py:136` 是
`tenant.real_name or tenant.username`，租客没填实名时合同上的承租方
写的是 `tenant1` 这种登录名。法律文本上出现登录名很扎眼，答辩演示尤其。

**做法**：签约前校验租客已实名，未实名直接拒绝并提示去
「个人中心 → 编辑资料」补；同时甲方（房东）也一并校验。
`render_contract_text()` 里的 `or username` 兜底去掉——
到这一步双方姓名一定有值，留着反而掩盖问题。

**验收**
- 用未填 `real_name` 的租客发起签约 → 409，提示「租客尚未实名…」，不生成合同
- 房东自己未实名 → 同样拒绝，提示补自己的资料
- 双方都实名 → 合同正文甲乙双方均为真实姓名
- 只填空格不算实名
- 拒绝签约时不能留下半份合同

**改动**
- `server/app/leasing.py`：`create_contract()` 在生成之前校验甲乙双方实名，
  未实名抛 `ValueError`（接口层转 409）；`render_contract_text()` 去掉
  `or username` / `or "房东"` 兜底——留着只会把「没实名」藏进一份看起来
  正常的合同里。
- 提示语写明「个人中心 → 编辑资料」，只说「未实名」用户没法照着做。
- 回归测试：`server/tests/test_contract_terms.py::TestPartiesMustBeNamed`
  与 `::TestUnnamedTenantRejectedByApi`（6 条）。

### K-05 高级筛选 ✅ 已完成

朝向、楼层区间、电梯、装修、租期、可入住日接进 `list_houses()` 与
`FilterBar.jsx`。数据在库里，纯接线工作。

**验收**：电梯 + 南向 + 中楼层组合后结果同时满足全部硬条件；
页面显示已生效条件数；「无电梯」不会被「有电梯」命中。

**改动**
- `server/app/main.py`：`list_houses()` 新增 7 个筛选参数
  （`orientation` / `floor_level` / `elevator` / `decoration` / `heating` /
  `lease_term` / `available_days`）；关键词检索扩到 `address` 与
  `business_area`——找房的人打的是「桂林街」，而地名往往只在地址里。
- `web/src/components/FilterBar.jsx`：新增六组条件，收在「更多筛选」里。
  一次摊开十一组，手机上要滚三屏才看得到房源列表；收起时若里面有
  生效条件会在按钮上标数字，否则用户看不见自己设过什么。
- 回归测试：`server/tests/test_house_filters.py`（21 条）。

**三个刻意的设计选择**
- **电梯做成三态**（不限/有/无），不是一个「有电梯」开关。
  做成开关，「我要找没电梯的便宜房」就表达不出来，而这是真实需求。
- **低/中/高楼层按三等分算**，不写死层数阈值。6 层老楼的第 5 层是高楼层，
  33 层塔楼的第 5 层是低楼层，固定阈值对不上这两种情况。
  楼层信息不全的房源不参与这个筛选——猜不了，也不该猜。
- **「三月内起租」包含「一月起租」**。用户点这档是在问「最短能租多久」，
  一个月起租的房源当然满足；排掉它就是把筛选做成了等值匹配。
  「年租起」方向相反，问的是「房东要求至少租一年」。

**测试为什么逐条核对而不是只数数量**：这个筛选曾经是**错的**，不是缺的
——`tags LIKE '%电梯%'` 会把「无电梯」也命中。只断言「返回了几套」
测不出那个 bug，所以每条用例都要核对返回的每一套房是否真的满足条件。

### K-06 普通搜索框 + AI 条件回填 + 可叠加 ✅ 已完成

**问题**（报告 4.2、4.3）：`/api/houses` 支持 `keyword` 但前端从不传，
全站唯一找房入口是 AI 输入框——**AI 一挂整站搜不了房**；
且 `App.jsx:211` 里用筛选器会清空 AI 结果，两者互斥。

**做法**：AI 只负责「把人话翻译成筛选条件」，翻译结果**回填到筛选栏**，
之后统一走 `/api/houses` 一条检索路径。顶部常驻关键词输入框。

**验收**：搜索框输入「桂林街」返回匹配房源，**智能体停掉也能用**；
AI 搜完再点「有电梯」结果同时满足全部条件，筛选栏高亮显示 AI 识别的条件。

**改动**
- `agent/app/main.py`：新增 `POST /agent/parse`——**只解析，不取数**。
  返回 `filters` / `features` / `source` / `divergence`。
- `agent/.../search_properties.py`：设施偏好改为交给后端筛。
  原先是把候选集整个翻完再在本地比子串（一次找房打好几趟后端，
  而且「无电梯」里含「电梯」，要电梯的人会被推一套没电梯的房）。
  随之删掉 `score_by_features` / `matches_all_features` 两个函数。
- `server/app/main.py`：`/api/houses` 新增 `features` 参数，
  已升格成列的（电梯/精装/集中供暖）比列，其余按**整词**匹配标签。
- `web/src/components/ActiveFilters.jsx`（新）：无论条件来自智能体、
  筛选栏还是搜索框，都在这里如实列出，每一条都能删。
- `web/src/App.jsx`：智能找房改为「解析 → 回填 filters → 走 /api/houses」；
  新增常驻关键词搜索框；删掉筛选与 AI 结果互斥的全部逻辑
  （`!result &&` 的门、另一条翻页路径、另一份房源列表）。
- 回归测试：`agent/tests/test_parse_endpoint.py`（8 条）、
  `server/tests/test_house_filters.py::TestFeatureFilter`（7 条）。

**浏览器实测确认的四件事**
1. 一句话 →「已生效条件 4」：区域中山区 / 租价 ≤3000 / 两室一厅 / 电梯，共 2 套；
2. 在此基础上点「中楼层」→ 条件变 5 条，**原有条件一条不丢**；
3. 逐条删 chip 生效，设施 chip 也能单独删；
4. **停掉智能体**后：关键词搜「桂林街」正常返回 2 套；点智能找房给出
   「智能体暂时联系不上，可以直接用上面的搜索框或下面的筛选条件找房」，
   房源列表和已有条件都不清空，筛选栏照常可用。

**顺手修掉的一个新 bug**（浏览器实测发现，不是推理出来的）
智能体解析出的「租价 ≤ 3000」落不进筛选栏的固定档位（2500–3500、
3500–5000…），此时 `priceIndex = -1`。再点任何一个筛选按钮，
`apply()` 会按 -1 发出空的价格区间，**把「三千以内」这一条抹掉**——
正是 K-06 要消灭的那种「一操作就丢条件」。`FilterBar` 现在把档位
表达不了的自定义区间单独记着，原样带走；只有用户亲手点了价格档位
才作废它。

用户刚用「有电梯」筛完，点进详情却看不到这一条，说不过去。
归到「卡片与详情信息密度」一并做（第三梯队）。

### K-08 用户举报入口 ✅ 已完成

`POST /api/reports` + 详情页按钮 + 管理员处理列表。
`ContentFlag` 是机器审核用的，用户举报走新的 `house_reports`，两者分开。

**验收**：未登录点举报先要求登录；提交后管理员可见可处理，结果通知举报人。

**改动**
- `server/app/routers/reports.py`（新）：5 个接口——提交、我的举报、
  管理员列表、处理、举报类型清单。
- `server/app/oplog.py`：补两条动作名，处理举报会以「处理房源举报」
  记进操作日志（中间件自动记，不用在业务里写）。
- `web/src/components/ReportDialog.jsx`（新）：详情页举报弹窗。
- `web/src/components/HouseReportPanel.jsx`（新）：管理端「举报处理」。
  与「内容审核」分成两个面板——那边是机器拦下的内容，只需判断留或删；
  这边有举报人、要给结论、结论要通知回去。
- `web/src/components/HouseDrawer.jsx` / `AdminPanel.jsx`：各两行接线。
- 回归测试：`server/tests/test_reports.py`（20 条）。

**四个设计决定**
- **必须登录**。匿名举报既没法给回执，也挡不住刷单。
- **同一人对同一房只留一条待处理举报**。不拦的话连点五次就把管理员的
  待办刷满，真正要看的举报反而被埋掉；上一条处理完可以再报。
- **处理时必须填结论**，前端就地拦下空结论。「已处理」三个字对举报人
  毫无意义——这条通知就是整个机制的闭环，也是他下次还愿不愿意举报的依据。
- **判定 ≠ 处置**：判「属实」不会自动下架房源。绑死的话，管理员为了
  下架一套信息过期的房源，就得把它判成「虚假房源」，房东从此背着一条
  假房源记录。要下架去「房源审核」做，界面上也写明了这一句。

**浏览器实测**：租客提交（单号 JB260903C75015）→ 管理端「举报处理」
待处理 1 → 不填结论点「判定属实」被就地拦下 → 填结论后处理成功 →
租客站内消息收到「举报处理结果：举报属实 | …」，「我的举报」里状态与
结论一致。

### K-09 保存搜索 + 上新提醒 ✅ 已完成

保存筛选组合并命名；新房源审核通过时匹配已保存条件，
复用站内消息发提醒，同一房源只提醒一次。

**改动**
- `server/app/house_query.py`（新）：**筛选条件构造全站只此一处**。
  列表接口和上新匹配共用它——两份实现一旦分叉，表现是最难查的那种：
  用户存的条件在列表页筛得到这套房、上新提醒却不发，或者反过来。
  `list_houses()` 里那一长串手写条件同步删掉了。
- `server/app/routers/saved_search.py`（新）：增删改查 + `notify_new_house()`。
- `web/src/components/SavedSearchPanel.jsx`（新）+ 个人中心「我的搜索」页签；

- 回归测试：`server/tests/test_saved_search.py`（16 条），其中
  `TestMatchingAgreesWithListing` 用 9 组条件逐一比对
  「列表页筛不筛得到」与「上新匹不匹配」，是那条共用约定的看门狗。

**四条规则**
- 上架那一刻才是「上新」——发布时房源还是 pending、对外不可见，
  那时通知等于让用户去看一套他点不开的房；
- 同一套房对同一条搜索只提醒一次，房源下架再上架不重发；
- 不给房东自己发他刚发布的房；
- 提醒可关不可丢：关掉提醒但保留条件，只给「删除」等于逼他把条件也丢掉。

**实测**：设「中山区 + 有电梯」→ 保存（自动命名「中山区 · 有电梯」）→
房东发一套匹配房源、管理员审核通过 → 租客收到
「有新房源符合「中山区 · 有电梯」」→ 在「我的搜索」里一键恢复条件，
结果由 7 套变 8 套（多的正是刚上架那套）。

### K-10 智能体提速 ✅ 已完成（短路**默认开启**，见下）

**改动**
- `agent/app/fusion.py`：`fuse()` 支持按规则置信度短路。
- `agent/app/config.py`：`LLM_TIMEOUT` 默认 **30s → 8s**；
  新增开关 `FUSION_SKIP_WHEN_CONFIDENT`，**默认 true**（团队 9/04 决定）。
- `web/src/App.jsx` + `styles.css`：解析中先摆骨架屏。
- 回归测试：`agent/tests/test_fusion_shortcut.py`（9 条）。

**关于「默认开启」这个决定**

报告里把「规则置信度高就跳过大模型」列为提速第一手。真做下去发现它
**推翻的是 `fusion.py` 开头那段刻意的设计决定**：融合的立场是
「规则与大模型同时参与」，理由写得很清楚——规则再全也覆盖不了所有说法，
置信度高只说明规则**认得出**，不等于它**认得对**。所以最初做成开关、
默认关闭，把取舍留给团队。**9/04 团队决定默认开启。**

要清楚它换来什么、又付出什么：

- **换来**：规则能确定的那类查询（「中山区两室一厅三千以内」这种
  占绝大多数）不再多付一趟大模型往返；
- **付出**：那类查询里「规则认得出但认错了、本可由大模型纠正」的情况，
  从此不会被纠正。

觉得漏判变多时，**先调高 `RULE_CONFIDENCE_THRESHOLD`**（让「多确定才算
确定」更严），而不是整个关掉；确实要对照老行为时再置
`FUSION_SKIP_WHEN_CONFIDENT=false`，比如跑 AI-01 验收指标做 A/B。

一个现实提醒：项目目前**没有配 `LLM_PROVIDER`**，全程纯规则模式，
这个开关此刻不产生任何可观测差异。它的影响要等真接上 DeepSeek 才显现，
届时建议用 `test_acceptance.py` 的 AI-01 准确率跑一次开/关对照。

**超时从 30 秒降到 8 秒是无条件改的**，它不涉及这个取舍：
降级路径是完整可用的，没有理由为了「说不定第 29 秒能回来」让人干等着。

注意：不配 `LLM_PROVIDER` 时本来就是纯规则模式，这两项都只影响
「配了大模型」的那条路径。

### K-11 找回密码 ✅ 已完成

邮箱收一次性重置链接，复用已有的邮件通道，零新增依赖。

**改动**
- `server/app/routers/password_reset.py`（新）：`/api/auth/forgot`、`/api/auth/reset`。
- `server/app/ratelimit.py`：新增**带命名空间的尝试限流** `hit()`。
- `web/src/components/ForgotPasswordForm.jsx`（新），接进登录弹窗。

**三条安全约束**
- **不透露账号是否存在**：存在与不存在返回同一句话，且不存在时
  不真的建记录。区别对待的话，这个接口就成了免费的「账号是否注册」
  查询器——撞库的第一步正是筛出哪些账号真实存在。
- **只存令牌哈希**，原文只在那封邮件里。库被读到也不能拿它去改密码。
- **重置即吊销全部旧令牌**，并把该用户其余未使用的链接一并作废——
  邮箱里那几封旧邮件仍然是活的钥匙。

**一个自己写出来又被测试抓到的 bug**：最初复用了登录那套限流，
但它统计的是**失败**次数、且「登录成功即清零」——攻击者只要登录一下
自己的账号就能把找回密码的计数抹掉，限流形同虚设。
所以另开了一份带命名空间的尝试计数。

### K-13 租客升级为房东 ✅ 已完成

保留单 `role`，个人中心加「我也要出租房子」入口。

**改动**
- `server/app/routers/account.py`（新）：`become-landlord` +
  `landlord-eligibility`（点之前就告诉用户还差什么，而不是点完弹错误）。
- `web/src/components/BecomeLandlord.jsx`（新），接进「账号设置」。
- 回归测试：`server/tests/test_become_landlord.py`（15 条）。

**做的是单向升级，不是多角色。** 改成多角色会牵动全站每一处
`require_staff` 和前端的 `role === 'landlord'` 判断，风险远大于收益。
也**不提供反向降级**：名下有房源和合同的账号降回租客，那些数据就没有
主人了；真要退出出租业务该走「下架房源 + 结清合同」，不是一个开关。

**测试抓出了一个真 bug（这一项最大的收获）**

写「升级不能丢数据」的用例时发现：升级后**升级前签的租约当场消失**。
数据没丢，是查询把它挡住了——`/api/contracts/mine` 按角色二选一：
role 是 landlord 就只查「我出租的」。同样的写法还在
`/api/bills/mine`、`/api/appointments/mine`、`/api/refunds/mine`。

四处一并改成按「**我是不是其中一方**」判断，与 role 无关。
这不只是为了 K-13——「房东自己也租房」本来就该支持，
原来的写法在那种情况下同样是错的。

**实测**：租客升级后 role 变 landlord，2 条收藏、4 份合同一条不少
（改之前这里会是 0）。
