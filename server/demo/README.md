# 标准演示数据库

`rental_demo.db` 是一份可以直接拿来跑的演示数据快照。

```bash
cd server
python restore_demo.py        # 把它装回 rental.db
python -m uvicorn app.main:app --host 127.0.0.1 --port 8080
```

装回去之后，`admin / admin123`、`landlord1 / test123`、`tenant1 / test123`、
`agent1 / test123` 立刻可用，房源、合同、账单、评价都是齐的。

## 为什么要有它（`seed.py` 不是已经能生成了吗）

`seed.py` 里有 `random.seed(20260901)`，同一份代码在任何机器上生成的
数据都一样——**所以这份快照不是为了「数据一致」**，它解决的是另外三件事：

**一、答辩现场不用等播种，也不用赌它能跑通。** 播种要连着建表、写入、
生成账单，几十秒起步；真在台上报错了，现场没人来得及查。

**二、给「改坏了」留一条回头路。** 这一条是被咬过才加的：清理测试数据时
一个 `HT26091%` 的前缀匹配，把种子数据里的合同一起删了 129 份。
当时只能重新播种，而重新播种会连手动注册的测试账号一起抹掉。
现在 `python restore_demo.py` 就能回到已知良好的状态。

**三、文档和截图有一个对得上的基准。** 需求跟踪矩阵里的界面截图、
日志里引用的数字（「95 套在架」「33 笔待缴」），都出自这一份数据。
`seed.py` 一改，那些数字就对不上了，而快照还在。

## 两个真相源的风险，和怎么对账

快照和 `seed.py` 是两份可能漂移的东西。`manifest.json` 里记着生成这份
快照时 `seed.py` 的哈希：

```bash
cd server
python -c "import hashlib,io;print(hashlib.sha256(io.open('seed.py','rb').read()).hexdigest()[:16])"
```

对不上，说明 `seed.py` 改过而快照没跟着更新。**这不一定是错**——
快照本来就该停在某个版本上；但如果改的是演示要用到的数据，就该重做一份：

```bash
cd server
python seed.py
python demo/snapshot.py
```

## 里面有什么

| 表 | 条数 |
|---|--:|
| 用户 | 14（管理员 1、房东 8、租客 4、中介 1） |
| 房源 | 108 |
| 房源图片 | 324 |
| 合同 | 113（生效 6、已结束 106、待确认 1） |
| 账单 | 78（待缴 40，其中**逾期 1 笔**） |
| 评价 | 105（覆盖 69% 的房源，2–5 星都有） |
| 预约 | 15 |
| 报修 | 6 |
| 支付 | 38 |
| 知识条目 | 70 |
| 客服问答日志 | 67（答出 52、拒答 15） |

**评价刻意只覆盖 69%**：剩下三成房源没有评价，「暂无评分」这条分支
才走得到。全部铺满的话，那段代码坏了也没人发现。

**客服日志也是刻意铺的**：管理后台「智能客服 · 质量分析」整块——
答出率、拒答率、响应中位数、知识缺口清单、最常被引用与从未被引用的
条目——**全靠这张表算**。表空着的时候那一页只剩一句「0 次」，
70 条知识全列在「从未被引用」里，看不出它坏没坏，也看不出它好在哪。

拒答的那几条是**故意重复问**的：知识缺口按出现次数排序，
问一次看不出是缺口，问五次才是。反馈只留两条「没用」——
真实世界里点评价的人本来就少，铺满了那张清单就失去筛选意义。

**逾期刻意只留一笔**，就是本月这一笔：全缴清的话「逾期未缴」那一整条
分支（红色角标、催缴提醒、`faq-bill-late`）没东西可演；而「这个月的房租
还没交」本来就是最常见的情形，不必靠一笔欠了十四个月的陈账来制造。

两份已结束的历史合同原先建完直接 end 掉、没人缴费，25 笔账单从
2025 年 7 月一路欠到现在——演示账号 tenant1 打开「我的账单」看到的是
「34 笔待缴，合计 44200 元」。**「租期届满，正常退租」和「一年房租一分
没交」不能同时成立**，现在结束前一律结清。

合同里 106 份是历史租约（已结束），它们**不带账单**——四十份历史合同
会排出四百多条早已付清的账单，把「我的账单」冲得没法看，
而那些账单对演示没有任何价值。
