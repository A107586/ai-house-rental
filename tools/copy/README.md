# 文案抽取与回写

`docs/前端文案清单_2026-09-12.md` 是这三个脚本生成的。改文案的流程：

```
extract_copy.py   代码 → copy_rows.json（抽出所有面向用户的中文）
render_copy.py    copy_rows.json → 清单 Markdown（人在这里填「改为」）
apply_copy.py     清单 → 代码（按 #序号 写回）
```

```bash
cd tools/copy
python extract_copy.py      # 重新抽一遍（代码改动后）
python render_copy.py       # 重新生成清单
python apply_copy.py --dry  # 看一遍要改什么
python apply_copy.py        # 真的写回去
```

**`--dry` 不是可选步骤。** 这个脚本会直接改源码，而它依赖的行号和原文
可能已经过时——先看一眼要改的是不是你以为的那几处。

## 为什么不用 grep

grep 会把注释一起抓出来。这个项目的注释密度很高而且全是中文，
grep 的结果里十句有七句是写给我们自己看的。所以 `extract_copy.py` 里
写了个逐字符的小状态机，知道自己此刻在代码里、在哪种引号里、还是在注释里。

两个正则绕不过去的坑：`'https://…'` 里的 `//` 不是注释开头；
模板串 `` `共 ${n} 套` `` 里能嵌任意表达式，里面还能再套字符串。

## 三件做过之后才知道要做的事

**一、行号要数到文字本身，不是数到那个 `>`。**
JSX 习惯把标签和正文分行写，`>` 常常待在上一行末尾，
按 `>` 的位置数会少一行，回写时按行号就找不着。

**二、每张表都得有「改为」这一列，哪怕那一节本来就不该改。**
回写脚本认的是「最后一格」。「不要改」那张表原来只有四列，
于是「位置」顶到了最后一格，被当成了填写内容——
dry-run 里冒出 74 条根本没人填的「修改」。

**三、行号允许偏几行，但原文必须对得上。**
清单要人改几天，这几天里代码也在动；上面加三行注释，
下面所有行号整体后移。所以在记下的行号**附近四行**里找原文，
找不到就跳过并报出来。

不全文搜是刻意的：「确定」这两个字在一个文件里可能有十几处，
搜到哪个算哪个、改错了还不报错。行号在这里的作用是「大致位置」，
原文才是身份证。

## 三类文案分开放

| 类别 | 能不能改 | 为什么 |
|---|---|---|
| 普通文案 | 随便改 | 1508 条，绝大多数 |
| 带 `${...}` 的 | 能改字，坑位要留着 | 少一个大括号，那一屏会白掉 |
| 取值类 | **不要动** | 「整租」既显示在界面上，也是 `rent_type` 存的值和筛选传的参数 |

取值类改了会发生什么：筛选按钮点下去一条也搜不出来，而页面不会报错——
它只是安静地返回空列表，看上去像是「真的没有这类房源」。
真要改得连数据库里的存量数据一起改，那是一次迁移，不是一次文案调整。
